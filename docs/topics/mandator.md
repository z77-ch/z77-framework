## mental model

`z77/module-mandator` holds the installation's OWN company — the **Mandant** (owner decisions E1 / E2 of 2026-09-23, reviewed the same day). It is the **letterhead** of the printed reports and letters (name, address, contact data, logo), the UID and the VAT liability, and — since E2 — the **ledger accounts the business modules post with**, which until then were `financialConfig → vatAccounts` and `debtorConfig → debtorAccounts`. ONE record with the FIXED id 1, read through `CurrentMandator`, written through `MandatorService`, edited on one backend page; the two access points that existed before (`LedgerService::vatAccountFor()`, debtor's `DebtorAccounts`) stay the only readers of the account fields. The package depends on kernel and `persistence-doctrine` (ADR-039) only, and `suggest`s `module-financial` — an installation without bookkeeping still has a letterhead, and its account fields are then stored unverified. `module-financial` and `module-debtor` REQUIRE this package.

- **Rule of thumb, both directions (owner, 2026-09-23): the mandator is the letterhead, the payment target is the payee — the two may carry different names, and that is not an error.** IBAN, bank name, bank place and the creditor block of the QR-bill belong to debtor's `PaymentTarget` (`debtor.md`): the account holder as registered with the bank («Peter u/o Regina Ruepp») often differs from the company name, and a QR-bill naming another creditor than the account holder is faulty. The mandator's address is the FALLBACK that creditor block takes field by field when it is left empty (wdv's `picDepositor*()` model, to be built in P3 part 3 — the pending in `debtor.md`), never the source that «serves» the QR-bill. The currency is not here either: `systemConfig → baseCurrency` is the one source (Rule 2).
- **Package choice** (decided 2026-09-23): a package of its own rather than `kernel/shared` (the kernel carries no Doctrine and no Composer dependency, ADR-001 / ADR-039 decision 1) or `module-contact` (the contact is the model of OTHER parties; the mandator is not one, and account fields on it would drag a soft financial boundary into a module that must know no module). Dependency direction: mandator → kernel, persistence-doctrine; financial → mandator; debtor → mandator. financial still knows no posting source (ADR-040 decision 2) — the mandator is master data, not a source. **No `module-vat`** (owner, review 2026-09-23): the default tax code went (below), and with it the only reason a letterhead module dragged the VAT package along — a plain website with a company header must not need it.
- **Doctrine, not file-based** (owner E1: «the table gets an id»): D3 would put a single record into a file; the owner decided a table. Recorded as a deviation from D3 in the known issues, not hidden.
- **`Mandator`** (table `mandator`, no foreign key anywhere): `id` FIXED at `Mandator::ID` = 1 (below), `name` (required), `address_suffix_one` / `_two`, `street`, `house_no`, `zip` (four digits for CH, the `AddressValidator` rule), `city`, `country` (ISO 3166-1 alpha-2, default `CH`), `email` (deliverable when set), `phone`, `website`, `logo_path` (relative to the project root, forward slashes, no `..` — resolved by whatever prints it, the PDF of P3 part 3); `uid` (canonical `CHE-123.456.789`, empty allowed); `liable_to_vat` (a FLAG only — see pending); the eight account columns `account_{key}` (below). Field lengths: name / suffixes / street 120, house no 16, zip 16, city 70, e-mail and website 190, phone 40, logo 255 — letterhead lengths, NOT the QR-bill's (those live on the payment target). Setters for every field (the form posts snake_case through `mapFromArray()`); the accounts are READ through `account($key)` only — the eight typed getters were removed with the review (no production reader).
- **The primary key IS the «one mandator» guard** (review 2026-09-23, finding 3 — P7 measured 24 of 25 racing first saves ending with TWO rows through the old `exists()`-then-flush window, which is wide because the validator makes eight account queries in between). Chosen over a `singleton` UNIQUE column and over compensation after the flush: the id is ASSIGNED (`#[ORM\Id, ORM\Column] private int $id = self::ID`, no `GeneratedValue`; the migration's `id INT NOT NULL` carries no AUTO_INCREMENT), so two first saves both INSERT id 1 and the second fails on the PRIMARY KEY inside the database — `MandatorService::save()` maps the `UniqueConstraintViolationException` to `MandatorAlreadyExistsException`, the screen shows the sentence and reloads. No auxiliary column to explain, no compensation code; `theOne()` is a plain `find(1)`. A row written past the framework under ANOTHER id is dead data — never read, never a second mandator (harness D8). **What a multi-mandator build removes:** the assigned id becomes generated (one ALTER to AUTO_INCREMENT), `Mandator::ID` and `find(ID)` give way to a «current mandator» resolution, and — the real work — every table that belongs to a mandator gets a `mandator_id` and every query its filter. TODAY none of that exists and nothing prepares it (harness A8b: no `mandator_id` anywhere).
- **The UID** (`Services/Uid`, pure like debtor's `Iban`): the setter normalises what a user types (`che 109322551 MWST` → `CHE-109.322.551`, a trailing register suffix MWST / HR / IDE / IVA / TVA dropped); the validator asks two questions with two German sentences — the canonical shape, then the **modulo-11 check digit** (eCH-0097: weights 5 4 3 2 7 6 5 4 over the first eight digits, check = 11 − (Σ mod 11), 11 → 0, 10 → the number is invalid). `CHE-000.000.000` is refused although its arithmetic works out (Σ = 0): nine zeros are a placeholder, and the field is optional. The number RANGE is not otherwise restricted (decided 2026-09-23 on the review's question): the register's actual range was not verified here, and a wrong assumption would refuse real numbers — the check digit already catches 10 of 11 typos. The ` MWST` suffix is NOT stored; whoever prints the VAT number appends it when `liable_to_vat` is set (wdv's `UID/MWST` header did exactly that).
- **The account fields (E2)** — `Mandator::ACCOUNT_KEYS`, key → property: `receivable`, `discount`, `loss`, `rounding`, `dunning-fee` (debtor's five) and `vat-input-material`, `vat-input-other`, `vat-owed` (the three VAT accounts; the categories `standard` / `reduced` / `special` all map onto `vat-owed`). The column / form field is `account_` + `Naming::toSnakeCase(key)` (`Mandator::accountField()`, Rule 5). Each is optional — `''` = «not set», refused AT THE POINT OF USE by the reader that needs it (an installation that never duns needs no dunning-fee account), never on save; `account($key)` returns the number TRIMMED, so whitespace written past the setter never reaches a reader. When set: digits, at most 10 (`Account::NUMBER_LENGTH`, repeated because financial may be absent), and **softly postable**: `LedgerAccountCheck::isPostable()` — `true` / `false` / `null` (= financial not registered, stored unverified). A GROUP, an unknown or an inactive account IS refused when financial is there (`false`), with the field's label in the message.
- **An UNCHANGED account keeps its number** (decided 2026-09-23 on the review's question P3a3 — the reference rule of ADR-043 decision 19 applied to the account fields, the `DebtorProfileValidator::$requireActiveTerms` / `ManualEntryForm` model): `MandatorService::update()` hands the validator only the keys whose number CHANGED (`$checkAccounts`), `save()` all of them. So a letterhead correction never fails on a bookkeeping field that became invalid after the save (a chart change grouped or deactivated the account) — the stored number stays, the screen still flags it («prüfen», from `MandatorAccounts::status()`, which asks every key), the reader still refuses at the point of use. Re-typing that field to another invalid account is a change and refused. Why not «validate everything on every save»: it blocked the address (the review's finding) for a field whose refusal already lives at the use; why not «half-save»: the validator stays whole — it only decides per field whether the bookkeeping is asked.
- **Start values, not a config key** (`MandatorAccounts::DEFAULTS`): the KMU numbers — 1100, 3800, 3805, 3809, 6950, 1170, 1171, 2200 — are constants the screen pre-fills a NEW record with (`prefilled()`), verified against `module-financial/res/charts/kmu.json` by the harness (E2). They are the pre-fill of a form, not a setting; the setting is the record (Rule 2). A project with another chart types its numbers once. **The two old keys are REMOVED** from `financialConfig` and `debtorConfig`, and a key that is still present — a project override copied before the move (BOOT-CONFIG-001) — is refused by its former reader with a GERMAN sentence naming the move (`UnexpectedValueException`; financial's is `VatAccountUnavailableException`), never read as a second source; the journal pages and the debtor / dunning-level screens show that sentence as a red band (`LedgerService::vatAccountNotice()`, `DebtorAccounts::notice()`), the MwSt row of the one-line entry is refused with it, a debtor finalize gets it as `AccountingRefusedException` (owner decision, review finding 4: a band, not a 500).
- **The two access points are unchanged in name and place**, and are the ONLY code that asks the record for an account (harness H4): `LedgerService::vatAccountFor($category)` — an INSTANCE method now (it needs the EntityManager), category → key, `null` for a category without a tax line (zero, exempt, reverse-charge), for a missing mandator or an empty field; the callers (`OneLineEntryForm`, debtor's `LedgerAccountingGateway`) refuse with a German sentence ending in `LedgerService::MANDATOR_HINT` («im Mandanten hinterlegen (Finanzen → Mandant, Konten)»). Debtor's `DebtorAccounts::number()` / `postableNumber()` / `status()` — `number()` is an instance method now — refuse with `AccountNotConfiguredException` naming the key, its label and the mandator (no mandator: «kein Mandant erfasst»). Nothing else may resolve an account from the record — otherwise the resolution stands at twenty places again.
- **Three answers, not two — `CurrentMandator` is three-valued like `LedgerAccountCheck`** (owner decision, review finding 2): a `Mandator`; `null` = none saved yet (a letterhead prints empty, a resolver refuses naming the screen); `MandatorUnavailableException` = the record CANNOT be read, in exactly two installation states — **the module is not registered** (`ModuleManager::getModuleConfig('mandator')` is null: the package is in `vendor/` but the project `composer.json` lacks the psr-4 entry, so the entity is not announced) and **the table is missing** (the module is registered, `z77-db migrate` not run — Doctrine's `TableNotFoundException`, translated in `MandatorRepository::theOne()`). Both carry a German sentence naming the next step; `unavailableReason()` asks without throwing. The readers hand it on: `vatAccountFor()` → `VatAccountUnavailableException` (the one-line form refuses the MwSt row with it, `startFrom()` falls back to the Sammelbuchung, every journal page shows the band), `DebtorAccounts` → `AccountNotConfiguredException` + `notice()` (the band on the debtor and dunning-level screens), the mandator screen itself shows the band and no form. Before the review these states were a 500 on every taxed entry and every finalize — with the misleading text «is not announced as a Doctrine entity». Nothing else is translated: any other database failure stays an error (harness F5e).
- **No lock against «becomes a group»** (decided 2026-09-23, the FIN-TYPE-001 question; the review's probe confirmed it): `lockAccounts()` protects a POSTING in flight, where a row is being written against the account; the mandator is a configuration re-validated at every use — an account turned into a group after the save is refused at the point of use with a message naming the key, and the mandator screen shows «prüfen» on the field (`MandatorAccounts::status()`), so nothing goes unnoticed. A cross-module lock (the chart refusing to group an account the mandator names) was considered and not built.
- **`LedgerAccountCheck` moved here from module-debtor** (Rule 8): two modules now need the same three-valued soft check (the mandator's account fields, debtor's payment target), so it exists once and debtor imports it. Debtor's harness counts exactly ONE class naming module-financial now (`LedgerAccountingGateway`). `postableAccounts()` is the read the screen's `<datalist>` needs — plain arrays, no template touches a financial class.
- **The screen** (`/backend/finance/mandator/edit`, group `finance` next to the chart, the journal and the debtor screens; the record's account settings relate to them and `finance` is UI organisation, not a domain boundary — ADR-005 §11): the fragment/host pattern (ADR-018), `Ui/MandatorControllerTrait` + `MandatorLayout::config()` (pins the body to `edit`), host `Finance/MandatorController` in module-backend with the `defaultAction` deviation `edit` in `backendConfig` (one record, no list — the `report` model). A PAGE form (`#[Csrf]`, `csrf_token`; an existing record additionally checks the entity token `mandator`), the fields in three sections — Briefkopf, UID und MWST, Konten —, the account fields typed by number with a `<datalist>` of the postable accounts when financial is registered, each with a status badge (ok / prüfen / ungeprüft). A hidden `liable_to_vat=0` precedes the checkbox so «unchecked» is submitted. A refused save re-renders the DRAFT (ADR-039 decision 9: the managed entity is never mutated first); a valid one redirects 303 with a flash; an unreadable record shows the German band and no form. No JavaScript, no CSS of its own (Rule 7). The navigation entry is NOT in the kernel seed: a project adds «Mandant» → `/backend/finance/mandator` under its «Finanzen» section (FIN-NAV-001).
- **Migration** `Version20260923160948` (`res/migrations`, namespace `Z77\Module\Mandator\Migrations`): one table, `utf8mb4_unicode_ci`, `ENGINE = InnoDB`, expand only, no FK, `id INT NOT NULL` without AUTO_INCREMENT (the guard). Written to the shape `z77-db diff` generates; `tests/module-mandator.php` A applies it and proves `diff` reports «No changes». Adjusted in place before it was ever committed (the module-contact precedent): the review's fixes — the assigned id, no `default_tax_code` — are folded in, so the module ships one migration.
- **Upgrading an EXISTING installation (z77.ch)** — corrected on the review's finding 1: the installer registers modules from the PROJECT `composer.json`'s `autoload.psr-4` (`Install.php::resolveModules()` over `additionalPsr4Paths`, `installer.md` «adding a module»), NOT from a package's own psr-4 — `composer update` alone leaves the package in `vendor/` unregistered, and then every taxed entry and every finalize refused (before the review with a 500). The real path: (1) add `"Z77\\Module\\Mandator\\": ["override/z77/module/mandator/src/"]` to the project's `autoload.psr-4` (and, in a path-repository project like z77.ch, the path repository for `packages/module-mandator`), (2) `composer update` — the installer registers the module and its source paths, (3) `php vendor/bin/z77-db migrate` on `next`, (4) save the mandator in the backend — the first save pre-fills the KMU accounts; an installation whose chart lacks one of them (z77.ch has no 3809) sees the refusal on that field and empties or repoints it. Until (2) and (3) are done the readers show exactly these steps as their refusal.
- **Where the package is required**: the monorepo ROOT `composer.json`, `module-financial` and `module-debtor` — NOT `skeleton/composer.json`; a project that wants only the letterhead requires it directly.

## rules

- When any code needs the mandator → MUST read it through `CurrentMandator::find()` / `exists()`, treat `null` as «none yet» (an empty letterhead, a refusal with a message) and let `MandatorUnavailableException` (module not registered, table missing) reach the user as ITS German sentence — a band, a refusal, a field error; MUST NOT `find(1)` on the repository from outside the module, MUST NOT create a record on access and MUST NOT let a missing or unreadable mandator end in a 500
- When a module needs an account the mandator carries → MUST ask its own access point — `LedgerService::vatAccountFor($category)` for a VAT account, `DebtorAccounts::number()` / `postableNumber()` for a debtor account — and refuse with a message naming the key and the mandator when it answers null / throws; MUST NOT call `Mandator::account()` or `CurrentMandator` from anywhere but those two classes (harness H4) and MUST NOT keep a copy of a number in a config
- When a screen of financial or debtor renders a page that depends on the account settings → MUST show `LedgerService::vatAccountNotice()` / `DebtorAccounts::notice()` as a red band when it is not null (a leftover config key, an unreadable mandator); MUST NOT let `VatAccountUnavailableException` / the `UnexpectedValueException` of a leftover key propagate to the kernel handler
- When a new module needs a NEW account of the company (creditors, the year-end) → MUST add the key to `Mandator::ACCOUNT_KEYS` with its column (expand migration), its label and its KMU start value in `MandatorAccounts`, and ONE access point in the reading module; MUST NOT add the column before the reader exists (CLAUDE.md «no just-in-case») and MUST NOT resolve the number in more than one place per module
- When writing the mandator from any code path (backend, import) → MUST go through `MandatorService::save()` (the first record) / `update($mandator, $values)` (cleaned snake_case values onto a detached draft first — ADR-039 decision 9); MUST NOT `persist()` a `Mandator` directly, MUST NOT call setters on the managed entity before validation, and MUST NOT catch the primary-key violation anywhere but in `save()`
- When an account field is validated on an UPDATE → MUST check only the keys whose number CHANGED against the bookkeeping (`MandatorService::changedAccounts()` → `MandatorValidator::$checkAccounts`), so an unchanged number survives a chart change (ADR-043 decision 19); MUST check EVERY key for a NEW record and when the screen shows the state; MUST NOT skip the shape rules (digits, length) for any field
- When a project override of `financialConfig` or `debtorConfig` still carries `vatAccounts` / `debtorAccounts` → MUST remove the key (the readers refuse it with a German sentence naming the move, shown as a band) and set the numbers on the mandator screen once; MUST NOT reintroduce either key as a fallback or a default
- When registering this module on an EXISTING installation → MUST add the psr-4 entry `"Z77\\Module\\Mandator\\": ["override/z77/module/mandator/src/"]` to the PROJECT `composer.json` (plus the path repository where packages are consumed by path), run `composer update`, then `php vendor/bin/z77-db migrate` on `next`, then save the mandator; MUST NOT expect `composer update` alone to register the module — the installer reads the project's psr-4, not the package's
- When a bank connection, an IBAN or the creditor block of a QR-bill is needed → MUST take it from debtor's `PaymentTarget` (P3 part 3 adds the creditor block there, with the mandator's address as the field-by-field FALLBACK); MUST NOT add IBAN, bank or currency fields to the mandator — the letterhead and the payee may differ, and that is not an error
- When a UID is stored → MUST go through `Mandator::setUid()` (normalisation) and let `MandatorValidator` check shape AND check digit (`Uid`); MUST NOT store the ` MWST` suffix — whoever prints the VAT number appends it when `liable_to_vat` is set — and MUST NOT restrict the number range beyond the all-zero refusal without verifying the register's range first
- When an account field is validated → MUST allow `''` and MUST treat `LedgerAccountCheck::isPostable()` `null` as «cannot tell, store unverified»; MUST refuse `false` naming the field's label; MUST NOT require module-financial to be registered
- When a screen needs the postable accounts for a picker → MUST read `LedgerAccountCheck::postableAccounts()` (plain `{number, label}` rows, `[]` without financial); MUST NOT `use` a `Z77\Module\Financial\…` or a `Z77\Module\Vat\…` class anywhere in this module (harness H1 — financial is named as a string, vat is no dependency)
- When the mandator screen is mounted elsewhere → MUST `use MandatorControllerTrait`, delegate the layout to `MandatorLayout::config()`, override `mandatorBase()` to the mount's URL root and give the controller `defaultAction` `edit`; MUST NOT add a list, an add or a delete action — one record
- When multi-mandator capability is ever wanted → MUST be built as its own block: the assigned id becomes generated (AUTO_INCREMENT, one migration), a `mandator_id` column on every table that belongs to a mandator PLUS the filter in EVERY query of every module PLUS a «current mandator» resolution replacing `Mandator::ID`; MUST NOT be read into the existing id, and MUST NOT start with a column on one table and no filter (a half-built tenancy is worse than none)
- When adding a column or an entity to this module → MUST run `php vendor/bin/z77-db diff --namespace="Z77\Module\Mandator\Migrations"` and commit the reviewed migration with the entity, expand/contract; MUST NOT change `Version20260923160948` once an installation may have applied it

## known issues

- **MANDATOR-ONE-001** — resolved 2026-09-23 (review finding 3): the guard is the PRIMARY KEY (assigned id 1), so two first saves racing end with ONE row and the loser sees `MandatorAlreadyExistsException` — proven by the review's two-process probe (P7, 25 of 25 rounds one row after the fix; 24 of 25 with two rows before). What remains: don't assume the database forbids a row under ANOTHER id — a hand INSERT of id 7 succeeds and is simply never read (`theOne()` is `find(1)`); the row is dead data to remove by hand.
- **MANDATOR-VAT-001** — don't assume `liable_to_vat` switches anything off yet: it is stored and shown, nothing reads it. What it should hang on is the owner's decision (pending) — until then an installation not liable to VAT posts VAT wherever a tax code is chosen.
- **MANDATOR-LOGO-001** — don't assume `logo_path` is checked against the file system: the validator checks the shape only (relative, no `..`). Whether the file exists is the printer's business (P3 part 3), which must degrade to «no logo» rather than fail.
- **MANDATOR-D3-001** — don't assume the record follows plan decision D3 («Doctrine where needed, everything else file-based»): a single record with no transaction and no report would be a file entity by D3; the owner decided a table (E1). Recorded here as the deviation, not silently. A file entity would also have worked on an installation WITHOUT a database (a plain website with a letterhead) — such an installation cannot have a mandator today.
- **MANDATOR-NAV-001** — don't expect a «Mandant» entry in the navigation after install: the kernel seed carries none (like FIN-NAV-001); the project adds it under its «Finanzen» section → `/backend/finance/mandator`.
- **MANDATOR-STALE-001** — don't assume a saved account number stays valid: the chart can deactivate or group it afterwards. The record KEEPS the number (an unchanged field is not re-checked on save — the address must stay editable), the screen flags it («prüfen»), the reader refuses at the point of use — the same three places as before E2, only the number now lives in the record instead of a config. Retyping the field is a change and must name a postable account.
- **MANDATOR-UID-001** — don't assume the UID validator knows the register's number range: it checks shape and check digit and refuses the all-zero number only. A syntactically valid UID that was never assigned passes; the range is deliberately not narrowed (a wrong assumption would refuse real numbers).
