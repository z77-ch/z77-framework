## mental model

A creditor is a CONTACT with a creditor profile — the debtor model (creditor plan §2.2): name, address, language and e-mail stay on the contact, a supplier who is also a customer is one party. The contact editor's role «Kreditor» (module-contact's `contactRoles` registry) opens an empty profile; the master-data screen «Kreditoren» (Stammdaten › Finanzen) edits UID, IBANs and the defaults a new invoice line starts with. Stage 1a (2026-11-15) built this. Stage 1b (2026-11-15) built the creditor INVOICE: the PDF upload and the «Kreditorenjournal» (Finanzen), where an invoice is checked, split into lines, and a suspected duplicate released or discarded. Stage 1c (2026-11-15, [ADR-059](../02-decisions/adr-059-creditor-module.md)) brings the paid invoices into the books: «Bezahlt am …», then «Journal verbuchen …» up to a cut-off on the PAYMENT date — the direct variant (cash principle).

- **Module direction:** creditor REQUIRES contact, vat, mandator, financial, receipt (owner answer 1: payment methods, field rules, later the rate proposal) and dms (the PDF, from 1b). None of them names creditor (harness O2); creditor names no debtor class.
- **`creditor_profile`:** `contact_id` (unique), `uid` (canonical `CHE-…`, unique, NULL = none — recognition in stage 2 takes an exact UID over the IBAN, so one UID names one creditor), the defaults `default_account` (number), `default_tax_code` OR `default_without_vat`, `default_payment_method_code` (module-receipt's `PaymentMethod` code) — all by code, no foreign key (ADR-043 decision 19) —, `defaults_set_at` / `defaults_set_by`, `active`, `version`. No creditor number (plan §2.2).
- **`creditor_iban`:** several per creditor, stored normalised, `is_qr_iban` derived, `hint`, `active`. The index on `iban` is NOT unique — a shared IBAN (a billing or collection company) is allowed; `CreditorIbanRepository::findProfilesByIban()` answers 0, 1 or n creditors (active links and active creditors only by default). One creditor lists an IBAN once (`uniq_creditor_iban_profile`). Any country — a supplier abroad has a foreign IBAN; the MOD-97 check digits are what is insisted on. Nothing references a row (an invoice will SNAPSHOT the IBAN), so the window removes a row by emptying it.
- **The defaults stamp (plan §5):** NULL = no defaults decided; a saved invoice fills the missing ones (learned defaults, below) and stamps. A change of the defaults through the window stamps actor + time (they are decided now); emptying all of them clears the stamp. An IBAN-only change leaves the stamp alone.
- **Optimistic lock:** `version` is a plain column the SERVICE bumps on every write (an IBAN-only change does not touch the profile row, so Doctrine's `ORM\Version` would not count it). `update()` validates a detached draft FIRST, then locks the row `FOR UPDATE`, compares the version, reads it fresh, applies, syncs the IBANs (same IBAN kept with its id, new ones added, missing ones removed), bumps.
- **Validation** (`CreditorProfileValidator`): UID shape + modulo-11 check digit (module-mandator's `Uid`), unique; account and tax code through module-receipt's `ReceiptFields` (exists, postable / active, splits a gross amount); payment method exists and is active — each only when CHANGED (an unchanged reference deactivated since is kept); a tax code and «ohne MWST» never together; a mandator NOT liable to VAT refuses a tax code (owner answer 5 applied to the defaults; 1c forces «ohne MWST» on the invoice lines); IBAN rows: shape, check digits, once per creditor, hint ≤ 80.
- **The role «Kreditor»** (`CreditorContactRole`): on = `open()` (refused for an inactive contact or a contact that already is a creditor); off = `delete()` (profile + IBANs) after the dialog's `offConfirm` — only while no invoice names the creditor: with invoices the state is not switchable (reason «… nur deaktiviert werden», the summary counts them) and `delete()` refuses `CreditorRefusedException::IN_USE` (asked before and under the lock).
- **The invoice (1b, `Version20261115120000`, plan §2.3):** `creditor_invoice` carries from the start what 1c, stage 2 and the collective variant need — creditor or the recognised `creditor_proposal` (JSON), intake, PDF (`document_id`), number, invoice / due date, IBAN snapshot, `reference_type` (QRR / SCOR / NON, DERIVED from the reference) + reference, message, `amount` CHF + the receipt FX columns (`original_amount` / `original_currency` / `exchange_rate` — used since stage A0, below), payment state / `paid_on` / payment method / credit account, `posting_variant` snapshot `direct`, state `open` / `blocked` / `posted`, the duplicate mark, `recognition`, who / when, `version` (`ORM\Version`). Lines (`creditor_invoice_line`, owner answer 2): position, text, gross amount, account, tax code OR `without_vat`; replaced as a set on save. `creditor_journal_posting` exists (empty until 1c). `missing()` (German): Kreditor, Betrag, Bezahlt mit, Konto, MWST, «Zeilen = Betrag».
- **Intake (`CreditorIntakeService::receive()`, plan §3):** sniffs the BYTES (not empty, ≤ `creditorConfig['intake']['maxBytes']` 20 MiB, `%PDF-` in the first KiB AND `finfo` = application/pdf), SHA-256 → a hash read before is refused `DUPLICATE_FILE` «bereits eingelesen am … (Rechnung …)» and stores nothing (owner answer 4; `creditor_intake.sha256` UNIQUE decides a race); stores the PDF unaltered through `DocumentService::forModule('creditor', 'Kreditorenrechnungen')` → `<fiscal year>/<month of receipt>` (`saveGenerated`, checksum compared); then ONE unit of work: intake row + invoice (open, unpaid, direct) + ONE line — on the creditor's defaults when a creditor is handed in. No session needed (actor as data), ready for the stage-2 folder job.
- **Saving an invoice (`CreditorInvoiceService::update()`):** values through module-receipt's `ReceiptFields` plus IBAN / QR / RF checks (QRR only with a QR-IBAN, SCOR never with one); the creditor's defaults fill what is EMPTY (line account, line VAT, «Bezahlt mit» + Haben); one line without amount takes the invoice amount; a mandator NOT liable to VAT forces «ohne MWST» on every line and refuses a typed tax code (owner answer 5); then under the row lock: head + lines, the duplicate check, the LEARNED DEFAULTS (below; «als Standard übernehmen» on a complete invoice overwrites on purpose via `CreditorProfileService::takeDefaults()`).
- **Learned defaults (owner 2026-11-16: «ich möchte nicht den Umweg über Kontakt → Kreditor machen müssen; wenn noch kein Konto hinterlegt ist, soll er einfach den übernehmen, den ich bei der Rechnung eintrage»; replaces «defaults once» = the first COMPLETE invoice):** every save of an invoice with a creditor (`update()`, and `adoptCreditor()`) calls `CreditorProfileService::learnDefaults()` in the same unit of work: the creditor WITHOUT a default account takes the first line's account, together with that line's VAT decision while it has none (they belong together — the VAT only with an account learned now or equal to the default); WITHOUT a default «Bezahlt mit» it takes the invoice's. Only empty parts, never an existing default; each value judged by the creditor window's own `CreditorProfileValidator` (account exists, postable, active; tax code active and allowed for the mandator; payment method active) — a refused one is not learned. Stamped, version bumped. `update(…, &$learned)` hands what was learned to the screen; the flash says it («Konto 6500, MWST VM und «Bezahlt mit» Bank als Standard für Digitec Galaxus AG gespeichert.»). Invoices adopted or matched later get the learned defaults.
- **Suspected duplicate (owner answer 4):** on every save (and adopt) `CreditorInvoiceRepository::findDuplicate()` — same creditor + invoice number, or same IBAN + reference, on any other invoice (any state) — marks THIS invoice `blocked` with «mögliches Doppel von Rechnung … — …»; a match gone (typo fixed) lifts the mark. Settled pairs are skipped both ways: the invoice the owner released this one against (`duplicate_cleared_of`), and any invoice already marked or released as a duplicate of this one — so saving the original never blocks it. «Kein Doppel — übernehmen» = `release()`; «Verwerfen …» = `delete()`.
- **Delete (owner 2026-11-15, 1c):** «Löschen …» of an UNPOSTED invoice removes it COMPLETELY — invoice, lines and intake row; its file hash is free, the same PDF may be uploaded again; the screen moves the PDF to the DMS trash (`DocumentService::delete()` with the session — restorable; a failure is logged and the flash says the PDF stayed). «Verwerfen …» of a BLOCKED invoice (a confirmed duplicate) removes invoice and lines but keeps the intake row as `discarded` — the file stays refused («bereits eingelesen … als Doppel verworfen»), the PDF stays. A posted invoice cannot be deleted (`lockAt()` refuses `changed`). `delete()` answers `{documentId, freed}`. **A blocked invoice's window offers BOTH (owner 2026-11-16: «ja löschen auch im fenster anbieten»):** «Verwerfen …» (`confirm-delete?id=…`, unchanged) and «Löschen …» (`confirm-delete?id=…&completely=1`, help sections `discard` / `delete`); the confirmation keeps its last look and posts `completely=1` on, `confirmDeleteAction()` hands it to `delete(…, completely: true)` — the same path as the bulk «Löschen …»: the invoice goes completely, the hash is free, the PDF to the DMS trash.
- **Bulk «Löschen …» (owner 2026-11-16, live look at z77.ch: «alle auswählen und löschen»; «gesperrte müsste man löschen können genau gleich»):** the selection bar of «Im Journal» AND «Gesperrt» carries «Löschen …» (danger) — in «Im Journal» next to «Bezahlt am …», in «Gesperrt» ALONE (owner 2026-11-16: «ja nur löschen, macht sinn oder sonst wäre er ja nicht gesperrt»; the form's own action is then `confirm-delete-selected`) — the same GET form `#creditor-selection` (`CreditorJournalListing::SELECTION`), the button's `formaction` opens the window `confirm-delete-selected` («47 Rechnungen löschen?», the invoices compactly, «Doppel?» marked). Its POST (`#[Csrf]`, the pairs as hidden `inv[]` = `{id}:{version}`) is `CreditorInvoiceService::deleteSelected()`: in id order, each through `delete($id, $version, completely: true)` in its own unit of work — open AND blocked invoices go COMPLETELY (lines and intake row, the hash free, the PDF to the DMS trash by the screen); a row changed, posted or deleted since is skipped and named in the flash («Nicht gelöscht: …»), the others are deleted; an empty selection is refused (`selection`). The single window of a blocked invoice offers «Verwerfen …» (the file stays refused) AND, since 2026-11-16, «Löschen …» (completely, as the bulk path).
- **«alle» (owner 2026-11-16, Rule 9):** the selection column is `Column::checkAll(SELECTION)` — the list head carries the checkbox «alle» (kernel `partials/listHead`, `data-check-all`, label rendered `hidden`), core.js «check all» (`_Z77.core.checkAll`, revealed by `wire()`) ticks / clears every row checkbox of the form and shows a partial selection as indeterminate. A shared building block (listing.md, fetch.md), not the DMS's own «Alle / Keine» (drive.js).
- **A deleted invoice stops its recognition (owner 2026-11-16):** the job meets it gone and drops the result — no error, nothing counted, nothing written back: `find()` null → skipped; its PDF gone (trashed) → `endRecognition()` answers null, no «PDF nicht lesbar» note; the text or AI step's `applyRecognition()` finds no row (`lockRow()` null) → `recognize()` answers null, not counted as recognised; before an AI step the job asks the DATABASE (`CreditorInvoiceRepository::isInJournal()`, not the identity map) — an invoice deleted after its text step is never sent to the AI.
- **«Bezahlt am …» (1c, plan §6):** the payment date — the posting date of the direct variant; a valid day, never in the future; `paid` ⇔ `paid_on` set (`CreditorInvoice::markPaid()`). Per invoice in the window (field `paid_on` of `update()`: '' = unpaid again, the key ABSENT = unchanged), or for ticked rows of «Im Journal» at once: the selection bar above the list (GET form `#creditor-selection`, `data-window-form`, checkboxes `inv[]` = `{id}:{version}`, «alle» in the head) opens the window `confirm-paid` (the invoices, the date — proposed today —, optionally «Bezahlt mit» for all); its POST is `markPaid($pairs, $date, $method)` — one unit of work, rows locked in id order; a row changed / posted / deleted since is NOT written and named in the flash, the others are. **A blocked invoice is not marked paid in bulk (owner 2026-11-16: a suspected duplicate is decided first):** the tab «Gesperrt» shows no «Bezahlt am …», and `markPaid()` refuses a ticked blocked row by itself («… gesperrt (mögliches Doppel) — zuerst entscheiden, nicht gesetzt») — until then it accepted one. The window's field «Bezahlt am» of a blocked invoice is still open (not part of the decision), and an invoice paid before it became blocked stays paid — the run then refuses it as blocked.
- **«Journal verbuchen …» (1c, owner answer 3):** the action cell (green; disabled while nothing is paid) opens the posting window (`confirm-post`, the shared `partials/postConfirm`, cut-off proposed today, a GET filter re-renders it). The RUN = every invoice still in the journal (open or blocked) with `paid_on` ≤ cut-off; unpaid invoices and later payments are not in it and block nothing. `CreditorJournalPostingService::preview()` names what blocks (blocked as a suspected duplicate, incomplete — `missing()`, not buildable — e.g. a tax code while the mandator is not liable, no fiscal year, a closed or VAT-settled period) — then the window shows only those errors with links. `post($cutOff, $seen)` (the receipt pattern): rows locked EXCLUSIVE in id order, each at the version shown, the run compared with `paidIdsUntil()` (one paid / changed since = `changed`), a blocked or incomplete one refuses the WHOLE run, then the protocol row and per invoice (payment date, id order) its strategy's payment posting → `LedgerService::post()` → `CreditorInvoice::post()` (state `posted`, entry ref, protocol, who / when — immutable from then on: every write asserts open / blocked). All or nothing; the ledger's refusal comes out as `ledger` naming the invoice.
- **Foreign currency by hand (stage A0, owner 2026-11-15 — decision 1 of the bank account service plan; follows receipt's FX plan F2–F5, F7, F12, not re-invented):** an invoice in USD / EUR (Tinify, USD 9.00) keeps its printed amount and currency (`original_amount` / `original_currency`, columns of `Version20261115120000` — no migration); `amount` is the CHF the bank or card actually DEBITED (fees included, e.g. CHF 8.12), typed by the owner — it may stay EMPTY: the invoice is then incomplete (`missing()` names «Betrag CHF», `CreditorInvoice::amountLabel()`), it can still be marked paid (as any incomplete invoice) but the run refuses it («es fehlt: Betrag CHF»). The currency list is receipt's — `receiptConfig['foreignCurrencies']`, read ONLY by `ReceiptFields::foreignCurrencies()` (created with A0, receipt FX plan T3; default EUR, USD — F7 named only EUR, USD added for the creditor invoices); `ReceiptFields::foreignCurrency()` refuses a currency outside the list («Währung GBP ist nicht freigegeben (erlaubt: CHF, EUR, USD).») except the invoice's own, `originalAmount()` requires the amount with a foreign currency and refuses one without. `update()`: the key `currency` ABSENT = the original unchanged; CHF / '' = a CHF invoice (an original amount then refused). The rate is DERIVED (`ReceiptFields::derivedRate()` — CHF per unit, 6 places, half away from zero, integer long division; `CreditorInvoice::derivedRate()`), shown under «Betrag CHF» («Kurs 0.902222»), never typed and NOT stored (`exchange_rate` stays NULL — F12: CHF is free). Never set = ON (z77.ch released the AI before the switch existed and keeps running it); an unreadable file = OFF and logged (no paid call on an unreadable choice). `CreditorRecognitionService::recognize()` runs the AI step only when released AND on, reading the file at EVERY invoice (no cache): switching off stops every AI step not yet started — an invoice already marked or queued keeps going, its text step runs, an AI call already waiting finishes; «Jetzt erkennen» follows the switch because it only queues the job. Off with an unresolved invoice → the note «nicht erkannt, KI-Erkennung ausgeschaltet — von Hand erfassen» (`NOTE_AI_OFF`). The toggle is `ai-switch` (POST, `#[Csrf]`, the route's module role ADMIN like every journal action): with the script the core `data-fetch-toggle` POSTs `{value: bool}` (set, not flipped; an error reverts the switch), without it the form posts the checkbox through a `<noscript>` «Übernehmen» and the page comes back with a flash. The server re-checks POST, the release and the value's type.
- **Learning per creditor (owner 2026-11-16, «ja starten» — the plan of 2026-11-15 built without waiting for the 20-invoice AI trial; trigger: with the AI off, Digitec, Swisscom, cyon (QR-IBAN) and SBB (UID) were found, but NOT the foreign creditors Tinify (USD, no slip, no Swiss UID) and Allegion (NL) although both exist; owner: «er soll einen bestimmten Bereich einer Rechnung, der immer gleich ist, definieren und ablegen, so dass er ihn erkennt»):** `Services\CreditorLearningService`, two tables (`Version20261116100000`). Never a hash of the whole text (date, amount and number change every time).
  - **The text is kept (`creditor_invoice_text`):** pdftotext runs only in the job (CREDITOR-RECOG-WEB-001), the owner settles an invoice in a web request — so the text step's `applyRecognition(…, $text)` stores the layout text the job read (one row per invoice, replaced by a re-run, ≤ 256 KiB, deleted with the invoice by `delete()`), and the learning reads it back. Chosen over a learning step in the job: no second extraction, no deferred queue, and the next invoice of the same batch already profits. Its own table, so a list of invoices never loads the texts. An invoice recognised before this deploy has no text — «Jetzt erkennen» keeps it, the next save learns.
  - **Who sent it (`Recognition\SenderFeatures`):** a foreign VAT number in its national format (`NL…B01`, `DE…`, `ATU…`, `EU…` OSS, `GB…`, … — normalised; never an IBAN: fixed lengths, no digit may follow), the registrable domain of a mail address / URL / bare host (generic mail hosts and payment platforms in `GENERIC_DOMAINS` and the mandator's own e-mail / website domains never count), the sender line = a column segment of the layout text that contains the creditor's contact name (never one of the own company — the mandator's name and street, `Recognition\OwnParty` —, never one with a date, an amount or a month and year; ≤ 5 per invoice). Learned when the OWNER settles the creditor: every `update()` with a creditor and every `adoptCreditor()` (also each carried-over invoice) calls `learnFromInvoice()` in the same unit of work — only new values (`creditor_learned.value` compares binary, `utf8mb4_bin`).
  - **Matching (`CreditorRecognitionService::match($facts, $text)`):** IBAN and UID first, unchanged; then the learned features — a feature counts only when exactly ONE active creditor holds it; weights `vat` 2, `domain` 1, `sender` 1; a creditor whose unique features weigh ≥ 2 is decided (`match` = `learned`, `steps.text.learned_by` = the `kind:value` that decided; the window: «Kreditor am Gelernten erkannt (MWST-Nr. …)»). A domain alone never decides. Several decided, or only weak hits → `learned-choose` with the candidates (the list: «Kreditor wählen (passt zu: …)»; the AI still runs); IBAN / UID name one creditor and the features another → `learned-conflict`, both candidates, no pick; a shared IBAN is decided by the features when they name one of its creditors. The owner putting ANOTHER creditor on an invoice the features chose (`match` = `learned`) takes those features away from the wrong one (`forgetFeatures()`) — the right one learns them with the same save.
  - **The labels (`Recognition\LearnedLabels`, `kind` = `label`):** per creditor one label per field (`invoice_number`, `invoice_date`, `due_date`, `amount`): the words printed right before the value on its line (after the last token with a digit) or the column head right above it; a label naming the field wins («Amount due», «Rechnungsdatum»), else the last amount / the first other value; kept only when reading the text at it gives exactly the value again. Dates in every form the module reads plus «October 1, 2026», «1 Oct 2026», ISO, and a month-first numeric date (`date_order` = `mdy`). The amount with its currency (`currency`) — A0: a foreign invoice's ORIGINAL, never the CHF the owner typed. Reading: at every place the label stands, ONE distinct value, else nothing; an amount with another currency sign beside it = nothing, without a sign only when the text names the learned currency. Learned from the AI's answer in the job (`afterAi()`) and from the invoice's values when the owner saves / adopts (`learnFromInvoice()`): a label that reads another value than the invoice now has is learned again (trust 0), one the text does not print is dropped.
  - **The AI only when needed:** with the creditor known (set, matched by IBAN / UID / features), `read()` reads its labels; `InvoiceFacts::withLearned()` fills what the text step left empty (source `text-learned` → «Text»; QR amount, Swico S1 and the general header labels win). `agreed` counts how often PHP's reading and the AI's answer agreed; when the required labels (number, invoice date, amount) agreed `TRUST_AFTER` = 2 times AND read their value now, the invoice counts as resolved and the AI step is left out (`steps.text.learned` = `trusted`, the window: «Werte an den gelernten Stellen gelesen, die KI war nicht nötig»). Before that, with the AI released and switched on, the learned values are NOT filled — the AI reads (`learned` = `compare`) and PHP is compared after it; with the AI off they are filled (`used`). A required value missing or implausible → not trusted → the AI reads → the label is learned again. Text-layer PDFs only — a scan has no text.
  - **The creditor window («Kreditoren»):** the section «Gelernt aus Rechnungen» (read-only): «Erkannt an: MWST-Nr. … · Domain … · Absender «…»», «Liest: Rechnungs-Nr. bei «Invoice number» · … · Betrag in USD bei «Amount due»», and the trust in plain words («Noch in Prüfung (1 von 2 Vergleichen mit der KI)» / «… die KI wird für diesen Kreditor nicht mehr gebraucht»). «Gelerntes vergessen» (ghost, in the action row — only when something is learned) is a submit of the window form to `forget-learned` (POST, `#[Csrf]`, the window's entity token, the route's module role ADMIN like every write of the screen) → `forget()`; nothing typed is saved; the window closes and the list reloads. A deleted creditor profile takes its rows with it (`CreditorProfileService::delete()`).

## rules

- When a contact must become a creditor → MUST go through `CreditorProfileService::open()` (the role «Kreditor», later «Kreditor übernehmen …»); MUST NOT persist a `CreditorProfile` directly
- When changing a creditor → MUST call `CreditorProfileService::update($profile, $version, $values, $ibanRows)` with the version the screen showed and the COMPLETE list of IBAN rows (`CreditorProfileService::ibanRows()` cleans what a form posts); MUST handle `CreditorRefusedException::CHANGED` by reloading
- When the defaults of a creditor are set by anything but the creditor window (an invoice save through `learnDefaults()`, «als Standard übernehmen») → MUST fill only EMPTY defaults through `CreditorProfileService::learnDefaults()` (the window's validator judges them), MUST stamp `defaults_set_at` / `defaults_set_by` through the entity's `stampDefaults()` and MUST NOT overwrite defaults while the stamp is set unless the owner asked for it (plan §5)
- When matching an invoice to a creditor by IBAN → MUST use `CreditorIbanRepository::findProfilesByIban()` and treat n > 1 as «choose» (the hint decides only on exactly one hit); MUST NOT make `creditor_iban.iban` unique or pick the first of several (plan §2.2, never a guess)
- When checking an IBAN, a QR reference or an RF reference anywhere in the framework → MUST use `Z77\Shared\Payment\Iban` / `QrReference` / `ScorReference`; MUST NOT copy the check into a module
- When a creditor invoice carries a foreign currency → MUST take it from receipt's ONE list (`ReceiptFields::foreignCurrencies()` / `foreignCurrency()`, `receiptConfig['foreignCurrencies']`) and MUST NOT add a second list or config key; MUST post CHF only (`amount`, ADR-042 decision 4), MUST NOT accept a typed rate or store a derived one in `exchange_rate`; the original goes into the posting text only through `DirectPosting::text()`
- When a creditor default or line names an account or a tax code → MUST judge it through module-receipt's `ReceiptFields`; MUST NOT add a second rule set
- When the mandator is not liable to VAT → MUST NOT accept a tax code on a creditor default and MUST force «ohne MWST» on every creditor invoice line (`CreditorInvoiceService`, owner answer 5) — a typed code is refused, an undecided line is set
- When a supplier file enters the installation (upload, the folder job) → MUST go through `CreditorIntakeService::receive()` (it writes the invoice «Erkennung ausstehend»); from a request MUST then queue the job (`CreditorIntakeJob::queue()`); MUST NOT store a creditor PDF or create an invoice another way (the sniff, the hash idempotency and the DMS place live there)
- When recognising an invoice (pdftotext, the AI) → MUST run in the job `creditor-intake` (`CreditorRecognitionService::recognizePending()`, the PDF through `CreditorIntakeService::storedPdf()`); MUST NOT call `recognize()` in a web request — a host's web PHP may forbid `proc_open()` and the AI may take minutes (CREDITOR-RECOG-WEB-001); MUST NOT add a `popen()` / `exec()` fallback (owner: it depends on another host setting); MUST NOT ask a host to enable `proc_open()` for the web — the owner keeps it disabled on purpose (2026-11-15: a hole in any site of the hosting account would otherwise start programs on the server)
- When deciding whether the AI step runs → MUST require BOTH the release (`AiSettings::enabled()` — `creditorAi.enabled` + key) AND the owner's switch (`AiSwitch::isOn()`, read per invoice, no cache); MUST NOT render or accept the switch while the AI is not released; MUST NOT persist the owner's choice by writing `config/client/kibot.inc.php` or any PHP config from a request (CREDITOR-AI-SWITCH-001)
- When a recognition step (text layer, AI, a later one) has values for an invoice → MUST hand them as `InvoiceFacts` to `CreditorInvoiceService::applyRecognition()`; MUST NOT overwrite a non-empty field, MUST NOT pick one of several creditors behind a shared IBAN, MUST NOT turn the AI's expense category into an account (owner answer 9, plan §5)
- When a file leaves the intake folder after it was read → MUST compare the DMS document's checksum with the file's SHA-256 first (`CreditorIntakeFolder`); MUST NOT add a `processed/` folder (owner answer 7) and MUST NOT follow a symlink or use a file name outside the folder
- When changing a creditor invoice → MUST call `CreditorInvoiceService::update()` / `markPaid()` / `release()` / `delete()` / `adoptCreditor()` with the version the screen showed; MUST NOT write `CreditorInvoice` or its lines directly — the duplicate check, the VAT forcing and the learned defaults run there
- When adopting a proposed creditor → MUST go through `adoptCreditor()` (it carries the creditor over to the same party's invoices); MUST NOT create a contact in «Kreditor übernehmen …» while `creditorSameContacts()` finds one, unless `confirm_new` was posted; MUST NOT widen «same party» to a similar name or a shared IBAN (conservative: in doubt, no creditor)
- When deleting creditor invoices in bulk → MUST go through `CreditorInvoiceService::deleteSelected()` with the `{id, version}` pairs the list showed (each through `delete(…, completely: true)`); MUST NOT delete a row whose version changed or that was posted — skip and name it
- When marking creditor invoices paid in bulk → MUST go through `markPaid()`, which refuses a BLOCKED invoice (owner 2026-11-16: decide the suspected duplicate first); MUST NOT offer «Bezahlt am …» in the tab «Gesperrt» (only «Löschen …»); the same in the invoice window — `update()` refuses a new paid date on an invoice that is still blocked after the save's duplicate check, and the field is disabled there
- When the recognition job is about to call the AI for an invoice → MUST ask `CreditorInvoiceRepository::isInJournal()` (the database, not the identity map) first; MUST treat `applyRecognition()` / `endRecognition()` answering null (the invoice gone or posted) as «dropped», never as an error
- When deleting a creditor invoice → MUST go through `CreditorInvoiceService::delete()`: an unposted invoice frees its intake row (the hash), a discarded duplicate keeps it as `discarded`; MUST NOT delete a posted invoice or an intake row elsewhere (owner 2026-11-15) — the one exception is a `failed` row of the folder channel, removed by `CreditorIntakeFolder::retry()` / `remove()` / `removeSelected()` (each through `remove()`)
- When posting creditor invoices → MUST go through `CreditorJournalPostingService::post()` with the `{id, version}` pairs the confirmation showed and the cut-off on the PAYMENT date; MUST resolve the strategy from the invoice (`CreditorPostingVariant::strategyFor()`), MUST NOT read `postingVariant` anywhere but `CreditorPostingVariant::current()`; MUST NOT build creditor posting lines outside a strategy (they come from `GrossEntryBuilder`)
- When adding the collective variant → MUST add a `CreditorPostingStrategy` and list it in `CreditorPostingVariant::BUILT`; MUST NOT re-interpret existing invoices (their `posting_variant` snapshot decides) and MUST allow a switch only at a fiscal-year start with no open invoice (plan §2.4)
- When a creditor has invoices → MUST NOT delete its profile (`CreditorProfileService::delete()` refuses IN_USE); deactivate it
- When a creditor should be recognised without IBAN or Swiss UID → MUST learn through `CreditorLearningService` (`learnFromInvoice()` on the owner's save / adoption, `afterAi()` in the job) from the text the job kept (`creditor_invoice_text`); MUST NOT extract text in a web request (CREDITOR-RECOG-WEB-001) and MUST NOT match by a hash of the whole text
- When matching by learned features → MUST count only a feature exactly one active creditor holds and decide only at the weight `SenderFeatures::DECIDES` (a VAT number, or two of domain / sender line); MUST list candidates for several creditors or a conflict with IBAN / UID and MUST NOT let a learned feature override an IBAN or UID match
- When learning features → MUST NOT learn anything of the installation's own company (`OwnParty`: the mandator's name, street, e-mail and website domains) nor a generic mail host or payment platform (`SenderFeatures::GENERIC_DOMAINS`)
- When learning an amount label → MUST learn the printed amount in its currency (a foreign invoice's original, stage A0); MUST NOT learn the CHF amount the owner typed for a foreign invoice
- When deciding whether the AI step may be left out → MUST require the required labels (`LearnedLabels::REQUIRED`) agreed `CreditorLearningService::TRUST_AFTER` times with the AI AND reading their value now; MUST let the AI read (and relearn) when a learned value is missing or implausible
