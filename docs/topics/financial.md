## mental model

`z77/module-financial` (plan §5, ADR-040, ADR-042) is the double-entry bookkeeping every posting source reaches through one door, `LedgerService::post()` — it knows no module. Built in three parts: **part 1** the chart of accounts and the fiscal years with their periods; **part 2** the journal (`JournalEntry` / `JournalLine`), `LedgerService` (`post()`, `reverse()`), manual entries with their change log (`EntryChange`, `ManualEntryService`) and the journal screens; **part 3** the reports — trial balance, balance sheet, income statement, account statement, journal — as SQL aggregates (`LedgerReports`, `JournalLineRepository`) with one backend page each; **P5 part 1 (2026-09-30)** closing and reopening a whole fiscal year (below); **the year opening (2026-10-22)** — the closing balances of a year carried into the next as its opening entries (one per account against 9100), its own button, repeatable while the year is open (below). The VAT return (P5 part 2) is being built in stages: the pure core, the read-only data layer (stage S1a) and the read-only screens with the PDF (stage S1b, below) exist — the return can be READ and printed; the posting, the lock and the correction path do not. All entities are Doctrine (`#[Entity('doctrine')]`, announced in `financialConfig.inc.php` → `doctrineEntities`); the package depends on kernel, `persistence-doctrine`, `module-vat` (tax codes are validated against it and the manual form resolves rates through `VatRates`) and — since owner decision E2, 2026-09-23 — `module-mandator` (the VAT accounts live on the mandator record, [`mandator.md`](mandator.md)) and requires PHP 8.4.

### Part 1 — chart of accounts, fiscal years

- **`Account`** (table `account`: `number` unique, `name`, `type`, `parent_id` FK to `account`, `postable`, `active`, `selectable_on_documents`, `module_posting_only`). The number is digits only, at most 10, stored as a string — string order is the chart's order (`1` < `10` < `100` < `1000` < `1020` < `106` < … < `11`), which `AccountRepository::allInOrder()` uses and the list indents by. Grouping is a plain parent reference, no nested set. A **group** (KMU class `1`, main group `10`, group `100`) is an account with `postable = false`; only postable AND active accounts are accepted on a journal line (`PostingRules`).
- **Five types** (`AccountType`: `asset`, `liability`, `equity`, `expense`, `revenue` — owner decision 2026-09-22): equity is its own type so the balance sheet splits equity from debt by type, without a number rule. German labels live in the UI (`ACCOUNT_TYPE_LABELS` in the trait: Aktiven, Fremdkapital, Eigenkapital, Aufwand, Ertrag). A group carries a type as well; for a group mixing types (KMU classes 7 and 8, group 69 with `6950 Finanzertrag`) it is informational.
- **Validation** (`AccountValidator`): number required, digits, unique; name required; type one of the five; the parent must be a GROUP, never the account itself or one of its descendants (the validator walks the chain upwards, with a visited set against a cycle already in the data); a group WITH children cannot become postable; the journal locks on `type` and `postable` (below, FIN-TYPE-001). Deliberately no rule tying the number to the parent's number or the type to the parent's type — the KMU chart mixes types inside a class, and its groups are number RANGES, not prefixes (`1020` sits in group `100`, `1850` in `180`).
- **Write side = `AccountService`**: `save($new)`, `update($account, $values)` (the parent travels as the entity under the key `parent`), `setActive()`, `adoptKmuChart()`. `update()` validates a detached `clone` first and applies the values to the managed entity only when it passed (ADR-039 decision 9, the `ContactService` model); a refused change never reaches the next flush. The **number is immutable** (`AccountNumberChangedException`): settings and other modules' configuration name accounts by number (plan §5.1, §5.4), and so does every `PostingLine`. No delete anywhere — an account is deactivated; journal lines reference it by FK. A unique-number race in `save()` becomes the validator's field error (`uniq_account_number`).
- **Journal locks on `type` and `postable`** (owner decision 2026-09-22, FIN-TYPE-001). Why: the reports read the account TYPE at runtime (`LedgerReports::section()`), so a type change moves every past posting of the account between balance sheet and income statement — closed years included; after the close nothing changes. Hence: (1) `type` may change as long as NO journal line of the account lies in a `closed` period — «closed year» = periods in state `closed` (the P5 year-end closes the periods; there is no year state); `vat-settled` does not lock. Afterwards refused, and the German message names the correction: a new account with the wanted type plus a manual transfer entry (Umbuchung). (2) `postable` true → false (the account becomes a group) is refused as soon as ANY journal line references it, in any period state — a group never carries lines. (3) `name` and `active` stay free; the number was immutable already. The rules live in `AccountValidator` (`validateType()` / `validatePostable()`, fed by the service with the STORED type and postable and `JournalLineRepository`; messages `AccountValidator::TYPE_LOCKED` / `POSTABLE_LOCKED`). The queries (Doctrine-only SQL): `accountHasLines()` — one probe of the FK index on `account_id`, `LIMIT 1`; `accountHasLinesInClosedPeriod()` — first the closed periods (a few dozen rows), merged into one date range per run of adjacent closed periods of a year (none closed → no journal query at all), then per range the account-statement shape (`account_id`, `fiscal_year_id`, `entry_date BETWEEN`) with `LIMIT 1`. The ranges are probed NEWEST first — the latest closed year is where an account in use has lines, so the common case stops at the first range. Measured: ≈ 1 ms in the harness (section P, 20'000 lines: hit; miss; an account with 3'333 lines none of which lies in the — small — closed year) and ad hoc at 200'000 lines (the harness is not parametrised). The review measured the expensive case: a busy account against a closed 100'000-entry year that holds none of its lines costs ≈ 0.5 s per such year (the optimizer walks the entry side), linear in the number of closed years it has to pass — with oldest-first probing every closed year before the one with a hit. Newest-first makes the common case one range; a MISS (a type change on an account with lines only in open periods, many closed years) still pays every closed year. A single join over all closed periods at once was worse (it walked every line of a busy account, 0.7 s at 200'000 ad hoc). No composite index; the structural fix is the `type_locked` marker of P5 (pending).
- **How `AccountService::update()` checks them — validate before mutate, twice.** A change of `type` or `postable` true → false is validated first LOCK-FREE on the detached draft against the managed entity's state — the common refusal, nothing touched, the managed entity unmodified and no later flush writes it. When that passes, the change runs in a unit of work of its own (`getTransaction(Account::class)->run()`): FIRST statement `AccountRepository::lockForUpdate()` (`SELECT type, postable … FOR UPDATE`), then the validator AGAIN against that row, then the managed entity is mutated and the commit flushes it. The guarded path refuses to run inside an open unit of work (`LogicException`) — its re-check must read after the lock, not from a caller's older snapshot (InnoDB's REPEATABLE READ snapshot starts at the first plain read). Name, active and group take the plain flush path as before. A refusal UNDER the lock (only in a race) rolls the unit of work back, which replaces the EntityManager (DOCTRINE-TX-004): the account handed in is detached and serves the form only — the screen re-reads by id.
- **The race with a posting, and the lock order.** The FK insert of `journal_line` share-locks the account only at the caller's FLUSH, after `post()` validated the account on a plain read — an account turned into a group in between would get the line. So `post()` re-checks its accounts on a LOCKING read right AFTER drawing the number (`PostingRules::lockAccounts()` → `AccountRepository::lockForPosting()`, `SELECT … LOCK IN SHARE MODE`, the latest committed postable / active, held until commit); the manual edit does the same after `resolveAccounts()` (it draws no number). Lock order: `NumberRange` → accounts (shared) in a posting, the account (exclusive) in `update()` — which since P5 part 1 takes only the fiscal-year and period rows SHARED after it (the closed-period probe), in the same accounts → years → periods order every posting follows; no cycle (ADR-039 decision 10 unchanged: `NumberRange` first; the full order in «P5 part 1» below). Two outcomes, both proven by forced two-process probes in the harness (T14, T16), each failing without the shared lock: a posting in flight holds the row shared → `update()`'s lock waits for its commit and the re-check refuses on its line; `update()` holds the row → the posting (lock-free check passed, number drawn) waits, reads the account as a group and is refused with `account-not-postable` — its rollback gives the number back. The type rule had no such race before P5 (no period transition existed); since the year close (P5 part 1) the guarded type change reads the closed periods SHARE-LOCKED inside its unit of work (`accountHasLinesInClosedPeriod()` adds `LOCK IN SHARE MODE` when a transaction is active — `state` has no index, so every period row it scans is locked), and a close takes the periods EXCLUSIVELY: the two serialise, a close cannot slip in between the type check and its commit. The `type_locked` marker (pending) stays the performance fix, no longer the race fix.
- **Side effect, accepted (review 2026-09-22):** a posting holds its accounts' rows SHARED until its commit, so ANY change of such an account — name, active, parent included, whose flush updates the row — waits behind an in-flight posting on the same account. Normally milliseconds; a long unit of work (an import posting thousands of entries in one `run()`) can delay a rename up to `innodb_lock_wait_timeout` (50 s by default), after which the rename fails with the driver's exception.

- **The code** names the year and its number range `journal-entry.{code}` (`FiscalYear::journalEntryRange()`, the one place it is composed): lower-case kebab (`2026`, `2026-27`), at most 16 characters, unique, proposed from the dates (`FiscalYearService::proposeCode()`: `2026` inside one calendar year, `2026-27` across). A code is needed rather than the start year because two years can start in the same calendar year (short year 1.1.–30.6.2026, then 1.7.2026–30.6.2027) — orchestrator's follow-on decision to the owner's free dates. Immutable: `FiscalYear` has no public setter (code and dates come with the constructor), and there is no edit of a year — a wrongly opened one is deleted while still empty (below) and opened anew. An empty code is reported only when both dates are valid — otherwise the code would have been proposed from them, and the date errors say what to fix.
- **Opening a year** (`FiscalYearService::open()`): validate (`FiscalYearValidator`), derive the monthly periods, then ONE unit of work through `UnifiedEntityManager::getTransaction(FiscalYear::class)->run()` — first `getRepository(NumberRange::class)->create('journal-entry.{code}')` (lock order: `NumberRange` first), then `persist()` of the year with its periods (cascade). The range is created at 0 and committed with the year, so the first draw under contention never takes the new-row path (DOCTRINE-NR-003); an exception anywhere rolls back year, periods and range together. The range must be NEW: `create()` answers `false` for a row that already exists (a leftover of a removed year, an import), and continuing it would start the year's entries at its old number + 1 unnoticed — refused as a `code` field error, rolled back (review M1). `open()` OWNS its unit of work and refuses to run inside an open one (`LogicException`): nested, the flush would happen at the caller's commit, where the race mapping can no longer turn a unique-index violation into a field error (review L1) — the production caller is the backend controller. After the range, `open()` locks every fiscal-year row (`FiscalYearRepository::lockAll()`, `SELECT … FOR UPDATE`, a handful of rows) and runs the validator AGAIN under that lock — `delete()` takes the same lock, so a predecessor deleted between the first validation and the commit is seen and the opening is refused on `start_date` instead of leaving a gap (FIN-FY-002). Two openings of the same next year on a NON-empty table are serialised by that lock: the second one ALWAYS fails the re-validation and gets a `start_date` field error (a row written past the validator that shares the start date still collides on `uniq_fiscal_year_start`, the same field error — D28). On an EMPTY table the two openings of the first year deadlock instead (FIN-FY-003); the screen answers the loser with a sentence.
- **Deleting a wrongly opened year** (owner decision 2026-09-22, FIN-FY-002 — `FiscalYearService::delete(int $yearId)`): allowed only for the **latest** or the **earliest** year (a middle one would break contiguity; the earliest since the prior years, owner 2026-09-29) and only while **nothing was ever posted** in it — no `journal_entry` references it, no `journal_entry_change` row of it exists (a deleted manual entry leaves one AND a consumed number; its gap history must not be orphaned), and its range `journal-entry.{code}` still stands at `last_number = 0`. Removes the year, its periods and the range in ONE unit of work through `getTransaction()->run()`, and refuses to run inside an open one (`LogicException`, the `open()` model). The existence of a change row is asked with `findOneBy()` (one row, no hydration of the whole log). Everything is decided INSIDE the unit of work, under locks, so a posting cannot slip in between: first the range row — `NumberRangeRepository::dropUnused()` locks it (`FOR UPDATE`) and deletes it only at 0 (lock order: `NumberRange` FIRST, DOCTRINE-NR-002; a poster of the year either committed before, and the range is no longer at 0, or waits; after the delete's commit its `next()` re-creates the range at 0 and draws 1, its `journal_entry` insert then fails on the foreign key to the deleted year, and its rollback removes the re-created range row again — nothing is written. The journal's «Buchung erfassen» answers that failure with «Das Geschäftsjahr wurde inzwischen gelöscht» — recognised by the key's name `JournalEntry::FK_FISCAL_YEAR` down the exception chain (`Ui/RaceFailure`), no other foreign-key violation (Y18–Y20)); then every fiscal-year row (`lockAll()`, against an opening of the next year racing the delete); then the checks on the fresh state. A refusal (`FiscalYearNotDeletableException`, reasons `not-found`, `not-latest`, `has-entries`, `had-entries`, `range-used`) or any failure rolls back the whole unit of work — the range row is back as it was. The code is free again afterwards: the year re-opens with the same code and a NEW range at 0. `deletionRefusal($year)` is the lock-free read the screen asks (it does not read the range — through the ledger a committed number always leaves an entry or a change row; `delete()` checks the range anyway). The screen: «Löschen …» in the year's ⋮ menu (`actions?id=`, owner 2026-10-10 — was a button on the section header) of the latest or the earliest year, offered only while `deletionRefusal()` is null; `confirm-delete?id=` (modal, `data-fetch-get`, says why when refused) and `delete` (`#[Fetch, HttpMethod('POST')]`, entity token `fiscalYear`, success redirects to the list). Verified: Y1–Y16 (latest empty year deleted and re-opened with the same code, not-latest, an entry, a created and deleted manual entry, a drawn number, a rollback at the flush, nested).
- **Period state** (`PeriodState`: `open`, `closed` — ADR-042 decision 10 as amended by the addendum 2026-11-24, point 2): every period is created `open`. Whole YEARS move between `open` and `closed` (`FiscalYearCloseService`, below — the only caller of `Period::transitionTo()`). The ledger refuses a `closed` period (part 2, below). **«VAT-settled» is NOT a period state** — the case `vat-settled` was removed with stage S2 slice 2 (nothing ever wrote it; the column is a plain `VARCHAR(12)`, no data migration). A date is settled while a live ordinary VAT return covers it, read from the returns (`VatSettlement`, «the freeze» below) — one source, and reopening a year cannot lose it.

### P5 part 1 — closing a fiscal year (owner decisions 2026-09-30)

- **Only the whole YEAR is closed.** There is no month-by-month close in the UI and no year-state column: a year is closed when EVERY one of its periods is `closed` (`FiscalYear::isClosed()`). Closing sets all periods `closed`; reopening sets them `open` again. The periods keep carrying the state because the ledger asks the period of a date. A VAT period is not a fiscal period (a quarter, a year, a short first period) and its «settled» lives on the returns, not here.
- **In order.** A year closes only when the year before it (the one ending the day before it starts — years are contiguous) is closed, or it is the earliest year. Reopening goes in reverse: only a closed year whose successor is NOT closed. The screen asks `closeRefusal()` / `reopenRefusal()` (lock-free); the service decides again under lock. A PRIOR year opened in front of a closed earliest year (owner 2026-09-29) is open while its successor is closed — it is closable (no predecessor) and the order rule holds from there; nothing else produces a closed year after an open one.
- **The close check** (plan §5.3, ADR-042 decision 11) is the open-work registry of persistence-doctrine (`OpenWorkChecks`, [`persistence-doctrine.md`](persistence-doctrine.md)) — financial knows none of the checks. Scope **`period-close`** (`FiscalYearCloseService::SCOPE`), parameters **`fiscalYear`** (the code), **`from`** and **`to`** (`DateTimeImmutable`, the year's first and last day). Each finding is BLOCKING (the close is refused, `blocked`) or a WARNING (the close needs the explicit confirmation, else `warnings-unconfirmed`). Financial adds one warning of its own: the year has not ended yet («endet erst am …»). Registered today: debtor's `InvoicingInProgressCheck` — a document dated in the year that is not posted yet (a draft in `invoicing`, or issued and waiting in the Faktura-Journal, ADR-054 decision 17) blocks — and `UnbookedTransactionsCheck` (CAMT transactions not yet booked, P4) ([`debtor.md`](debtor.md)); and since 2026-10-13 financial's OWN `SubledgerReconciliationCheck` (below), declared in `financialConfig` → `openWorkChecks`; module-order's `InvoiceableOrdersCheck` (an order of the year not yet invoiced — a WARNING, [`order.md`](order.md)) and module-receipt's `UnpostedReceiptsCheck` (a receipt of the year still in the Belegjournal BLOCKS, [`receipt.md`](receipt.md)). Decision (orchestrator, owner to confirm): the plan's «`PeriodCloseCheck` interface in financial» IS this registry — plan §2 moved the open-work check into persistence-doctrine exactly for this, a second interface would duplicate it (Rule 8).
- **The subledger reconciliation** (owner decision 2026-10-13, review 2026-10-13 §2: «collective account 1100 ≠ open items, nothing prevents or reports it»): `Close/SubledgerReconciliationCheck` compares, at the close, every collective account with the subledger its module reports. Financial still names no module: a module implements the PORT `Close/SubledgerReconciliationInterface` — `balances(string $fiscalYear, DateTimeImmutable $from, DateTimeImmutable $to): iterable<SubledgerBalance>`, one `SubledgerBalance(account number, label for the sentence, Money balance = debit − credit the ledger should show at the END of $to)` per collective account it keeps, nothing when it books elsewhere — and declares the class under its config key **`subledgerReconciliations`** (a list; or an extension file `App/Config/subledgerReconciliationsConfig.inc.php`), collected by `Close/SubledgerReconciliations::fromModules()` (the `OpenWorkChecks` pattern: a bad entry fails at registration, naming its origin; instantiated without arguments). The check computes the account's balance in the journal (the year's lines up to `to`, `JournalLineRepository::accountTotals()`) and reports, each as a **WARNING** (decision 2026-10-13, to confirm by the owner — the closer confirms it explicitly and the protocol keeps it in `confirmed_warnings`; not blocking, because a later year's journal carries the receivables only through its opening entry — before the year opening (2026-10-22) not at all, and a year opened provisionally or from an imported history inherits whatever difference its predecessor had at its end; the hard guard is the flag above. A year opened with «Eröffnung erstellen» agrees as far as its predecessor agreed: the module's figure is cumulative, the journal's is the year's lines INCLUDING the opening line of the collective account): a difference — both balances, the difference, and the MANUAL entries on the account by number with their net (`JournalLineRepository::manualLinesOnAccount()`, the first 12 numbers, then «…»); the account missing from the chart or a group; the account not flagged «nur durch Module bebuchbar». Registered today: debtor's `Close/ReceivablesReconciliation` (2026-10-13, [`debtor.md`](debtor.md) «The year-close check»: booked invoices and fees − credit notes − booked allocations up to `to`, on the mandator's receivable account). How the dev data of z77.ch is reported (verified 2026-10-13 with debtor's real reconciliation through the registry and `FiscalYearCloseService::closeCheck()`, read-only, the year not closed): «Sammelkonto «1100 Forderungen aus Lieferungen und Leistungen (Debitoren)» stimmt nicht mit den offenen Posten Debitoren überein: Saldo im Journal per 31.12.2026 19'758.05, laut Modul 19'866.15, Differenz −108.10. Manuelle Buchungen auf dem Konto: Nr. 4, 6, 7, 9, 10, 11, 12 (zusammen −108.10).» A module that registers nothing makes the check compare nothing and say nothing.
- **The bank check at the close** (ADR-061 decisions 25, 26, stage C4, 2026-11-17): financial's SECOND own check, `Close/BankReconciliationCheck`, registered under `period-close` AND `vat-return` — for every bank-driven bank account it BLOCKS on a statement not read to the end of the range, movements «zu prüfen», a check that does not agree and a transfer clearing account that is not at zero, and WARNS at the VAT return with «n Buchungen mit Vorsteuer ohne Beleg · CHF x Vorsteuer» (at the year close with an unconfirmed anchor). - **`FiscalYearCloseService`**: `close(int $yearId, ?string $confirmedWarnings = null)`, `reopen(int $yearId, string $reason)`, plus the lock-free `closeRefusal()`, `reopenRefusal()` and `closeCheck()` the screen asks, and `warningsFingerprint(OpenWork)`. Each write OWNS its unit of work and refuses to run inside an open one (`LogicException`, the `FiscalYearService` model). Inside: every fiscal-year row locked (`lockAll()` — against an opening, a delete, a second close/reopen; it answers the locked rows, so the neighbours come from a LOCKING read), then the periods of the year and its neighbour re-read under an exclusive lock and REFRESHED in the identity map (`FiscalYearRepository::lockPeriodsOf()`, DQL `PESSIMISTIC_WRITE` + `HINT_REFRESH`), and only THEN the first plain read — so the REPEATABLE READ snapshot the close check reads in starts after every lock is held (review 2026-09-30: before, a plain read ahead of the locks fixed an older snapshot, and a document finalised meanwhile could show up as a false blocking finding); then every rule again — order, close check — and only then `Period::transitionTo()` and the protocol row. **Warnings are confirmed by fingerprint** (review 2026-09-30): the modal carries `warningsFingerprint()` of the warnings it SHOWED; the POST passes it only with the checkbox ticked; under the lock a different set of warnings is refused (`warnings-changed`, «Die Hinweise haben sich geändert — bitte erneut prüfen»). The actor is the session identity (`Actor::current()`) or named explicitly (CLI, harness).
- **The ledger stays the last line of defence, now also under a race.** The lock-free period check of a posting reads the state before any lock; a close committing in between would let the posting land in a closed year. So every write into the journal re-reads its period's state SHARE-LOCKED (`PostingRules::lockedPeriodState()`, held until commit) — and FIRST share-locks the period's FISCAL-YEAR row, then the period (`SELECT id FROM fiscal_year WHERE id = ? LOCK IN SHARE MODE`, then `SELECT state FROM fiscal_period … LOCK IN SHARE MODE`): `post()` / `reverse()` after the number and the account locks — a refusal there rolls back and gives the number back —, a manual edit after the entry and the account locks, a delete after the entry lock (old AND new period). **Why the year first** (review 2026-09-30, a real deadlock in the first build): the `journal_entry` insert share-locks its fiscal-year row at the flush anyway (foreign key `fiscal_year_id`). With only the period locked, a posting held the period (S) and wanted the year (S) at its flush, while a close held the year (X, `lockAll()`) and wanted the period (X) — a cycle, InnoDB 1213, a 500. Year before period on both sides removes it: whoever comes second waits at the year. **Lock order** — posting: `NumberRange` (X) → accounts (S) → year (S) → period (S); manual edit: entry (X) → accounts (S) → year (S) → period (S) (the accounts BEFORE the period since the review — the other order could deadlock with a type change); manual delete: entry (X) → year (S) → period (S); type change: account (X) → all years (S) → periods (S) (`accountHasLinesInClosedPeriod()` inside a unit of work); close / reopen: all years (X) → periods (X), no account, no range; opening / deleting a year: `NumberRange` (X) → all years (X). Every path takes years before periods and accounts before years, the close takes neither ranges nor accounts. Proven by two forced two-process races against the real service (YC42: a posting in flight, the close waits and closes after it; YC43: a close in flight, the posting waits and is refused `period-closed`, the number back — both FAIL with the 1213 deadlock / without the wait when the year lock is removed, probed 2026-09-30) and single-process with a stale identity map (YC14/YC15).
- **Reopen = ADMIN, with a reason** (owner): `reopen` / `confirm-reopen` are PINNED to ADMIN in `backendConfig` (`FiscalYearController` → `actions`, owner 2026-09-30) although that equals the backend's `moduleRole` today — a deliberate exception to AUTH-B003: a project that lowers the finance controllers for a bookkeeper must not hand out «Wieder öffnen» with them. Closing follows the controller role (ADMIN today, like every finance screen). The button is shown only when `fiscalYearCanReach('reopen')` says so (`AuthService::canReach()` with the mount's segments, backend.md). Reopen restores `open` — P5 part 2 introduces `vat-settled` and MUST decide what a reopen restores then (a period whose VAT return was filed).
- **The protocol** (`FiscalYearCloseLog`, table `fiscal_year_close_log`, migration `Version20260930120000`): one row per close and per reopen — year id AND code as plain columns (no foreign key, the `journal_entry_change` model: a reopened, still empty year may be deleted and its protocol stays), action `close` | `reopen`, actor, `acted_at`, `reason` (mandatory on a reopen, none on a close, at most 500 characters — kept WHOLE: the service refuses a longer one with `reason-too-long`, the entity throws, nothing is cut), `confirmed_warnings` (the warnings a close confirmed, one per line). ### P5 — the year opening (owner decisions 2026-10-22)

- **What it writes** (`Services/YearOpeningService`, plan §5.7, ADR-042 decision 12 and its addenda 2026-10-22): generated journal entries in the TARGET year, dated its first day — **ONE TWO-LINE ENTRY PER ACCOUNT against the contra account** (owner 2026-10-22, second round: the first build wrote ONE compound entry, and the statement of 9100 showed «div.» on both of its lines; now like wdv's «EB:» entries — the 9100 statement names every account, FIN-REPORT-006). Every balance-sheet account (asset, liability, equity) with a non-zero closing balance of the PREDECESSOR gets its entry: the account with that balance on its side, the mandator's **`opening-balance`** account (KMU 9100) with the same amount on the other (owner: «9100 Eröffnungsbilanz»); posted in chart order (the number as a string), so the numbers follow the chart; zero balances omitted. The predecessor's RESULT (Σ debit − credit of its expense and revenue accounts) is ADDED to the mandator's **`annual-result`** account (KMU 2979) — to that account's own carried balance, so 2979 gets ONE entry with the sum (owner: Swiss KMU; the appropriation to 2970 / reserves is booked by hand afterwards). Each entry: text «Eröffnungsbilanz {code}» (the account stands in the statement's counter column, no need to repeat it in the text), origin `opening` / the target code (`YearOpeningService::SOURCE_TYPE`), key `opening:{code}:{account}` (`idempotencyKey($year, $account)`). 9100 nets to zero; it carries a balance only when it had one at the predecessor's end (an incomplete imported opening) — shown, not hidden. Base currency only (ADR-042 decision 4): a foreign-currency account carries its CHF balance; a revaluation is an ordinary entry in the predecessor first.
- **The predecessor's closing balance** is ITS OWN entries — its opening included, imported (`EB:YYYY` of wdv) or generated — read with the reports' aggregate `JournalLineRepository::balancesByAccount()` over its days; never earlier years added up (FIN-REPORT-001, resolved by this).
- **Its own measure, not part of the close** (owner: «Sperren und neu eröffnen sind 2 unterschiedliche Massnahmen»): «Eröffnung erstellen …» on the TARGET year. **Repeatable while the target year is open** («… muss das alte Jahr geändert werden und die Eröffnungsbilanz neu erstellt werden»): a re-run REPLACES the whole SET in one unit of work, entry by entry (`YearOpeningPlan`: `toPost` / `toAmend` / `toRetract`, the rest unchanged): an account whose balance changed is amended in place through `LedgerService::amend()` — the source correcting its own generated entry (ADR-042 addendum 2026-10-06): the SAME number, one `EntryChange` update row (before / after, the change log shows it); an account that no longer carries a balance is retracted (`retract()`, a documented gap, a delete row); a new account is posted (the next number). Unchanged entries are not touched; an unchanged set writes nothing (`YearOpeningResult::UNCHANGED`); a predecessor without any balance removes every entry (`REMOVED`). The set is found by its ORIGIN (`opening` / the code, `JournalEntryRepository::generatedFrom()`), so the ONE compound entry of the first build (key `opening:{code}`) is part of it and a re-run retracts it. Never a storno pair, never a second entry per account (the key is unique). Refused for a CLOSED target (`target-closed` — the opening is frozen with its year; reopen it to change it). An OPEN predecessor is allowed — the opening is PROVISIONAL, and the dialog, the flash and the year's status line say «Vorjahr {code} noch nicht abgeschlossen — Eröffnung provisorisch, nach Änderungen neu erstellen.» (the agent's reading of the owner's decision — FIN-OPENING-001).
- **Refused as well** (`YearOpeningRefusedException`, reasons; the screen speaks German through `fiscalYearOpeningMessage()`): `no-predecessor` (the earliest year — the ⋮ does not offer it), `account-missing` (a year-opening account empty on the mandator or not a postable active account — the sentence names the field and ends with `LedgerService::MANDATOR_HINT`), `foreign-opening` (the contra account already has entries in the target year of ANOTHER origin than `opening` / the code — `JournalLineRepository::entriesOnAccountNotFrom()`; an imported «EB:», a manual opening: «Eröffnung bereits vorhanden (importiert / von Hand): «9100 Eröffnungsbilanz» hat im Jahr die Buchungen Nr. …»), `account-inactive` (an account with a closing balance is inactive — `post()` needs active accounts; reactivate it or transfer the balance in the predecessor), `nothing-to-carry` (no balance and no opening to remove), `not-found`.
- **Collective accounts**: the opening is a GENERATED posting, so 1100 «nur durch Module bebuchbar» (FIN-MODULE-ONLY-001) is opened like any other account — one entry with its closing balance. The debtor reconciliation (`ReceivablesReconciliation`, cumulative) then agrees in the new year as far as it agreed at the predecessor's end.
- **Where the accounts are configured** (Rule 2, mandator.md's rule for a company account): on the MANDATOR record next to the VAT and debtor accounts — keys `opening-balance` (`account_opening_balance`) and `annual-result` (`account_annual_result`), KMU start values 9100 / 2979, column DEFAULTS of the migration `Version20261022140000` of module-mandator (an existing record gets them at once). Read in this module ONLY through `LedgerService::yearOpeningAccount($key)` (constants `OPENING_BALANCE_ACCOUNT` / `ANNUAL_RESULT_ACCOUNT`), the `vatAccountFor()` model.
- **Unit of work and locks**: `create($yearId)` OWNS its unit of work (refuses a nested call, the `ManualEntryService` model). Inside, plain reads first (the year, the predecessor, the balances — one consistent snapshot), then the retractions, the amendments and the new postings, each through the ledger, which takes its own locks in its own order (`post()`: `NumberRange` → accounts → year → period; `amend()` / `retract()`: entry → accounts → year → period) and re-checks the target period share-locked — a close of the target committed meanwhile refuses (`period-closed`), the rollback undoes the whole set and the numbers go back. No lock is taken on the predecessor: a change there after the snapshot is what «provisional — re-create» covers. Two openings of the same year at once: the second fails on `uniq_journal_entry_idempotency` (a post) or waits on the entry lock (an amend), nothing of it written; the screen says «gleichzeitig erstellt — neu laden».
- **The screen** (Stammdaten › Finanzen › Geschäftsjahre; the action cell stays «+ Geschäftsjahr»): the ⋮ of an open year with a predecessor offers «Eröffnung erstellen …» / «Eröffnung neu erstellen …» (`fiscalYearActions()` → `opening`); the dialog `confirm-opening?id=` (`data-fetch-get`, a confirm without an input field — the actions at the end) shows the lines it would write through `Backend/partials/entrySnapshot` — per entry the account's line with its name, the text column marking «neu» / «geändert» (nothing when unchanged), the entries a re-run removes («wird entfernt»), then the contra account's Haben and Soll over all entries («Gegenbuchung (n)») —, Soll = Haben over all lines, how many entries, whether it brings a standing opening up to date («n geändert (gleiche Nummer), n neu, n entfernt, n unverändert», change log) or changes nothing, and the provisional note; POST `opening` (`#[Fetch, HttpMethod('POST')]`, entity token scoped `fiscalYear.opening` — the close/reopen model, ADR-049's dialog flow) → flash (success, or info when provisional) + close + reload. Under each year's header a status line (`data-fiscal-year-opening`): `none` «Eröffnung {code} nicht erstellt» (badge «fehlt»), `current` «Eröffnung: 45 Buchungen {code}/{first}–{code}/{last}» («Buchung {code}/{n}» for one; `fiscalYearOpeningRefs()`), `provisional` (badge «provisorisch», the owner's note), `outdated` «… nicht aktuell — das Vorjahr … hat sich seither geändert, neu erstellen» (badge «nicht aktuell»), `refused` (the sentence), `frozen` (a closed year with its opening). The status computes the plan (the predecessor's balances, one aggregate) for OPEN years with a predecessor only — one or two in practice.
- **The dashboard** (the setup step `financial.opening` since 2026-11-19, «dashboard» below): «Eröffnung {code} nicht erstellt» (todo) when the year covering today has a CLOSED predecessor and no opening — neither the generated one nor entries on the contra account (`YearOpeningService::isOpened()`, no balances read).
- Verified: `tests/module-financial.php` EB0–EB26 (EB5/EB6 the five per-account entries, EB8b the 9100 statement without «div.», EB10/EB11 a re-run posting one, amending two, retracting one, EB18b the first build's compound entry retracted). **Not verified live** (the test project needs the mandator migration first, FIN-OPENING-001).

### P5 part 2 — the VAT return's read path (stage S1a, 2026-11-24)

Read-only, nothing written (no entity, no posting, no lock, no migration): `VatReturn\VatReturnService` sits between the journal and the pure `VatReturnCalculator` (ADR-041 / ADR-042 addenda 2026-11-24, review sections 4, 6.2, 8). One instance per request; every answer is computed from the journal on the call and cached on the instance, never stored. The screens of S1b consume it without further logic.

- **The gate** — `settingsRefusal(): ?VatReturnRefusal` from `CurrentMandator::vatSettings()` (or a `VatSettings` handed in — the harness): `not-liable` (unless «Abrechnung bis» is set — the screen stays for the last periods, ADR-041 point 3), `method-not-set` / `method-unsupported` (net tax rate, flat tax rate), `consideration-not-set` / `consideration-unsupported` (received), `rhythm-not-set`, `from-not-set`, `mandator-unavailable`. Every reading method refuses through the gate with `VatReturnRefusedException` (the `VatReturnRefusal`: `reason`, German `message`, `fix` = an opaque place — `mandator:vat`, `mandator`, `tax-code:{CODE}`). Per period on top: `no-period` (`periodOn()` of a day outside the liability), `no-form` (no edition of the country pack covers it — before 2024), `reverse-charge` (a reverse-charge line in the period — until stage S6), `unmapped-code` (the pack's `UnmappedTaxCodeException`), `unknown-tax-code` (a journal code module-vat does not know).
- **The periods** — `calendar()` (`VatPeriodCalendar` from the record: ONE rhythm from «Abrechnung ab», cut at «bis» — the record keeps no rhythm history, MANDATOR-VAT-RHYTHM-001), `periodOn($day)`, `periods(FiscalYear, ?today)` → `VatReturnPeriodSummary` per period that ENDS in the year (screen decision 3): state `open` / «offen», the method label («Effektive Methode · Vereinbartes Entgelt», from `MandatorLayout`), `elapsed`, `payable` (one aggregate query per period, cached) or the period's `refusal` — a refused period stays a row. `nextReturn(?today)` = the first ELAPSED period not settled; `isSettled(VatPeriod)` asks `VatSettlement` since stage S2 slice 1 (below, «the posted return»).
- **The aggregate** — `JournalLineRepository::vatReturnAggregate(yearIds, from, to)`: ONE query, the coded lines (`tax_code IS NOT NULL`) of the period grouped by code, rate, source type, account and a REVERSAL flag, Σ `tax_base`, Σ `tax_amount`, count; the years the period touches (`fiscal_year_id IN (…)`) keep `idx_journal_entry_date` usable per year — a period may span two fiscal years. The flag is SQL (`reversal_of_id IS NOT NULL` or a reversal of the entry dated on or before the period's end — one probe of `uniq_journal_entry_reversal_of`); the CLASSIFICATION is PHP, in one place. No new index: measured ad hoc on the harness data blown up to 120 832 lines in the year (34 816 coded lines in the quarter — the synthetic year sits almost wholly in that quarter, so MariaDB 11.4 scanned `journal_line` rather than the date index): aggregate 0.10 s, movements 0.15 s.
- **The origin** — `VatReturn\VatReturnSources::rowOrigin(sourceType, reversalPair)` turns the opaque origin into the calculator's `RowOrigin`: a reversal pair → `reversal` (netted into 200; the original only when its reversal is dated within the period's end, so an earlier period stays as computed); correction → not built (S3; the marker goes into that method); a source type DECLARED `reduction` → `reduction` (field 235); everything else, manual entries included → `ordinary`. Financial names no module: each posting module declares its source types under the config key **`vatReturnSources`** (`'credit-note' => ['label' => 'Gutschriften', 'origin' => 'reduction']`; or an extension file `App/Config/vatReturnSourcesConfig.inc.php`) — debtor: `invoice` «Rechnungen», `fee` «Mahngebühren», `credit-note` «Gutschriften» (reduction), `payment` «Skonto und Verluste» (reduction — of debtor's allocations only «Skonto» and «Verlust» carry tax data; a payment and «Gebühren» post no code); receipt `receipt` «Belege»; creditor `creditor` «Kreditoren»; financial `bank` «Bank», `opening` «Eröffnung»; a manual entry is the key `manual` «Manuelle Buchungen» (shown last); an undeclared source type is ordinary and labelled by itself. The same declarations give the display origin of «Herkunft».
- **One period** — `preview(VatPeriod)` → `VatReturnPreview`: the form (`VatReturnForm`, the calculator's answer — never re-rounded), `fields` (`VatReturnField` for EVERY field of the edition: label from the rule file — `FormEdition::label()` —, exact value, `rounded` to the Rappen, base, line count, `shown`: a field with an amount, the totals 289 / 299 / 399 / 479 always, 500 or 510 by the sign of the payable amount), `breakdown` (`VatReturnBreakdown` nodes field › origin › account; `amount` is the node's share of the field's figure — the base for 200 / deduction / rate fields, the negated base for 235, the posted tax for the input fields — so every level adds up to the form), `groups` / `rows`, `DECLARATION_NOTE` «Deklaration netto (ohne MWST)» (review T2), state «offen».
- **The entries of a node** — `lineSearch(period, field, ?origin, ?accountId)` → `Repositories\VatReturnLineSearch` built from the very groups the form was computed from (selectors code + rate + source type + reversal flags), so the list's total equals the node; `narrowed(dayFrom, dayTo, number, text, sort, descending)` for the list's own magnifiers and sort (`SORTS`: date, number, account, text, base, tax — a fixed ORDER BY map); `lines(search, offset, limit)` → `VatReturnLine` (entry «2026/17», date, texts, account, code, rate, base, tax, origin, and `documentQuery()` — the `{id, sourceType, sourceRef}` that `Ledger\EntryDocuments::documentsFor()` takes for the document link); `countLines()` for the pager, `lineTotals()` for the total line. The `{X}Listing` definition is the screen's (S1b).
- **The reconciliation** — `reconciliation(VatPeriod)` → `VatReturnReconciliation` from ONE movement query (`vatReturnMovements()`: per account and code, without the source types `opening` and `vat-return` — `VatReturnService::SOURCE_TYPE`, the settlement entries of S2, named once — and without entries on the opening contra account): (a) the revenue accounts' MOVEMENTS (credit − debit) against field 200 − 235, the named differences (`ReconciliationLine`: `uncoded` per revenue account, `coded-other-type` = output-coded lines on another account type, negated; `correction` none before S3) and the `remainder()`; (b)+(c) `VatAccountReconciliation` per VAT account the mandator names (`vatAccountFor()`; VAT owed first): its movement against Σ posted tax of the coded lines of its categories, `difference()`.
- **The findings** — `findings(VatPeriod)` → `VatReturnFinding` (blocking first): the open-work registry for scope `vat-return` (`from`, `to`; message and reference passed through, code `open-work`) plus the return's own: `check-failed` (an eCH check of the form — BLOCKING, a defect), `vat-account-missing` / `vat-account-remainder` (BLOCKING), `vat-account-shared` (BLOCKING, since 2026-11-25 — one account named for owed VAT and input tax, replaces that account's remainder; FIN-VAT-ACCOUNTS-001), and as warnings `turnover-remainder` (screen decision 6), `uncoded-revenue` per revenue account (not the mandator's invoice-rounding account, `LedgerService::invoiceRoundingAccount()`), `uncoded-asset-credit` (credit lines without a code on an account under the chart group `14` «Anlagevermögen» — `VatReturnService::FIXED_ASSET_GROUP`, the chart has no fixed-asset type; since S1b NOT on a value-adjustment account: number ending in `9` AND name starting «Wertberichtigung» — `VALUE_ADJUSTMENT_PREFIX`, both, so the yearly depreciation no longer warns and a renamed account warns as before), `negative-field`, `exempt-without-correction` (naming the interest exception up to CHF 250 000), `rounding-difference` (above half a Rappen per coded document, ADR-041 point 13). References: `account:{number}`, `field:{field}`, `reconciliation`, `mandator:accounts`, or the check's own.
- Verified: `tests/financial-vat-return-ledger.php` (O offline; M–F against MariaDB, checkpoints C / D / E / F — F is the screens, below) — a Q3 posted through the ledger (debtor's document and allocation shapes, `GrossEntryBuilder` for receipt / creditor / bank, `ManualEntryService`, `LedgerService::reverse()`), the rows by origin, the form = the calculator = the hand-computed figures, the tree = the form, the lists = their nodes, the reconciliation to 0.00 and its defects, two fiscal years, the periods per rhythm, every refusal. **Not verified:** `mandator-unavailable` live (the record is read through the harness's own registered module); the debtor shapes are the builders' shapes posted by hand, not `PostingBuilder` / `PaymentPostingBuilder` themselves.

### P5 part 2 — the freeze: a settled VAT period refuses tax lines (stage S2 slice 2, 2026-11-24)

The ledger's write path reads «settled» from the returns — still no writer: no production code creates a return, so nothing is settled in an installation and the product behaves as before; the settled path is live and tested with rows the harness inserts (plan `docs/temp/vat-return-s2-plan.md` §2.1 posting side, §3.6–§3.8; ADR-042 addendum 2026-11-24, points 2 and 3).

- **The rule.** A posting, an amendment, a retraction, a manual edit, a manual delete or a reversal is refused when the old OR the new version of the entry carries a TAX line and the old OR the new date lies in a settled VAT period — reason `vat-period-settled` (`PostingRefusedException::VAT_PERIOD_SETTLED` for a new entry, `EntryNotEditableException::VAT_PERIOD_SETTLED` for a change; both carry the period as `$vatPeriod`). An entry without a tax line stays possible in a settled period while its fiscal period is open. A reversal follows from its DATE: dated into the settled period it is refused, dated in the running period it passes — that is «a later event belongs to the running period». The old reason key `period-vat-settled` is gone (the message names the VAT period, not the month).
- **Where it is decided — `PostingRules`.** `assertPeriodAccepts()` / `assertPeriodAllowsChange()` judge `closed` only (the `$withTaxLine` parameter went). `assertVatAccepts(PostingRequest, bool $locked)` and `assertVatAllowsChange(JournalEntry, ?PostingRequest $new, bool $locked)` ask `VatSettlement`; WHAT is frozen is said in ONE private place, `vatFrozenDates(?JournalEntry $stored, ?PostingRequest $request)` — no date when neither version has a tax line, else the stored date and the new date. An exemption belongs there and nowhere else (S3: a correction entry, marked by its own columns, contributes no date). `settledVatPeriod(date)` is the lock-free answer for `periodRefusal()`. Nothing about «settled» is cached in `PostingRules` or `LedgerService` — every question builds a fresh `VatSettlement`.
- **Two checks per write, and the second one decides.** Lock-free first (`locked: false`, before any lock — the common refusal costs no number). Then, after the period's share lock, `locked: true` → `VatSettlement::lockedPeriodCovering()` (`LOCK IN SHARE MODE` on `vat_return`). Why a locking read: the isolation is REPEATABLE READ and the unit of work's first plain read (the idempotency lookup) fixes its snapshot — a plain read would answer from before a return that committed meanwhile (VR-R9).
- **Lock order as built.** A posting (`post()`, `reverse()`): number range (X) → accounts (S) → fiscal year (S) → period (S) → **`vat_return` (S) — only with a tax line**. `amend()` / manual edit: entry (X) → accounts (S) → year (S) → old period, new period (S) → `vat_return` (S, old date then new date). `retract()` / manual delete: entry (X) → year (S) → period (S) → `vat_return` (S). An entry without a tax line takes no new lock and makes no new read. The return side (slice 5) takes range (X) → VAT accounts (S) → every year (S) → the periods of the touched years (X) → `vat_return` (X): a posting in flight holds the period (S) until its commit, so the return waits and then sees it; a posting that arrives later waits at the range or the period and then meets the committed return on its locking read — refused, the rollback gives the number back. Proven with a stand-in for the return (a second process holding those locks with an uncommitted row): VR-R2s (tax posting), VR-R4s (manual edit, no range — it meets the return at the period row), VR-R3s (no tax line: waits, accepted).
- **`LedgerService::periodRefusal(\DateTimeImmutable $date, bool $withTaxLine): ?string`** — financial's public answer for a module's PREVIEW and for a screen: null, or `no-fiscal-year` (no year or no period covers the date) | `period-closed` | `before-vat-start` (slice 4a, below) | `vat-period-settled` (the last two asked only with a tax line). Lock-free, read fresh; it shows, `post()` decides. **`periodRefusalText(string $reason, \DateTimeImmutable $date, ?VatPeriod $settled = null): string`** — the ONE German sentence per reason, without its final full stop: «Die MWST-Periode 3. Quartal 2026 ist abgerechnet — eine Buchung mit MWST-Code geht dort nicht mehr» (the period handed in — a refusal's `$vatPeriod` — or looked up for the date; named by its LABEL since slice 3, below). Readers: `CreditorJournalPostingService` and `ReceiptJournalPostingService` (preview through `periodRefusal()`, the settled sentence from the text source; their own sentences for «no year» / «closed» unchanged), `Bank\BankPostingService` (the ledger's refusal + the bank's way out), the journal screen (`journalRefusalMessage()`), debtor through its port (`AccountingGateway::periodRefusal()`, `LedgerAccountingGateway`, slice 3). No module reads a period state for this any more.
- **The journal screen.** The list's ROW state `vat-settled` (icon «lock», a UI state — not the enum) is computed from ONE `VatSettlement` per page: a manual entry with a tax line whose date a live return covers. The detail shows «offen · MWST abgerechnet» for such a date. The fiscal-year list has no month badge «MWST abgerechnet» any more — a VAT period is not a month.
- **What `FiscalYearCloseService::reopen()` owes: nothing** — the state it resets never held «settled».
- Verified: `tests/financial-vat-return-posting.php` section F (the matrix post / amend / retract / update / delete / reverse × tax line / none × settled / open, a lifted return and a correction row freeze nothing, `periodRefusal()` + text, VR-R9, VR-R2s – R4s, the source guards VR-R10; checkpoint `--from=F`); `tests/module-financial.php` D18, G25–G28c, I14–I18, T1, S11b, YC16, YC24; `tests/financial-bank.php` C28.

### P5 part 2 — no tax line before «Abrechnung ab» (stage S2 slice 4a, 2026-11-25)

The rule of plan §5.1 (ADR-041 addendum 2026-11-24, point 3: «before «Abrechnung ab» … a posting made in z77 with a tax code is refused»). LIVE as soon as a liable mandator names the day — unlike the freeze it needs no return. Slice 4a builds the rule only; the setup screen, the carry-over and the zero-balance warning (§5.2, §5.3) wait for the owner's board answers.

- **When it applies.** Only while the mandator is LIABLE and «Abrechnung ab» is SET (`PostingRules::vatStart()` → `CurrentMandator::vatSettings()`). Not liable, no day, no record, or a record that cannot be read (`MandatorUnavailableException` — an upgrade half done must not stop every tax posting) → no rule. A liable mandator without the day settles its VAT outside z77 and is never blocked (ADR-042 addendum point 6). Lock-free: a setting, not a race; Doctrine's identity map — one read per request. Asked only for a request WITH a tax line.
- **The rule — `PostingRules::vatStartCrossed()`, the ONE place**, asked first by `assertVatAccepts()` and `assertVatAllowsChange()` (on both passes, before the settled check), reason `before-vat-start` (`PostingRefusedException::BEFORE_VAT_START` for a new entry, `EntryNotEditableException::BEFORE_VAT_START` for a change; no `$vatPeriod`):
  - a NEW entry with a tax line dated before the day — `post()`, a manual entry, `reverse()` dated before the day — is refused; on the day and later it passes;
  - a CHANGE (`amend()`, manual update) is refused when its new version carries a tax line before the day, UNLESS the stored entry already carried a tax line and the date does not move earlier (an old entry may be corrected in text or amount) — **the plan's recommendation for the OPEN board question 9** (`docs/temp/canvas-mwst-s2/questions.md`); the owner's answer changes `vatStartCrossed()` only;
  - a removal (`retract()`, manual delete) and a version without a tax line are never refused for it; existing entries stay untouched (no migration, no backfill).
- **The public answer.** `LedgerService::periodRefusal(date, withTaxLine)` answers `before-vat-start` after `no-fiscal-year` / `period-closed` and BEFORE `vat-period-settled` (a date before the day is that, settled or not). `periodRefusalText('before-vat-start', …)` reads the day from the mandator: «Vor dem 01.12.2026 wird in z77 keine MWST abgerechnet — eine Buchung mit MWST-Code geht dort nicht» (day cleared since the refusal: «Vor «Abrechnung ab» wird …»).
- **Readers and their way out.** The journal screen: the sentence + «; Buchungen ohne MWST-Code sind dort möglich.»; the bank: «… Nichts gebucht / zurückgenommen — vor diesem Tag geht nur eine Buchung ohne MWST-Code.» — the take-back reverses on the entry's own date, so an entry with a tax line dated before the day cannot be taken back (plan: `reverse()` before the day refused like `post()`); creditor: the sentence, no way out (as for the settled period); receipt: «; beim Beleg «ohne MWST» wählen»; debtor — see [`debtor.md`](debtor.md) (`PeriodRefusal::isVat()`, «auf diesen Tag oder später legen»).
- **A future journal importer** needs its own entrance — the rule refuses an import of coded lines before the day as it refuses a posting (plan §5.1, open decision 13 / board question 12). No importer exists in `packages/`.
- Verified: `tests/financial-vat-return-posting.php` section S (S1–S6, checkpoint `--from=S`); `tests/module-debtor.php` VS11; `tests/module-creditor.php` VS3; `tests/module-receipt.php` VS3.

### P5 part 2 — lifting a posted return, the service layer (stage S2 slice 6a, 2026-11-25)

«Aufheben» — `VatReturnPostingService::lift(returnId, version, reason): VatReturn` (ADR-042 addendum 2026-11-24 point 5; plan `docs/temp/vat-return-s2-plan.md` §4). **Services only: no controller action, button, confirm window or list column calls it** — board B4 and the admin pin come with the screens slice (6b). - **What it does:** (1) the settlement entry is reversed through the ledger's own reversal — `LedgerService::reverse()`: key `reversal:{year}/{number}`, origin `vat-return` + the same reference inherited, `reversal_of` set, no tax code (the reversal passes the freeze of its own period) —, **dated the settlement entry's own date** (the period's last day, plan §4 / scratch case 12): the VAT accounts carry the period's coded tax again as of its end, every later period stays untouched; text «Aufgehoben: » + the entry's text (with « (Neuerstellung n)» for a revision) + « — {reason}», whitespace folded, cut to 255; the whole reason stays on the row and in the protocol. (3) One `VatReturnLog` row `lift` with the reason (detail: `entry`, `reversal`; none for a nil return). A **NIL return** has no entry — no reversal, no number, the row and the protocol only.
- **Lock order** (the writer's): **0** the writer row `vat-return` (X), **1** the journal range of the settlement entry's fiscal year (X — the year the reversal goes into; none for a nil return), **2** the accounts of the settlement entry's LINES (S — exactly the rows the reversal posts on, not the mandator's current numbers), **3** every fiscal-year row (S), **4** the period rows of every year the VAT period touches (X, refreshed), **5** the latest live ordinary return, then the return asked for (X), **6** the first plain read (the row re-read), **7** `LedgerService::reverse()` re-takes 1–4 without waiting. A correction / annual row (S3) → `LogicException` — S3 lifts its own. ### Part 2 — journal, LedgerService, manual entries

- **`JournalEntry`** (table `journal_entry`, ADR-042 decision 5): `fiscal_year_id` FK, `number` (unique per year — `uniq_journal_entry_number`), `entry_date` (not `date`, a MariaDB function name), `text`, `kind` (`EntryKind`: `generated` | `manual`), `source_type` + `source_ref` (the OPAQUE origin, ADR-040 decision 2 — null on a manual entry), `idempotency_key` (unique `uniq_journal_entry_idempotency`, null on a manual entry — MariaDB allows many NULLs), `reversal_of_id` (self FK, unique `uniq_journal_entry_reversal_of` — **an entry is reversed at most once, in the schema**; a `ManyToOne` plus a named unique index rather than `OneToOne`, so the index carries our name and `diff` stays clean), `created_by` / `created_at`, `changed_by` / `changed_at`, and `version` (`#[ORM\Version]`, the optimistic lock of a manual edit — below). Index `(fiscal_year_id, entry_date)` for the reports. The period is NOT stored — it is derived from the date (`FiscalYear::periodOn()`), and period bounds never move. No setter; the one mutation is `amend()` for a manual edit, and it refuses a generated entry itself. `snapshot()` (the change log's before/after) carries the header incl. `created_by/at` and `changed_by/at`, and the lines; the idempotency comparison picks its own keys out of it and ignores the audit fields.
- **`JournalLine`** (table `journal_line`): `entry_id` FK (cascade persist + remove, `orphanRemoval`), `position` (from 1, deliberately NOT unique — Doctrine inserts before it deletes, and an edit that replaces the lines would collide with itself), `account_id` FK, `debit` / `credit` (`MoneyType`, `DECIMAL(15,2)`, exactly one positive, the other `0.00` — the entity constructor guards it too), tax data `tax_code` (VARCHAR 8, indexed) / `tax_rate` (INT, hundredths of a percent) / `tax_base` / `tax_amount` (money, nullable) — **all-or-none**, on the NET line only (revenue or expense), never on the tax-account line or the counter line: the VAT return (P5) is Σ `tax_base` and Σ `tax_amount` per code and rate, so exactly one line per taxed amount carries them. `text` nullable. No currency (ADR-042 decision 4).
- **Tax fields — what ADR-041 says and what is stored.** ADR-041 decision 7 names `taxCode`, `taxBase`, `taxAmount`; the line stores those AND a **`taxRate` snapshot** (plan §5.6: the return groups by code «+ rate», and two rates of one code meet in one period around a rate change — 2023/2024; `vat.md`'s rule for a Doctrine reference to a tax code asks for the rate snapshot as well) — recorded as a dated addendum to ADR-041, approved by the owner 2026-09-22. The label is NOT snapshotted (label snapshots belong to documents; a ledger line reports by code + rate, not by label). The tax code is referenced BY CODE with no foreign key (ADR-043 decision 19). **Base and amount are SIGNED** as the poster states them: a credit note or a reversal carries them negated, so the return can sum the column without asking which side the account was on. Verified: a sale and its reversal sum to `0.00` (`tests/module-financial.php` H8).
- **`EntryChange`** (table `journal_entry_change`, ADR-042 decisions 7 and 9, Q4): `entry_id`, `fiscal_year_id`, `entry_number` as PLAIN columns — **no foreign key**, so the row of a DELETED entry survives and documents the gap in the numbering; `action` (`ChangeAction`: `update` | `delete`), `changed_by` / `changed_at`, `before_snapshot` / `after_snapshot` (`JournalEntry::snapshot()` as JSON in TEXT columns — TEXT rather than the platform JSON type so the schema diff does not depend on how a MariaDB version reports a JSON check; `after` null for a delete). Immutable: constructor and getters. Creation is not logged — the entry carries created by/at. Shown per entry in the journal detail and as a whole on the change log screen (FIN-JOURNAL-CAPTURE-001, 2026-10-08).
- **`Ledger/` — the DTOs other modules see** (plan §5.4): `PostingRequest` (`generated(date, text, sourceType, sourceRef, idempotencyKey, lines)` / `manual(date, text, lines)`, private constructor), `PostingLine` (`debit(account, amount, …)` / `credit(…)`, the account by NUMBER, optional `taxCode` + `taxRate` + `taxBase` + `taxAmount` + `text`), `EntryRef` (`fiscalYear` code + `number` — no database id; how a module STORES it is its own shape, P3). Immutable and validated on construction (`InvalidArgumentException` = a programming error of the caller): at least two lines, one currency, Σ debit = Σ credit, one positive side per line, tax data all-or-none, a generated request names its origin and carries a key, a manual one carries no key.
- **`LedgerService::amend(string $idempotencyKey, PostingRequest $new): EntryRef` / `retract(string $idempotencyKey, string $sourceType): ?EntryRef`** (ADR-042 addendum 2026-10-06, owner: a generated entry is corrected ONLY by the module that posted it, the journal screen never edits it, no storno pair for a typo) — inside the caller's unit of work like `post()`. The entry is found by its KEY and locked (`lockForUpdate`); `amend()` compares the fingerprint (equal → no-op), refuses a date in another fiscal year (`fiscal-year-changed`), applies the period rules of a manual edit through `PostingRules::assertPeriodAllowsChange()` (lock-free first, then share-locked), resolves and share-locks the accounts (postable, not necessarily active — the counterpart of what exists), then `JournalEntry::amend()` + an `EntryChange` update row (before / after, the actor). `retract()` writes the delete change row (full snapshot) and removes the entry — its number stays a gap; a key nobody carries answers null (the Null gateway's world, or retracted already). Refused as `EntryNotEditableException`: `not-found`, `manual`, `source-mismatch` (another `sourceType`), `source-ref-changed` (another `sourceRef` — the origin is IMMUTABLE, review 2026-10-13: `JournalEntry::amend()` never stored a new ref, so a differing one was a change on every call, logged each time; decided: refuse rather than drop the ref from the fingerprint — a new ref is a new source, retract and post anew), `reversed` (a reversed entry or a reversal — the pair is frozen), `period-closed`, `period-vat-settled`, `fiscal-year-changed`; a manual request → `LogicException`. Lock order: entry (X) → accounts (S) → year (S) → period (S), the manual edit's. `JournalEntry::amend()` no longer refuses a generated entry itself — who may call it is the services' rule (`ManualEntryService::assertManual()` keeps the bookkeeper out). Verified: `tests/module-financial.php` K2-1–K2-6; first consumer debtor's `PaymentService` ([`debtor.md`](debtor.md)).
- **`LedgerService::post(PostingRequest): EntryRef`** — the one write path (plan §1, ADR-040 decisions 2 and 8, ADR-042 decision 6). Asserts `getTransaction(JournalEntry::class)->isOpen()` and never opens a unit of work (`LogicException` otherwise). Order inside: (1) **idempotency**, a read — a generated request whose key exists returns the existing `EntryRef` when the CONTENT is the same, and throws `IdempotencyConflictException` (a `PostingRefusedException`, reason `idempotency-conflict`, naming the existing entry) when it differs. «Content» = `PostingRequest::fingerprint()`: date, text, origin and the lines in order (account, debit, credit, tax code/rate/base/amount, text) — everything the module decides; compared with `fingerprintOf($entry->snapshot())`. Why loud: returning the old entry silently would hide that the source and the books disagree, posting again would post twice — both are worse than an exception at the caller. (2) **the rules** (`PostingRules`, `@internal`, shared with the manual edit): the fiscal year and period for the date (`no-fiscal-year`, `no-period`), the period state (`closed` → `period-closed`), the VAT freeze lock-free (a tax line dated in a settled VAT period → `vat-period-settled`, «the freeze» above), every account exists AND is postable AND active (`account-unknown`, `account-not-postable`, `account-inactive`), every tax code EXISTS in module-vat (`tax-code-unknown`), then the actor is resolved (an unnamed author refuses here). (3) **the number**, the FIRST write: `NumberRangeRepository::next($year->journalEntryRange())` — never before validation, so a refused posting never takes the range lock; right after it the accounts are re-checked under a shared row lock (`PostingRules::lockAccounts()`, FIN-TYPE-001 — refuses only in a race with «becomes a group» / a deactivation, and the refusal must propagate so the number goes back), then the period's committed state under a share lock, then — with a tax line only — the settled check again on a LOCKING read of the returns (`PostingRules::assertVatAccepts(…, locked: true)`). (4) the entry with its lines, `persist()`ed; the caller's flush at commit writes it, a rolled-back caller consumes no number (verified: G18/G19, and gapless under three parallel processes with rollbacks, K).
- **Tax codes: exist vs. active.** `PostingRules::assertTaxCodesExist()` asks for EXISTENCE only. A posting carries the code its document snapshotted, and that document may be finalised or reversed after the code was deactivated (ADR-043 decision 19: deactivated, never deleted; history resolves). Offering only ACTIVE codes for a NEW document is the screen's job — the manual form does (`ManualEntryForm::selectableCodes()`: active codes plus, on an edit, the codes the entry already carries; a deactivated code may be kept, never newly chosen — the `contact.md` type rule).
- **Accounts: postable vs. active** (ADR-043 decision 19 applied to accounts, review 2026-09-22 M5 — «inactive» means not offered for NEW postings, existing references keep working): `post()` needs every account POSTABLE and ACTIVE; `reverse()` needs POSTABLE only — a counterpart of an existing entry must always be possible, also on an account deactivated since (`PostingRules::resolveAccounts($lines, requireActive: false)`); a manual edit needs an active account for every NEW or CHANGED line and lets an UNCHANGED line keep its now-inactive account (`requireActive` as a `list<bool>` by line — a line is unchanged when its fingerprint equals a stored line's: account, amounts, tax data, text). `ManualEntryForm::keepFrom($entry)` applies the same rule first, so the row shows the error («… ist inaktiv — nur eine unveränderte Zeile behält es»).
- **What a caller of `post()` / `reverse()` sees under a race** (review M4; the behaviour is kept, this is the contract): the idempotency lookup is a READ, so the same key posted in two parallel units of work — or twice inside ONE unit of work before its flush — passes the lookup twice and fails at the caller's COMMIT with Doctrine's `UniqueConstraintViolationException` on `uniq_journal_entry_idempotency`; two parallel reversals of one entry fail the same way (their key is `reversal:{year}/{number}`), and on `uniq_journal_entry_reversal_of` should the keys ever differ. The whole unit of work rolls back, **no number is consumed**, nothing is half-written. The caller lets it propagate and does not retry inside the unit of work (ADR-039 decision 10 — no retry loop); a retry is a NEW unit of work, and with the same key it then returns the existing entry.
- **A reversal may be dated in a LATER fiscal year** than the entry it reverses (review P12): a correction happens in an OPEN period (ADR-042 decision 10), the reversal takes the next number of the year it is dated in, and `reversalOf` links across the years (verified K5). The journal shows «Storno von {year}/{number}» with the reversed entry's own year.
- **`LedgerService::reverse(EntryRef, DateTimeImmutable $date, string $reason): EntryRef`** (plan §1 correction principle, ADR-042 decisions 7 and 8): a GENERATED counterpart with debit and credit swapped and tax base / amount NEGATED (`PostingLine::swapped()`), dated `$date`, **its text IS the reason** (owner-approved 2026-09-22: the reason is the reversal entry's text, no separate column — the journal shows it where every entry shows what happened), origin INHERITED from the reversed entry (the same source is being corrected; `reverse()` has no origin parameter, plan §5.4), key `reversal:{year}/{number}`, `reversalOf` set. The reversal's date goes through the same period rules as any posting. Refused (`ReversalRefusedException`, reasons): `not-found`, `manual` (a manual entry is edited or deleted, never reversed), `is-reversal` (a reversal is not reversed — post the original anew), `already-reversed` (the service checks, the unique index enforces under a race), `no-reason`. Same open-unit-of-work rule as `post()`.
- **Who** (`Services/Actor`): the framework knows the current identity as `AuthUser` (`AuthService::getCurrentUser()`) — a logged-in backend user (realm `backend`, the username) or, in the CLI, the job runner's actor (realm `cron`, `cron:{jobKey}`, ADR-031). Both are NAMES, and the books keep the name (`created_by`, `changed_by`, the change log; VARCHAR 80) — not an id (a backend user can be deleted, the entry stays). `Actor::current()` REFUSES to guess (`LogicException`) when nobody is logged in or no `AuthService` is wired: a CLI script, the import (P5b) and the harness pass the actor explicitly (`new LedgerService($em, 'import:wdv')`). A posting without a named author is what the change log exists to prevent.
- **`ManualEntryService`** (owner, 2026-09-22): `create(PostingRequest $manual): EntryRef` (a manual request through `LedgerService::post()` in a unit of work opened HERE), `update(int $entryId, int $expectedVersion, PostingRequest $new): bool` (false = nothing to change: no change row, no version bump), `delete(int $entryId, int $expectedVersion)`. Each method OWNS its unit of work and refuses to run inside an open one (`LogicException`, the `FiscalYearService::open()` model) — a caller that wants many manual entries in one transaction (the import) uses `LedgerService::post()` with `PostingRequest::manual()` directly. Rules for edit and delete (`EntryNotEditableException`, reasons): a GENERATED entry → `generated` (in the domain — `JournalEntry::amend()` refuses as well); period `open` → allowed; `closed` → `period-closed`; a settled VAT period (the old or the new DATE is covered by a live return) → allowed only if NEITHER the old NOR the new version carries a tax line (`vat-period-settled`; the return summed the tax lines); an edit whose new date lies in ANOTHER fiscal year → `fiscal-year-changed` (the number belongs to the year — delete and re-create). Both the OLD period (where the entry is) and the NEW period (where the date moves) are checked. The new version arrives as a `PostingRequest` — structurally valid by construction. Inside `run()`: the entry is RE-READ with its header row locked (`JournalEntryRepository::lockForUpdate()`, `SELECT … FOR UPDATE`) and its version compared with `$expectedVersion` — gone or another version → `EntryConflictException`; then every database rule (`PostingRules`: year, period, accounts, tax codes) runs on the FRESH entity; only then is it touched (ADR-039 decision 9, DOCTRINE-TX-007): `EntryChange(update, before, after)` + `amend()` (date, text, lines replaced — the old lines leave the collection, orphan removal deletes them at flush — `changed_by` / `changed_at` stamped), or `EntryChange(delete, before, null)` + `remove()`. A delete leaves a GAP: the number is not reused (verified I22–I25).
- **Concurrency of manual edits** (review 2026-09-22 H1/M1–M3, decided: optimistic locking): `journal_entry.version` (`#[ORM\Version]`) travels as a hidden field of the edit form and the delete modal; the service takes id + expected version, never a pre-loaded entity. Two guards, one exception: the version check on the locked re-read catches a change that happened BEFORE the write (a second editor waits on the row lock, then reads the committed state — version bumped or row gone), and Doctrine's `OptimisticLockException` at flush (mapped to the same `EntryConflictException`) catches the rest. A manual edit ALWAYS bumps the version, also when only the lines change, because `amend()` counts the write (`WriteCounter`, FIN-LOCK-003) and the header row is updated — not because of the `changed_at` stamp, which doctrine/orm 3.8 ignores within the same second (verified I13b, I13c). The screen answers a conflict with «Die Buchung wurde inzwischen geändert oder gelöscht — bitte neu laden» and a redirect — never a 500. Verified: two parallel processes editing one entry → one `ok`, one `conflict`, two lines not four, version 2, one change row (I27/I28); a stale delete after a delete and a stale edit after a delete → `EntryConflictException`, one change row (I23b/I23c).

- **The one-line entry — the default capture form** (`Ui/OneLineEntryForm`, template `oneLine`; owner decisions 2026-09-22 after the P2 exit check 3a/3b): the wdv row `Soll | Datum | Bu-Nr | Text | Haben | Betrag`. The Soll account receives, the Haben account gives; the amount is the GROSS amount of the voucher or the bank. **Bu-Nr** is the journal number — shown, never entered: «neu» on a new entry (it is drawn gaplessly at post time, so it is not known before and is neither predicted nor reserved), the number when editing; there is no voucher-number field. **The MwSt row** (optional): a checkbox reveals it — CSS only, `.be-reveal` in `components/_forms.scss` (the `:checked` sibling selector). Rule 7 justification: showing an optional part of a form is presentation, the state has to reach the server anyway (the checkbox is a submitted field, re-rendered `checked`), and a CSS sibling rule does it without a script, a build or a no-JS fallback; no JavaScript was added. Fields: the tax code (active codes, reverse-charge excluded; on an edit also the entry's own) and the tax amount. **Empty tax amount** = computed from the gross at the rate valid on the ENTRY date — `VatCalculator::calculate()` in `PriceMode::Gross` (tax = gross × rate / (10000 + rate), commercial rounding): 400.00 at 8.1 % → 29.97, net 370.03; the wdv case 400.00 at 7.7 % (2023) → 28.60, not 30.80. **An entered tax amount** is the voucher value, taken as is, but only within min(`TAX_CORRECTION_MAX` 1.00, max(`TAX_CORRECTION_MIN` 0.05, `TAX_CORRECTION_PERCENT` 1 % of the computed tax)) — constants on `GrossEntryBuilder` since 2026-11-15, `OneLineEntryForm` names them for its help (orchestrator decision 2026-09-22 on review: a flat 1.00 let 0.00 pass on a 10.00 purchase; the limit is for voucher ROUNDING only). 400.00 VM: limit 0.30; 10.00 VM (computed 0.75): limit 0.05 (the floor); 25 000.00 VM (computed 1873.27): limit 1.00 (the ceiling). **PERCENT was 10 until 2026-09-23** (owner decision, P2 exit check case 7 in z77.ch, FIN-VAT-TOL-001): at 10 % the percentage only ever tightened a tax below 10.00, because above it the flat MAX won — so `400.00 VM` allowed a whole franc and accepted the wdv value **30.80** (400 × 7.7 % on top, the pre-2024 rate) against the correct 29.97, 0.83 off, without a word. That is the exact error the gross-mode form exists to end, so the tolerance must not wave it through; harness O6d pins it. A tax of 0.00 on a taxed code is accepted only when the computed tax is 0.00. The German refusal names the computed value and the limit. **The system writes the tax line — the net side by account TYPE** (owner, 2026-09-22): the NET line is the side whose account is an `expense` or `revenue` account, Soll or Haben; it carries `taxCode` / `taxRate` / `taxBase` = net / `taxAmount` = tax, the tax line (the `vatAccounts` account of the code's category) goes on the SAME side, the other side takes the gross. A purchase 6500/1020 VM: 6500 net + 1170 in Soll, 1020 gross; a sale 1020/3200 UN: 3200 net + 2200 in Haben; a customer credit note 3200/1100 UN 108.10: 3200 100.00 + 2200 8.10 in Soll, 1100 108.10 in Haben; a supplier refund 1020/4200 VM: 4200 + 1170 in Haben. Neither side a P&L account (a fixed asset 1500/1020 VI): the category decides — input codes Soll, every other Haben. Both sides P&L accounts: refused, Sammelbuchung. **Signs** exactly as the Sammelbuchung writes such a line (`ManualEntryForm::taxFor()`): base and amount positive when the net line stands on the code's NATURAL side (debit for input, credit for output), NEGATIVE on the opposite side — the credit note posts base −100.00 / tax −8.10 on UN, the refund −100.00 / −8.10 on VM (harness O19b/O20 compare both forms); the VAT return sums them per code + rate. **Zero / exempt codes** (`zero`, `exempt`): the code goes on the net line with base = gross and tax 0.00 (the return needs the turnover per code), NO tax line, a tax amount other than 0 is refused; a computed 0.00 of a taxed code (a few Rappen) also writes no tax line, and the hint says «keine Steuerzeile». **Reverse-charge** codes are refused in the one-line form (Bezugsteuer posts the tax on top to both sides — not a gross split): Sammelbuchung. **The tax account** comes from the MANDATOR record (owner decision E2, 2026-09-23 — `mandator.md`; until that day `financialConfig → vatAccounts`) — tax-code CATEGORY → the record's `vat-input-material` / `vat-input-other` / `vat-owed`, the ONE place (Rule 2), read only through `LedgerService::vatAccountFor()`; KMU start values pre-filled on the record's first save, verified against `res/charts/kmu.json`: `input-material` → 1170 «Vorsteuer MWST Material, Waren, Dienstleistungen, Energie», `input-other` → 1171 «Vorsteuer MWST Investitionen, übriger Betriebsaufwand», `standard` / `reduced` / `special` → 2200 «Geschuldete MWST (Umsatzsteuer)». An empty field, or an account that is not a posting target, is refused with a message naming the mandator screen (`LedgerService::MANDATOR_HINT`) — the latter through `LedgerService::accountExists()` (plan §5.4), whose first production caller this is (decided: the plan's public method rather than the form's own account lookup, because it is exactly «validate an account a configuration names», and debtor's account settings (P3) are the next caller). Accounts are typed by number with the shared `<datalist>` (its options read «1020 Bankguthaben»); a leading number is enough («1020 Bankguthaben» is read as 1020), and after a submit the resolved account name stands under the field. **Capture flow** (since 2026-09-28 on the journal page itself, FIN-JOURNAL-CAPTURE-001): after a save the journal comes back with the empty row, the SAME date (`list?date=…`, the mode kept) and a flash «Buchung 2026/17 erfasst»; the new entry stands at the top of the list below. **Editing**: an entry is edited one-line only when it is EXACTLY what the form writes — `OneLineEntryForm::startFrom()` reads the fields from the lines in the CANONICAL order the form writes ([Soll, Haben]; [net Soll, tax Soll, gross Haben]; [gross Soll, net Haben, tax Haben]) and must rebuild the stored lines 1:1 (fingerprint of the lines: order, sides, amounts, tax data, no line text, active accounts, the current `vatAccounts`). ### Part 3 — reports

- **The path**: `Ui/ReportControllerTrait` (host `Finance/ReportController`) → `Services/LedgerReports` (read-only, no unit of work) → SQL on `connection()` in `JournalLineRepository` (aggregates) and `JournalEntryRepository` (the journal report's page) — every method marked Doctrine-only (ADR-039 decision 8), every value BOUND (LIMIT/OFFSET too, `ParameterType::INTEGER`). Result types in `Reports/` (`TrialBalance`, `BalanceSheet`, `IncomeStatement`, `AccountStatement`, `JournalReport`, their rows, `ReportRange`, `Paging`) — immutable, no entity writes.
- **Never hydrated lines** (plan §5.5, §12/§13): one aggregate, `JournalLineRepository::balancesByAccount(year, from, to)` — Σ debit / Σ credit per account over `journal_entry` ⋈ `journal_line` ⋈ `account`, only accounts with lines, in number order — feeds the trial balance, the balance sheet and the income statement. What IS hydrated: the chart (`AccountRepository::allInOrder()`, a few hundred rows, for the group tree) and ONE bounded page of the journal report (the part-2 fetch-join `hydrate()`, reused — it now keeps the order of the ids the SQL chose).
- **Money from SQL**: MariaDB returns `SUM()` over `DECIMAL(15,2)` as a decimal STRING with two places; `LedgerReports::money()` turns it into `Money` with `Money::fromDecimal()` in the base currency (`LedgerService::baseCurrency()` — the ONE reader of `systemConfig → baseCurrency` in this module; the journal form's `journalCurrency()` delegates to it). No float anywhere on the path — a harness source guard (R46). Base currency only (ADR-042 decision 4).
- **`ReportRange`**: one fiscal year and from–to INSIDE it, both ends inclusive (`BETWEEN`); refused otherwise (`InvalidArgumentException`). A report never spans years.
- **Sign convention** (`AccountType::isDebitNormal()`): asset and expense are debit-normal, liability, equity and revenue credit-normal. Every balance a report shows is POSITIVE on the account's natural side and negative on the opposite side (an overdrawn bank account, a revenue reduction larger than the revenue). The trial balance does not sign at all: it splits the balance into «Saldo Soll» and «Saldo Haben».
- **Trial balance** (Saldobilanz): per account with lines in the range Σ Soll, Σ Haben, Saldo Soll / Saldo Haben; totals of both pairs, and `isBalanced()` (Σ Soll = Σ Haben AND Σ Saldo Soll = Σ Saldo Haben) shown as a badge.
- **Balance sheet** (Bilanz) is a statement AT a day: it reads from the year's FIRST day to «to» (`ReportRange::fromYearStart()`), whatever «from» says — the page offers «Stichtag» and the choice of section ENDS only (FIN-UI-013). Aktiven = type `asset`; Passiven = Fremdkapital (`liability`) and Eigenkapital (`equity`) as two blocks; the CURRENT RESULT (revenue − expense over the same days) is a line of its own in Eigenkapital. With it, Aktiven = Passiven by construction of double entry (Σ(debit − credit) over all lines is zero); the page shows it and would show the difference.
- **Income statement** (Erfolgsrechnung) over from–to: Ertrag (`revenue`) and Aufwand (`expense`); result = Ertrag − Aufwand, positive a profit. At the balance sheet's day and from the year's start it equals the balance sheet's result line (harness R13).
- **Grouping** (`LedgerReports::section()`): the TYPE decides the block, the chart's parent chain the grouping. Each block holds the accounts of its types with lines, and every group on their parent chains with the SUBTOTAL of exactly those accounts, walked top-down from the roots in number order, depth for the indentation. A group without such an account is left out («groups without movement are hidden»); an account that moved but balances to zero is shown with 0.00. A KMU group mixing types (class 6 / group 69 with `6950 Finanzertrag`) appears in BOTH blocks, each time with its own accounts — no number rule. An account whose parent chain never reaches a root (a group cycle or an orphaned group written past the validator — a database edit, an import) is NOT dropped: it is appended flat at depth 0, listed in `StatementSection::unplaced`, and the block shows a note naming it («Nicht im Kontenbaum erreichbar: …» — on the screen and in the PDF; the comparison keeps such accounts flat at the END of its block and names them in the block's `unplaced`, restored 2026-10-13 after the comparison of FIN-UI-011 had lost the note); afterwards Σ of the depth-0 rows equals the block total (asserted — a mismatch is a code bug and throws).
- **Account statement** (Kontoblatt): one account, one range. `accountTotals()` gives in ONE query the opening (Σ debit − credit of the lines of the SAME fiscal year dated before «from»), Σ debit, Σ credit and the line count in the range; `accountLines()` one page in date / number / position order with the running Σ (debit − credit) as a WINDOW FUNCTION (`SUM(…) OVER (ORDER BY … ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`, MariaDB ≥ 10.2) computed over the whole range BEFORE `LIMIT/OFFSET` — so page 7's running balance counts pages 1–6 without reading them. Balance of a line = opening + running, on the natural side; the page's «Übertrag» (carry) = the first line's balance minus its own movement (= the opening on page 1; on a later page the row reads «Übertrag von Seite n» and carries no date); total and closing cover the whole range. Counter account (owner 2026-10-22, FIN-REPORT-006): ONE extra query per page / PDF chunk reads every line of the page's entries (`JournalLineRepository::linesOfEntries()`), `LedgerReports::counterRows()` pairs them — the statement's line is the ONLY line on its side of the entry → ONE ROW PER COUNTER LINE (each counter account with that line's amount, the same date, number and text, `AccountStatementLine::$isSplit`; the running balance steps through them and ends on the line's own SQL running balance); the other side has exactly one line → that account; else (m:n, or the account on both sides) one row, the one other account, «div.» when there are several, «–» when none. Display only; totals, closing and paging (counted in journal lines) unchanged. The entry number links to the journal's detail page (`reportJournalBase()`).
- **Paging** (`Z77\Shared\Paging\Paging` in the kernel since P3 part 3 — was `Reports/Paging`; it moved with the pager partial when debtor's document list paged, Rule 8; server links `?page=`, `.be-pagination`): account statement 500 lines per page (`LedgerReports::ACCOUNT_STATEMENT_PAGE_SIZE`), journal report 200 entries per page (`JOURNAL_PAGE_SIZE`). Chosen over a hard limit: a busy bank account has thousands of lines a year and every one must be reachable; paper is the PDF, which takes every line (FIN-PDF-001). A page beyond the last (`?page=99`) shows the last page and a notice says so (`Paging::isBeyondLast()`), like the date fallbacks. The pager partial is the kernel's `partials/pager` (namespace `Z77\Shared`) since the second consumer arrived (debtor's document list, P3 part 3).
- **Journal report**: the entries of the range with their lines — a STANDARD LIST since 2026-10-15 (owner: «erlaube hier das Sortieren und Suchen — serverseitig, bei x tausend Einträgen», `Ui/JournalReportListing`, listing.md): Datum · Nr. · Konto · Text · MWST · Soll · Haben; the titles of Datum, Nr., Text and Soll sort (default date ascending — the journal's order), the magnifiers of Datum (a day / month / year), Nr. (exact), Konto (an account with a line on EITHER side — `JournalSearch::$account`), Text (contains) and Soll (the entry total) search in the DATABASE. The search is the journal list's own (`JournalSearch` → `JournalEntryRepository::search()`), held to the report range by `JournalSearch::within()` — a searched date narrows the range, never widens it. The count, Σ Soll and Σ Haben cover every entry the search finds in the range — each summed on its own in SQL (`JournalEntryRepository::searchSummary()`), the page shows both; the ids by SQL, then the part-2 fetch-join (which also fetches the reversed entry's fiscal year — «Storno von {year}/{number}» costs no query per reversal). The list is a fetch region (`journal-report-find-list`): sort, page and search reload only it, the range form above keeps what is typed; every link carries year / from / to. Changing the range drops the search (the range form carries none). Widths (owner 2026-10-16): every column fixed in rem — they grow with the font size — only Text takes the rest. «Zurücksetzen» stands BEFORE the title and drops the search AND the sort (`partials/listReset`, owner 2026-10-16 — every list). **The PDF prints what the screen shows** (owner 2026-10-16): the same search and sort, not paged, «Suche: …» in the subtitle and «Total gefunden» (`journalForPdf($range, $search)` → `JournalEntryRepository::searchInChunks()`, detached chunks as before; `JournalReportListing::describe()`). Deleted manual entries are gaps; the change log SCREEN (Finanzen › Änderungsprotokoll) lists them.
- **The screens** (`/backend/finance/report/…`, fragment/host pattern like parts 1/2): `trial-balance` (the controller's `defaultAction` — `backendConfig` deviation entry, the reports have no list), `balance-sheet`, `income-statement`, `account-statement?account={number}`, `journal`. Measured by the review (2026-09-22) at **200'000 lines**: trial balance and balance sheet ≈ 1.1 s, a journal page ≈ 0.8 s (filesort on date, number), an account statement of an account with 90'000 lines ≈ 1.6 s PER PAGE — the window function plus ORDER BY/LIMIT sorts the whole range on every page. EXPLAIN at 20'000 lines: `journal_entry` by `idx_journal_entry_date` (`fiscal_year_id, entry_date`), `journal_line` by the FK index on `entry_id`, `account` by primary key; whether MariaDB applies the account filter as a rowid filter or picks the `account_id` index depends on the volume and its statistics. A composite `journal_line (account_id, entry_id)` was measured and does NOT help (1.56 s). No new index or migration; the real fix is keyset pagination (pending, FIN-REPORT-005).

## rules

- When writing an `Account` from any code path (backend, import, a migration of a wdv chart) → MUST go through `AccountService` (`save()`, `update()`, `setActive()`); MUST NOT `persist()` an account directly — the validator lives there
- When changing an EXISTING (managed) account → MUST hand the cleaned values to `AccountService::update($account, $values)`, the parent as the entity under `parent`; MUST NOT call `mapFromArray()` or a setter on the loaded account first (ADR-039 decision 9)
- When an account is no longer needed → MUST deactivate it; MUST NOT delete the row or add a delete action — journal lines reference it
- When an account needs a different number → MUST create a new account and deactivate the old one; MUST NOT change `number` on an existing account (refused with `AccountNumberChangedException`)
- When an account's `type` or `postable` must change → MUST go through `AccountService::update()` OUTSIDE any open unit of work (the guarded path owns its unit of work and refuses a nested call); MUST NOT write `account.type` or `account.postable` in SQL or through a setter — the journal locks live in the service (FIN-TYPE-001)
- When the type of an account with lines in a `closed` period is wrong → MUST create a new account with the right type and move the balance with a manual transfer entry; MUST NOT reopen the year (or edit the type in SQL) just to get around the refusal (owner, 2026-09-22: after the close nothing changes — the admin reopen of 2026-09-30 is for a real correction, with its reason in the protocol)
- When a code path writes journal lines → MUST re-check its accounts with `PostingRules::lockAccounts()` AFTER the number is drawn (`post()` does, the manual edit does without a number); MUST NOT take an account row lock BEFORE the `NumberRange` draw (ADR-039 decision 10) and MUST NOT rely on the plain read of `resolveAccounts()` alone
- When a caller of `post()` / `reverse()` receives `PostingRefusedException` → MUST let it end the unit of work (propagate or roll back); MUST NOT catch it inside `run()` and commit — `account-not-postable` / `account-inactive` can come AFTER the number was drawn (FIN-TYPE-001 race), and a commit would consume the number without an entry or a change row
- When grouping accounts → MUST put a postable account under a GROUP (`postable = false`); MUST NOT make an account with children postable or give a postable account children
- When offering the KMU chart → MUST call `AccountService::adoptKmuChart()` and offer the button only while `AccountRepository::isEmpty()`; MUST NOT seed the chart in the installer or a migration (owner, 2026-09-22 — a migrated chart must not get it forced on it)
- When a save changes one account row (edit, the active switch, a new account) → MUST answer with `accountRowAnswer()` (`FetchResponse::replaceRow()` with `Backend/AccountController/_row`), a new account with `insertRow()` before the next number, and the in-place flash (`pushFlash()` BEFORE the answer is built); MUST NOT answer `reload` — only a GROUP moved to another group and the KMU fill reload (FIN-UI-006). A template showing an account row MUST render `_row`, never its own copy
- When a dialog of the account or fiscal-year screen gets actions → MUST render them with `partials/modalActions` (namespace `Z77\Shared`) directly under `.be-modal__header`; `'end' => true` only for a confirm without any input field (ADR-049 rev. 2026-10-10)
- When an account must not be chosen for an invoice line (a credit note on an earlier invoice still may name it, owner 2026-10-13) → MUST switch off «auf Belegen wählbar» on the account (`selectable_on_documents`, through `AccountService::update()`); MUST NOT keep a list of document accounts anywhere else (mandator, debtor config) — the flag on the account is the one source (owner 2026-10-12, Rule 2)
- When editing `res/charts/kmu.json` → MUST keep UTF-8 without BOM, parents before children, five-type values and the Sterchi numbers, and MUST run `php tests/module-financial.php` (B-section checks the structure); MUST NOT round-trip it through Windows PowerShell (DATA-JSON-001)
- When a fiscal year is opened (backend, import, test) → MUST go through `FiscalYearService::open()` OUTSIDE any open unit of work (it refuses a nested call) and MUST treat a leftover `journal-entry.{code}` range as a conflict to resolve, not to reuse (refused on `code`); MUST NOT persist a `FiscalYear` or a `Period` directly or create `journal-entry.{code}` elsewhere — the year, its periods and its range are one unit of work
- When a fiscal year was opened by mistake → MUST delete it through `FiscalYearService::delete($yearId)` OUTSIDE any open unit of work, which allows only the LATEST or the EARLIEST year with no entry, no change row and its range at 0; MUST NOT delete a year, its periods or its range by hand in the database, MUST NOT delete a year that was ever posted in (correct it with entries instead), and MUST NOT drop `journal-entry.{code}` anywhere else
- When code needs the name of a year's journal-entry range → MUST use `FiscalYear::journalEntryRange()`; MUST NOT compose `'journal-entry.' . …` inline
- When choosing a fiscal-year code → MUST keep it lower-case kebab of at most 16 characters (it is the dotted segment of a range name); MUST NOT reuse a code or rely on case
- When a fiscal year is closed or reopened (backend, script, a migrated past year) → MUST go through `FiscalYearCloseService::close()` / `reopen($yearId, $reason)` OUTSIDE any open unit of work (they own theirs, lock, re-check order and close check, and write the protocol); MUST NOT write `fiscal_period.state` in SQL, call `Period::transitionTo()` from anywhere else, or close single periods (owner 2026-09-30: only the whole year)
- When a period's state needs a NEW transition → MUST add it to `Period::transitionTo()` and to a service of this module with its own rules, locks and protocol, and MUST decide what a reopen restores for such a period; MUST NOT write `fiscal_period.state` any other way; MUST NOT bring «VAT-settled» back as a period state (ADR-042 addendum 2026-11-24, point 2 — it is read from the returns)
- When a module has work that must be done before a year is closed → MUST implement `OpenWorkCheckInterface` and declare it under `openWorkChecks` → `period-close` in its own config (parameters `fiscalYear`, `from`, `to`), BLOCKING for what would be refused or missing in the closed year, WARNING for what the closer should see; MUST NOT call into financial or let financial name the module
- When code writes into the journal (a posting, a reversal, a manual edit or delete) → MUST re-read the period's state through `PostingRules::lockedPeriodState()` (fiscal-year row S, THEN period S) after its number / entry / account locks, as `post()` and `ManualEntryService` do, and decide on that state; MUST NOT rely on the period entity a request loaded earlier (a year close may have committed since) and MUST NOT lock a period without its year first or take an account lock after the period — the close takes years (X) → periods (X), and the `journal_entry` insert share-locks the year at the flush anyway (review 2026-09-30, the deadlock)
- When adding a code path that locks fiscal-year or period rows → MUST keep the order `NumberRange` → accounts → fiscal-year rows → periods; MUST NOT lock a period before its year, or a year before an account, in any unit of work
- When any module or script writes into the journal (an invoice, a payment, an import, a job) → MUST build a `PostingRequest::generated()` with an opaque origin and an idempotency key and call `LedgerService::post()` INSIDE its own `getTransaction(JournalEntry::class)->run()`, together with the writes that belong to the posting; MUST NOT `persist()` a `JournalEntry` or a `JournalLine` directly, MUST NOT draw from `journal-entry.{code}` itself, and MUST NOT open the unit of work inside financial (ADR-040 decisions 2 and 7, ADR-042 decision 6)
