## mental model

`z77/module-financial` (plan §5, ADR-040, ADR-042) is the double-entry bookkeeping every posting source reaches through one door, `LedgerService::post()` — it knows no module. Built in three parts: **part 1** the chart of accounts and the fiscal years with their periods; **part 2 (this state)** the journal (`JournalEntry` / `JournalLine`), `LedgerService` (`post()`, `reverse()`), manual entries with their change log (`EntryChange`, `ManualEntryService`) and the journal screens; **part 3** the reports. The VAT return, the period transitions and the year-end are P5. All entities are Doctrine (`#[Entity('doctrine')]`, announced in `financialConfig.inc.php` → `doctrineEntities`); the package depends on kernel, `persistence-doctrine` and `module-vat` (tax codes are validated against it and the manual form resolves rates through `VatRates`) and requires PHP 8.4.

### Part 1 — chart of accounts, fiscal years

- **`Account`** (table `account`: `number` unique, `name`, `type`, `parent_id` FK to `account`, `postable`, `active`). The number is digits only, at most 10, stored as a string — string order is the chart's order (`1` < `10` < `100` < `1000` < `1020` < `106` < … < `11`), which `AccountRepository::allInOrder()` uses and the list indents by. Grouping is a plain parent reference, no nested set. A **group** (KMU class `1`, main group `10`, group `100`) is an account with `postable = false`; only postable AND active accounts are accepted on a journal line (`PostingRules`).
- **Five types** (`AccountType`: `asset`, `liability`, `equity`, `expense`, `revenue` — owner decision 2026-09-22): equity is its own type so the balance sheet splits equity from debt by type, without a number rule. German labels live in the UI (`ACCOUNT_TYPE_LABELS` in the trait: Aktiven, Fremdkapital, Eigenkapital, Aufwand, Ertrag). A group carries a type as well; for a group mixing types (KMU classes 7 and 8, group 69 with `6950 Finanzertrag`) it is informational.
- **Validation** (`AccountValidator`): number required, digits, unique; name required; type one of the five; the parent must be a GROUP, never the account itself or one of its descendants (the validator walks the chain upwards, with a visited set against a cycle already in the data); a group WITH children cannot become postable. Deliberately no rule tying the number to the parent's number or the type to the parent's type — the KMU chart mixes types inside a class, and its groups are number RANGES, not prefixes (`1020` sits in group `100`, `1850` in `180`).
- **Write side = `AccountService`**: `save($new)`, `update($account, $values)` (the parent travels as the entity under the key `parent`), `setActive()`, `adoptKmuChart()`. `update()` validates a detached `clone` first and applies the values to the managed entity only when it passed (ADR-039 decision 9, the `ContactService` model); a refused change never reaches the next flush. The **number is immutable** (`AccountNumberChangedException`): settings and other modules' configuration name accounts by number (plan §5.1, §5.4), and so does every `PostingLine`. No delete anywhere — an account is deactivated; journal lines reference it by FK. A unique-number race in `save()` becomes the validator's field error (`uniq_account_number`).
- **KMU chart by button, not by seed** (owner decision 2026-09-22): `res/charts/kmu.json` (UTF-8 without BOM, a list of `{number, name, type, postable, parent}` with parents before children) is the Swiss SME chart in the Sterchi structure — classes 1–9, main groups, groups and 196 rows with the common postable accounts, German names. `adoptKmuChart()` refuses unless the chart is EMPTY (`AccountRepository::isEmpty()`, any row counts, active or not — `ChartNotEmptyException`), validates every row before persisting any, and writes all in ONE flush; two adoptions racing collide on the unique number and the loser writes nothing. Rationale: an installation that migrates its wdv chart (P5b) must not get a second chart forced into it. Owner decisions 2026-09-22 on the content: class 28 ships in the **legal-entity variant only** («Eigenkapital (juristische Personen)») — a sole proprietorship adds Kapital / Privat by hand in the backend, there is no second chart file; class 9 «Abschluss» carries its main groups only — its postable closing accounts arrive with the year-end in P5.
- **`FiscalYear`** (table `fiscal_year`: `code` unique, `start_date` unique, `end_date`) and **`Period`** (table `fiscal_period`: `fiscal_year_id` FK, `start_date`, `end_date`, `state`; unique on year + start). Owner decisions 2026-09-22: FREE start and end dates (deviating, shortened, extended years), at most 24 months; years are contiguous — a new year starts the day after the latest one ends, the first may start anywhere; periods are CALENDAR MONTHS clipped to the year (15.3.–31.12. → ten periods, the first 15.3.–31.3.). `FiscalYear::covers($date)` and `periodOn($date)` (a walk over the dozen periods, no query) and `FiscalYearRepository::findByDate($date)` (DQL) are how the ledger finds the year and period of a posting date.
- **The code** names the year and its number range `journal-entry.{code}` (`FiscalYear::journalEntryRange()`, the one place it is composed): lower-case kebab (`2026`, `2026-27`), at most 16 characters, unique, proposed from the dates (`FiscalYearService::proposeCode()`: `2026` inside one calendar year, `2026-27` across). A code is needed rather than the start year because two years can start in the same calendar year (short year 1.1.–30.6.2026, then 1.7.2026–30.6.2027) — orchestrator's follow-on decision to the owner's free dates. Immutable: `FiscalYear` has no public setter (code and dates come with the constructor), and there is no edit and no delete of a year. An empty code is reported only when both dates are valid — otherwise the code would have been proposed from them, and the date errors say what to fix.
- **Opening a year** (`FiscalYearService::open()`): validate (`FiscalYearValidator`), derive the monthly periods, then ONE unit of work through `UnifiedEntityManager::getTransaction(FiscalYear::class)->run()` — first `getRepository(NumberRange::class)->create('journal-entry.{code}')` (lock order: `NumberRange` first), then `persist()` of the year with its periods (cascade). The range is created at 0 and committed with the year, so the first draw under contention never takes the new-row path (DOCTRINE-NR-003); an exception anywhere rolls back year, periods and range together. The range must be NEW: `create()` answers `false` for a row that already exists (a leftover of a removed year, an import), and continuing it would start the year's entries at its old number + 1 unnoticed — refused as a `code` field error, rolled back (review M1). `open()` OWNS its unit of work and refuses to run inside an open one (`LogicException`): nested, the flush would happen at the caller's commit, where the race mapping can no longer turn a unique-index violation into a field error (review L1) — the production caller is the backend controller. A race of two openings of the same next year collides on `uniq_fiscal_year_start` and becomes a `start_date` field error.
- **Period state** (`PeriodState`: `open`, `vat-settled`, `closed` — ADR-042 decision 10): every period is created `open`; there is no transition and no state setter yet (P5). The ledger refuses by it (part 2, below); the harness sets states directly in SQL to prove the refusals.

### Part 2 — journal, LedgerService, manual entries

- **`JournalEntry`** (table `journal_entry`, ADR-042 decision 5): `fiscal_year_id` FK, `number` (unique per year — `uniq_journal_entry_number`), `entry_date` (not `date`, a MariaDB function name), `text`, `kind` (`EntryKind`: `generated` | `manual`), `source_type` + `source_ref` (the OPAQUE origin, ADR-040 decision 2 — null on a manual entry), `idempotency_key` (unique `uniq_journal_entry_idempotency`, null on a manual entry — MariaDB allows many NULLs), `reversal_of_id` (self FK, unique `uniq_journal_entry_reversal_of` — **an entry is reversed at most once, in the schema**; a `ManyToOne` plus a named unique index rather than `OneToOne`, so the index carries our name and `diff` stays clean), `created_by` / `created_at`, `changed_by` / `changed_at`, and `version` (`#[ORM\Version]`, the optimistic lock of a manual edit — below). Index `(fiscal_year_id, entry_date)` for the reports. The period is NOT stored — it is derived from the date (`FiscalYear::periodOn()`), and period bounds never move. No setter; the one mutation is `amend()` for a manual edit, and it refuses a generated entry itself. `snapshot()` (the change log's before/after) carries the header incl. `created_by/at` and `changed_by/at`, and the lines; the idempotency comparison picks its own keys out of it and ignores the audit fields.
- **`JournalLine`** (table `journal_line`): `entry_id` FK (cascade persist + remove, `orphanRemoval`), `position` (from 1, deliberately NOT unique — Doctrine inserts before it deletes, and an edit that replaces the lines would collide with itself), `account_id` FK, `debit` / `credit` (`MoneyType`, `DECIMAL(15,2)`, exactly one positive, the other `0.00` — the entity constructor guards it too), tax data `tax_code` (VARCHAR 8, indexed) / `tax_rate` (INT, hundredths of a percent) / `tax_base` / `tax_amount` (money, nullable) — **all-or-none**, on the NET line only (revenue or expense), never on the tax-account line or the counter line: the VAT return (P5) is Σ `tax_base` and Σ `tax_amount` per code and rate, so exactly one line per taxed amount carries them. `text` nullable. No currency (ADR-042 decision 4).
- **Tax fields — what ADR-041 says and what is stored.** ADR-041 decision 7 names `taxCode`, `taxBase`, `taxAmount`; the line stores those AND a **`taxRate` snapshot** (plan §5.6: the return groups by code «+ rate», and two rates of one code meet in one period around a rate change — 2023/2024; `vat.md`'s rule for a Doctrine reference to a tax code asks for the rate snapshot as well). The label is NOT snapshotted (a ledger line reports by code + rate, not by label). The tax code is referenced BY CODE with no foreign key (ADR-043 decision 19). **Base and amount are SIGNED** as the poster states them: a credit note or a reversal carries them negated, so the return can sum the column without asking which side the account was on. Verified: a sale and its reversal sum to `0.00` (`tests/module-financial.php` H8).
- **`EntryChange`** (table `journal_entry_change`, ADR-042 decisions 7 and 9, Q4): `entry_id`, `fiscal_year_id`, `entry_number` as PLAIN columns — **no foreign key**, so the row of a DELETED entry survives and documents the gap in the numbering; `action` (`ChangeAction`: `update` | `delete`), `changed_by` / `changed_at`, `before_snapshot` / `after_snapshot` (`JournalEntry::snapshot()` as JSON in TEXT columns — TEXT rather than the platform JSON type so the schema diff does not depend on how a MariaDB version reports a JSON check; `after` null for a delete). Immutable: constructor and getters. Creation is not logged — the entry carries created by/at.
- **`Ledger/` — the DTOs other modules see** (plan §5.4): `PostingRequest` (`generated(date, text, sourceType, sourceRef, idempotencyKey, lines)` / `manual(date, text, lines)`, private constructor), `PostingLine` (`debit(account, amount, …)` / `credit(…)`, the account by NUMBER, optional `taxCode` + `taxRate` + `taxBase` + `taxAmount` + `text`), `EntryRef` (`fiscalYear` code + `number` — no database id; how a module STORES it is its own shape, P3). Immutable and validated on construction (`InvalidArgumentException` = a programming error of the caller): at least two lines, one currency, Σ debit = Σ credit, one positive side per line, tax data all-or-none, a generated request names its origin and carries a key, a manual one carries no key.
- **`LedgerService::post(PostingRequest): EntryRef`** — the one write path (plan §1, ADR-040 decisions 2 and 8, ADR-042 decision 6). Asserts `getTransaction(JournalEntry::class)->isOpen()` and never opens a unit of work (`LogicException` otherwise). Order inside: (1) **idempotency**, a read — a generated request whose key exists returns the existing `EntryRef` when the CONTENT is the same, and throws `IdempotencyConflictException` (a `PostingRefusedException`, reason `idempotency-conflict`, naming the existing entry) when it differs. «Content» = `PostingRequest::fingerprint()`: date, text, origin and the lines in order (account, debit, credit, tax code/rate/base/amount, text) — everything the module decides; compared with `fingerprintOf($entry->snapshot())`. Why loud: returning the old entry silently would hide that the source and the books disagree, posting again would post twice — both are worse than an exception at the caller. (2) **the rules** (`PostingRules`, `@internal`, shared with the manual edit): the fiscal year and period for the date (`no-fiscal-year`, `no-period`), the period state (`closed` → `period-closed`, `vat-settled` with a tax line → `period-vat-settled`), every account exists AND is postable AND active (`account-unknown`, `account-not-postable`, `account-inactive`), every tax code EXISTS in module-vat (`tax-code-unknown`), then the actor is resolved (an unnamed author refuses here). (3) **the number**, the FIRST write: `NumberRangeRepository::next($year->journalEntryRange())` — never before validation, so a refused posting never takes the range lock. (4) the entry with its lines, `persist()`ed; the caller's flush at commit writes it, a rolled-back caller consumes no number (verified: G18/G19, and gapless under three parallel processes with rollbacks, K).
- **Tax codes: exist vs. active.** `PostingRules::assertTaxCodesExist()` asks for EXISTENCE only. A posting carries the code its document snapshotted, and that document may be finalised or reversed after the code was deactivated (ADR-043 decision 19: deactivated, never deleted; history resolves). Offering only ACTIVE codes for a NEW document is the screen's job — the manual form does (`ManualEntryForm::selectableCodes()`: active codes plus, on an edit, the codes the entry already carries; a deactivated code may be kept, never newly chosen — the `contact.md` type rule).
- **Accounts: postable vs. active** (ADR-043 decision 19 applied to accounts, review 2026-09-22 M5 — «inactive» means not offered for NEW postings, existing references keep working): `post()` needs every account POSTABLE and ACTIVE; `reverse()` needs POSTABLE only — a counterpart of an existing entry must always be possible, also on an account deactivated since (`PostingRules::resolveAccounts($lines, requireActive: false)`); a manual edit needs an active account for every NEW or CHANGED line and lets an UNCHANGED line keep its now-inactive account (`requireActive` as a `list<bool>` by line — a line is unchanged when its fingerprint equals a stored line's: account, amounts, tax data, text). `ManualEntryForm::keepFrom($entry)` applies the same rule first, so the row shows the error («… ist inaktiv — nur eine unveränderte Zeile behält es»).
- **What a caller of `post()` / `reverse()` sees under a race** (review M4; the behaviour is kept, this is the contract): the idempotency lookup is a READ, so the same key posted in two parallel units of work — or twice inside ONE unit of work before its flush — passes the lookup twice and fails at the caller's COMMIT with Doctrine's `UniqueConstraintViolationException` on `uniq_journal_entry_idempotency`; two parallel reversals of one entry fail the same way (their key is `reversal:{year}/{number}`), and on `uniq_journal_entry_reversal_of` should the keys ever differ. The whole unit of work rolls back, **no number is consumed**, nothing is half-written. The caller lets it propagate and does not retry inside the unit of work (ADR-039 decision 10 — no retry loop); a retry is a NEW unit of work, and with the same key it then returns the existing entry.
- **A reversal may be dated in a LATER fiscal year** than the entry it reverses (review P12): a correction happens in an OPEN period (ADR-042 decision 10), the reversal takes the next number of the year it is dated in, and `reversalOf` links across the years (verified K5). The journal shows «Storno von {year}/{number}» with the reversed entry's own year.
- **`LedgerService::reverse(EntryRef, DateTimeImmutable $date, string $reason): EntryRef`** (plan §1 correction principle, ADR-042 decisions 7 and 8): a GENERATED counterpart with debit and credit swapped and tax base / amount NEGATED (`PostingLine::swapped()`), dated `$date`, **its text IS the reason** (that is where the reason is recorded — the journal shows it where every entry shows what happened; no extra column), origin INHERITED from the reversed entry (the same source is being corrected; `reverse()` has no origin parameter, plan §5.4), key `reversal:{year}/{number}`, `reversalOf` set. The reversal's date goes through the same period rules as any posting. Refused (`ReversalRefusedException`, reasons): `not-found`, `manual` (a manual entry is edited or deleted, never reversed), `is-reversal` (a reversal is not reversed — post the original anew), `already-reversed` (the service checks, the unique index enforces under a race), `no-reason`. Same open-unit-of-work rule as `post()`.
- **Who** (`Services/Actor`): the framework knows the current identity as `AuthUser` (`AuthService::getCurrentUser()`) — a logged-in backend user (realm `backend`, the username) or, in the CLI, the job runner's actor (realm `cron`, `cron:{jobKey}`, ADR-031). Both are NAMES, and the books keep the name (`created_by`, `changed_by`, the change log; VARCHAR 80) — not an id (a backend user can be deleted, the entry stays). `Actor::current()` REFUSES to guess (`LogicException`) when nobody is logged in or no `AuthService` is wired: a CLI script, the import (P5b) and the harness pass the actor explicitly (`new LedgerService($em, 'import:wdv')`). A posting without a named author is what the change log exists to prevent.
- **`ManualEntryService`** (owner, 2026-09-22): `create(PostingRequest $manual): EntryRef` (a manual request through `LedgerService::post()` in a unit of work opened HERE), `update(int $entryId, int $expectedVersion, PostingRequest $new)`, `delete(int $entryId, int $expectedVersion)`. Each method OWNS its unit of work and refuses to run inside an open one (`LogicException`, the `FiscalYearService::open()` model) — a caller that wants many manual entries in one transaction (the import) uses `LedgerService::post()` with `PostingRequest::manual()` directly. Rules for edit and delete (`EntryNotEditableException`, reasons): a GENERATED entry → `generated` (in the domain — `JournalEntry::amend()` refuses as well); period `open` → allowed; `vat-settled` → allowed only if NEITHER the old NOR the new version carries a tax line (`period-vat-settled`; the filed return summed the tax lines); `closed` → `period-closed`; an edit whose new date lies in ANOTHER fiscal year → `fiscal-year-changed` (the number belongs to the year — delete and re-create). Both the OLD period (where the entry is) and the NEW period (where the date moves) are checked. The new version arrives as a `PostingRequest` — structurally valid by construction. Inside `run()`: the entry is RE-READ with its header row locked (`JournalEntryRepository::lockForUpdate()`, `SELECT … FOR UPDATE`) and its version compared with `$expectedVersion` — gone or another version → `EntryConflictException`; then every database rule (`PostingRules`: year, period, accounts, tax codes) runs on the FRESH entity; only then is it touched (ADR-039 decision 9, DOCTRINE-TX-007): `EntryChange(update, before, after)` + `amend()` (date, text, lines replaced — the old lines leave the collection, orphan removal deletes them at flush — `changed_by` / `changed_at` stamped), or `EntryChange(delete, before, null)` + `remove()`. A delete leaves a GAP: the number is not reused (verified I22–I25).
- **Concurrency of manual edits** (review 2026-09-22 H1/M1–M3, decided: optimistic locking): `journal_entry.version` (`#[ORM\Version]`) travels as a hidden field of the edit form and the delete modal; the service takes id + expected version, never a pre-loaded entity. Two guards, one exception: the version check on the locked re-read catches a change that happened BEFORE the write (a second editor waits on the row lock, then reads the committed state — version bumped or row gone), and Doctrine's `OptimisticLockException` at flush (mapped to the same `EntryConflictException`) catches the rest. A manual edit ALWAYS bumps the version, also when only the lines change, because `amend()` stamps `changed_at` and the header row is updated (verified I13b). The screen answers a conflict with «Die Buchung wurde inzwischen geändert oder gelöscht — bitte neu laden» and a redirect — never a 500. Verified: two parallel processes editing one entry → one `ok`, one `conflict`, two lines not four, version 2, one change row (I27/I28); a stale delete after a delete and a stale edit after a delete → `EntryConflictException`, one change row (I23b/I23c).
- **The screens**: the fragment pattern (ADR-018) like the accounts and the fiscal years — `Ui/JournalControllerTrait` + `JournalLayout::config()`, templates in `res/view/templates/Backend/JournalController/`, the host `module-backend` `Finance/JournalController`, hc1 («Buchung erfassen», a LINK to the entry page) and hc2 (the fiscal-year switcher, one link per year — the `.be-lang-switch` anatomy) in the backend namespace. URLs `/backend/finance/journal/list?year={code}` (the year containing today by default, else the latest; bounded by `journalListLimit`, «n von m angezeigt»; a second section lists the deleted numbers with who and when, from the change log), `detail?id=` (header, lines with tax data, reversal link in both directions — «Storno von» names the reversed entry's OWN year —, the change log with before/after as disclosure rows — checkbox, no JavaScript), `add?year=` and `edit?id=` (PAGES with a plain `<form method="post">`, `#[Csrf]` + `csrf_token`; an edit also checks the entity token `journalEntry` and carries `version`; the edit page of a NON-editable entry — generated, or period closed — shows the same refusal the detail view shows and goes back there), `confirm-delete?id=` (modal, `data-fetch-get`, carries `version`) and `delete` (`#[Fetch, HttpMethod('POST')]`, entity token; success redirects to the journal through the envelope). The pages other than the list swap the pinned body section (`removeSection('main')` + `addPartials()`) — the layout config pins `listAction`. NO reverse button: the module that posted an entry reverses it (ADR-042 decision 7). Generated entries are shown only. The base currency the form parses amounts in is read in ONE helper (`JournalControllerTrait::journalCurrency()`, `systemConfig → baseCurrency`, the same key the Doctrine bootstrap hands `MoneyType`) — `MoneyType` exposes no getter, and asking it would tie the form to the driver having booted first.
- **The manual-entry form** (`Ui/ManualEntryForm`, no JavaScript — Rule 7): date, text, n rows (account NUMBER typed with a shared `<datalist>` of the postable active accounts, text, debit OR credit — `100`, `100.50`, `100,50`, `1'000.00` accepted, `Money::fromDecimal()` — and an optional tax code from a `<select>`). Four rows to start; «Weitere Zeilen» is a second submit button (`op=more`) the server answers with three more rows; the balance (Σ Soll, Σ Haben, Differenz) and the computed VAT per line are shown after EVERY submit. VAT (ADR-041 decision 7, net method): the bookkeeper puts the code on the NET line only; the form resolves the rate for the ENTRY DATE (`VatRates::resolve()` — a manual entry's date is its service date), base = the line's amount, tax = base × rate rounded once (`Money::multiplyByRatio()`), and shows «MWST VM 8.1 %: 8.10 auf 100.00» so the bookkeeper enters the tax-account line (1170 / 2200) by hand like any other line; the balance check catches a wrong one. **Sign convention** (lives in the form, not in the ledger): base and amount positive when the line stands on the code's NATURAL side — credit for an output code, debit for an input code (`TaxCategory` `input-material` / `input-other`) — negative on the opposite side, so a manual revenue reduction posts a negative base and the return sums correctly. Amounts are shown through `Ui/AmountFormat` (Swiss apostrophe grouping, string work on `Money::toDecimal()`, no float).
- **`journalListLimit`** (financialConfig, optional, positive int, default 200 — `LedgerService::listLimit()`, the `ContactService::listLimit()` model): not set in the package config on purpose (Rule 2); a project sets it in its override copy (BOOT-CONFIG-001 applies).
- **Migration** `Version20260922091711` (`res/migrations`): generated with `z77-db diff` against a database at the part-1 migration, reviewed — `utf8mb4_unicode_ci`, `ENGINE = InnoDB` spelled out, the Doctrine-named indexes and FKs kept so `diff` stays clean, expand only, no DROP. The `version` column of the review fix was folded into it BEFORE it was ever committed (the module-contact precedent), so part 2 ships one migration. `tests/module-financial.php` A applies both migrations through the `z77-db` application and proves `diff` reports «No changes» afterwards (money, version and TEXT snapshot columns included).
- **Where the package is required**: the monorepo ROOT `composer.json` only (so `vendor/` carries it for the harness); NOT `skeleton/composer.json` — a project requires it when it needs it, like `module-contact`. No `RUNTIME=` paths therefore. The module has no routes and no view area (`financialConfig.inc.php` carries no `defaultGroup`).
- **The navigation entries are NOT in the kernel seed** (a host entry that fatals without the module would be wrong on a fresh install): a project adds «Kontenplan» → `/backend/finance/account/list`, «Geschäftsjahre» → `/backend/finance/fiscal-year/list` and «Journal» → `/backend/finance/journal/list` in the backend, like the tax codes and contacts.

## rules

- When writing an `Account` from any code path (backend, import, a migration of a wdv chart) → MUST go through `AccountService` (`save()`, `update()`, `setActive()`); MUST NOT `persist()` an account directly — the validator lives there
- When changing an EXISTING (managed) account → MUST hand the cleaned values to `AccountService::update($account, $values)`, the parent as the entity under `parent`; MUST NOT call `mapFromArray()` or a setter on the loaded account first (ADR-039 decision 9)
- When an account is no longer needed → MUST deactivate it; MUST NOT delete the row or add a delete action — journal lines reference it
- When an account needs a different number → MUST create a new account and deactivate the old one; MUST NOT change `number` on an existing account (refused with `AccountNumberChangedException`)
- When grouping accounts → MUST put a postable account under a GROUP (`postable = false`); MUST NOT make an account with children postable or give a postable account children
- When offering the KMU chart → MUST call `AccountService::adoptKmuChart()` and offer the button only while `AccountRepository::isEmpty()`; MUST NOT seed the chart in the installer or a migration (owner, 2026-09-22 — a migrated chart must not get it forced on it)
- When editing `res/charts/kmu.json` → MUST keep UTF-8 without BOM, parents before children, five-type values and the Sterchi numbers, and MUST run `php tests/module-financial.php` (B-section checks the structure); MUST NOT round-trip it through Windows PowerShell (DATA-JSON-001)
- When a fiscal year is opened (backend, import, test) → MUST go through `FiscalYearService::open()` OUTSIDE any open unit of work (it refuses a nested call) and MUST treat a leftover `journal-entry.{code}` range as a conflict to resolve, not to reuse (refused on `code`); MUST NOT persist a `FiscalYear` or a `Period` directly or create `journal-entry.{code}` elsewhere — the year, its periods and its range are one unit of work
- When code needs the name of a year's journal-entry range → MUST use `FiscalYear::journalEntryRange()`; MUST NOT compose `'journal-entry.' . …` inline
- When choosing a fiscal-year code → MUST keep it lower-case kebab of at most 16 characters (it is the dotted segment of a range name); MUST NOT reuse a code or rely on case
- When a period's state has to change (VAT return, close — P5) → MUST add the transition to this module with its own rules (one way: `open` → `vat-settled` → `closed`, ADR-042 decision 10); MUST NOT write `fiscal_period.state` any other way
- When any module or script writes into the journal (an invoice, a payment, an import, a job) → MUST build a `PostingRequest::generated()` with an opaque origin and an idempotency key and call `LedgerService::post()` INSIDE its own `getTransaction(JournalEntry::class)->run()`, together with the writes that belong to the posting; MUST NOT `persist()` a `JournalEntry` or a `JournalLine` directly, MUST NOT draw from `journal-entry.{code}` itself, and MUST NOT open the unit of work inside financial (ADR-040 decisions 2 and 7, ADR-042 decision 6)
- When building an idempotency key → MUST derive it from the SOURCE (`invoice:{id}:final`, `payment:{id}`), stable across retries, and MUST repeat the identical content with it; MUST NOT reuse a key for different content — the ledger refuses it with `IdempotencyConflictException` instead of answering with the old entry
- When a posting has VAT → MUST put `taxCode`, `taxRate` (the rate that applied, from the document's snapshot), `taxBase` and `taxAmount` on the NET line only, signed as the document means them (a credit note negative); MUST NOT put tax data on the tax-account line or the counter line, and MUST NOT recompute the rate from the tables at posting time (ADR-041 decisions 6 and 7)
- When a generated entry is wrong → MUST call `LedgerService::reverse($ref, $date, $reason)` from the module that owns the source, inside its unit of work, with a reason of at most 255 characters (it becomes the reversal's text), dated in an OPEN period — the next fiscal year included; MUST NOT edit, delete or re-post it, and MUST NOT reverse a reversal or reverse twice (refused; the schema refuses the second reversal too)
- When a module's unit of work around `post()` / `reverse()` fails at commit with a `UniqueConstraintViolationException` on `uniq_journal_entry_idempotency` or `uniq_journal_entry_reversal_of` (a parallel poster with the same key, the same key twice in one unit of work, a parallel reversal) → MUST let the whole unit of work fail and propagate; MUST NOT catch it and retry inside the unit of work (ADR-039 decision 10) — no number was consumed; a retry is a new unit of work, and the same key then returns the existing entry. This binds the P3 debtor `AccountingGateway` adapter
- When a caller has no session identity (CLI script, import, harness) → MUST pass the actor's name to `LedgerService` / `ManualEntryService` explicitly; MUST NOT rely on `Actor::current()` there — it refuses rather than guesses
- When a MANUAL entry is created, changed or deleted (backend, script) → MUST go through `ManualEntryService::create()` / `update($entryId, $expectedVersion, $newRequest)` / `delete($entryId, $expectedVersion)` OUTSIDE any open unit of work (they own theirs, re-read and lock the entry, and log the change); MUST NOT call `JournalEntry::amend()`, `persist()` or `remove()` on an entry from anywhere else — the change log would miss the change
- When changing an EXISTING manual entry → MUST hand the NEW version as a `PostingRequest::manual()` together with the id and the VERSION the screen was rendered from (`JournalEntry::getVersion()`, the hidden `version` field); MUST NOT mutate a loaded entry or its lines (ADR-039 decision 9) and MUST NOT pass the version stored NOW instead of the one seen — that would defeat the lock
- When a screen or script receives `EntryConflictException` → MUST tell the user the entry was changed or deleted in the meantime and reload (the detail page or the list); MUST NOT retry with the current version automatically — the other writer's change has to be seen first
- When code checks whether a period accepts a write → MUST ask `PostingRules::assertPeriodAccepts()` (posting) or let `ManualEntryService` decide (edit/delete: old AND new period, tax line in old OR new version); MUST NOT re-implement the `open` / `vat-settled` / `closed` matrix elsewhere
- When a manual edit touches a line on an account that was deactivated since → MUST leave that line IDENTICAL (account, amounts, tax data, text) to keep it, or move it to an active account; MUST NOT expect a changed amount on an inactive account to pass (`account-inactive`)
- When a Doctrine entity of this module was loaded BEFORE a unit of work that rolled back → MUST re-read it through a repository before using it in a write; MUST NOT hand the detached object to a service (DOCTRINE-TX-004). The manual-entry services no longer take entities, so the UI path cannot run into this; a script that keeps its own objects across a failed unit of work still can
- When offering tax codes for a NEW manual line → MUST offer active codes only (`ManualEntryForm::selectableCodes()`); on an edit → MUST additionally allow the codes the entry already carries; MUST NOT let a deactivated code be newly chosen (ADR-043 decision 19)
- When showing an amount on a financial screen → MUST format it through `Ui/AmountFormat::of()`; MUST NOT cast a `Money` to float or call `number_format()` on it
- When the journal screen needs a list query → MUST add it to `JournalEntryRepository` (ids by SQL, hydration by a DQL fetch-join over lines and accounts, `latestForYear()` is the model) marked Doctrine-only; MUST NOT hydrate every entry of a year or let the template touch a lazy line collection per row
- When adding a column or an entity to this module → MUST run `php vendor/bin/z77-db diff --namespace="Z77\Module\Financial\Migrations"` and commit the reviewed migration with the entity, expand/contract; MUST NOT change `Version20260922071232` or `Version20260922091711` once an installation may have applied them
- When mounting the screens elsewhere → MUST `use AccountControllerTrait` / `FiscalYearControllerTrait` / `JournalControllerTrait`, delegate the layout config to `AccountLayout::config()` / `FiscalYearLayout::config()` / `JournalLayout::config()`, and override `accountListBase()` / `fiscalYearListBase()` / `journalListBase()` to the mount's URL root
- When adding a method to this package → MUST have a production caller in the same change (CLAUDE.md «no just-in-case»); `accountExists()` arrives with the first configuration consumer (see pending)

## known issues

- **FIN-NAV-001** — don't expect «Kontenplan» / «Geschäftsjahre» / «Journal» entries in the navigation after install: the kernel seed carries none (like CONTACT-NAV-001). The project adds them under the «Finanzen» section next to «MWST-Codes».
- **FIN-CHART-001** — don't assume the KMU chart is the full Sterchi chart: it is the classes, main groups, groups and the COMMON postable accounts (196 rows). An installation adds what its business needs (e.g. rounding accounts, plan §5.1 / §6.1) through the backend.
- **FIN-CHART-002** — don't assume the chart fits a sole proprietorship out of the box: class 28 is the variant for legal entities («Aktien-, Stamm-, Anteilschein- oder Stiftungskapital», reserves). Decided (owner, 2026-09-22): legal-entity variant only, no second chart file — a Personenunternehmen adds its equity accounts (Kapital, Privat) by hand in the backend after the adoption.
- **FIN-FY-001** — don't assume the proposed code is always free: two years in the same calendar year with the same shape (a short year 1.1.–31.3.2026 followed by 1.4.–31.12.2026) both propose `2026`; the second is refused on `code` and the user types another one (e.g. `2026-b`).
- **FIN-FY-002** — don't assume a fiscal year can be corrected after opening: there is no edit and no delete of a year. A year opened with wrong dates on an installation is removed by hand in the database (year, periods, `number_range` row) while nothing is posted yet; a guarded correction path is not built (owner question open).
- **FIN-TYPE-001** — don't assume `type` and `postable` are locked once journal lines exist: part 2 posts against an account but nothing refuses a type change or a postable account turned into a group afterwards (the validator only refuses a group WITH children becoming postable). Owner question open (see pending).
- **FIN-IDEM-001** — don't assume the idempotency check sees a posting of the SAME unit of work: `findOneBy(['idempotencyKey' => …])` queries the database, and an entry `persist()`ed but not yet flushed is invisible to it. Two `post()` calls with the same key inside ONE `run()` both draw a number and the caller's commit fails on `uniq_journal_entry_idempotency` — loud, rolled back, no number consumed. Same for two parallel requests with the same key: the second commit fails on the index. A caller posts one key once per unit of work.
- **FIN-IDEM-002** — don't assume the idempotency comparison ignores presentation: the `text` and the line `text`s are part of the content. A module that rebuilds a posting text differently on a retry (a date formatted by locale, a changed template) gets `IdempotencyConflictException`; build the text from the source deterministically.
- **FIN-TX-001** — narrowed 2026-09-22 (review fix): the manual-entry services take id + version and re-read the entry inside their own unit of work, so the UI path never hands a detached entity to a write any more. What remains: don't hold a loaded `JournalEntry` across a unit of work that rolled back (also a refused NESTED `create()` / `update()` / `delete()`, which throws `LogicException` from inside `run()` and replaces the EntityManager) and then READ it for display only — that works; writing through it does not (DOCTRINE-TX-004). A script that keeps its own objects re-reads them.
- **FIN-LOCK-001** — don't assume a stale delete is caught by Doctrine's optimistic lock: Doctrine checks the version on UPDATE, not on DELETE. The delete path is safe because `ManualEntryService::delete()` re-reads the row under a lock (`lockForUpdate()`) and compares the version itself before `remove()` — a version check on the service, not on the statement. Do not bypass the service to delete an entry.
- **FIN-LOCK-002** — don't expect the conflict message to name what changed: `EntryConflictException` says the entry is gone or at another version; the user reloads and sees the current state and the change log. No merge, no diff — a manual entry is small, redoing the edit is the correction.
- **FIN-UI-001** — don't expect the manual form to compute the tax-account line: it computes and SHOWS the VAT of a taxed net line («MWST VM 8.1 %: 8.10 auf 100.00»); the bookkeeper enters the 1170 / 2200 line by hand, and the balance check refuses an entry that does not add up. Deliberate (no JavaScript, one write path — the ledger stores what it is given), not a gap.
- **FIN-UI-002** — don't expect the journal list to show every entry of a year: it stops at `journalListLimit` rows (default 200, newest first) and says «n von m angezeigt». No paging and no search yet; the account statement and the journal export of part 3 are where a full year is read.
- **FIN-UI-003** — don't look for a reverse button in the backend: reversal is `LedgerService::reverse()`, called by the module that posted the entry (ADR-042 decision 7). A generated entry a bookkeeper wants gone is corrected by that module — or, until debtor exists (P3), not at all through the UI.
