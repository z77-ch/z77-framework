## mental model

Site statistics counted **server-side in the framework** — no third-party service, no analytics cookie, therefore no consent banner, and an ad blocker cannot remove the count (owner decision 2026-09-23, [web-stats-bauplan.md](../03-development/web-stats-bauplan.md)). One JSONL line per counted request (`logs/stats/stats-YYYY-MM-DD.jsonl`, the `FormLog` pattern, in a directory of its own that the backup leaves out), written by `StatsRecorder` from the Dispatcher **after the response went out**; a daily job (`stats-rollup`, `daily@04:40`) folds closed days into one aggregate per month (`data/framework/stats/YYYY-MM.json`) and deletes raw files after 7 days, aggregates after 24 months. What the client actually wants beyond page views — a form sent, a floor-plan PDF opened, an outbound application link — is an **event** the PROJECT declares; the framework knows none, and it counts every event per page as well. **Step 1 (recording + aggregation) is built and reviewed (2026-09-23); the report page, the token link and the mail (steps 1.3, 1.4, 2) are not.**

### recording — where the hook sits, and why that survives a cache HIT

- **`Dispatcher::execute()` → `$response->send()` → `countVisit()`**. The front controller `index.php` is a frozen OPcache trampoline («do not add logic here»), so the plan's «called from the front controller» is the Dispatcher the trampoline hands over to. The hook sits **behind `send()` in `execute()`**, not inside `resolveResponse()`: every branch — a fresh render, a page-cache HIT (`PageCache::get()` → `HtmlResponse::fromCache`), a 304 (`HtmlResponse::notModified`) — passes through that one `send()`, so a HIT is counted like a rendered page and the counter never sits in the render path (the one trap of the feature, acceptance 1; `tests/web-stats.php` pins the position by reading the source). A stateless route (/api) returns before it: no session, no page, nothing to count.
- **Never throws.** `countVisit()` is fenced, `observe()` / `event()` / `record()` are fenced again, every helper returns null or false on failure (`StatsSalt`, `CountryLookup`, `dir()`, `beaconAllowed()`); the response is already sent when the recorder runs, so nothing it does can reach the visitor (acceptance 6, verified in a real SAPI with a FILE named `logs`).
- **What counts** (`StatsRecorder::observe()`): a GET, in Page mode, to a module whose config says `'public' => true` (frontend, member — not the backend), answered with an `HtmlResponse` (a redirect, a JSON answer, a 204, a file are not page views), from a session **below** `AuthRole::EDITOR` (an editor or admin browsing the site is never counted — the same threshold as the page-cache bypass, ADR-045), from a user agent that is not a bot (`StatsClassifier::BOT_PATTERN`, an EMPTY agent is a bot), and whose document does not carry `data-stats="off"` within its first 4 KB (the `<html>` / `<body>` tag — a site marks a page off in its template, and because the check reads the response body it holds on a cache HIT too).
- **Assets never reach PHP** (Apache serves `public/`; a path with a `.` 404s at routing). A `/media` file delivered through PHP is a Fetch-mode request or a non-HTML response and is not a page view either — a document opened is an EVENT the project declares.
- **404 is not counted** (deviation from the plan's «2xx/3xx/404 are interesting», decided while building): a routing 404 never reaches the Dispatcher, and the ones that do are mostly probes that would pollute the page tally. A 304 (browser revalidation with `If-None-Match`) IS a visit and is counted with status 304.
- **Where the lines live** (owner decision E2, 2026-09-23): `logs/stats/`, a directory of its own, created by the recorder on first use — with the installer's deny `.htaccess` written into it (and into `logs/` when that one has none: the installer seeds deny files only into directories that exist at install time, INST-DENY-001, and this one is born at runtime). `BackupService::FIXED_EXCLUDES` leaves `logs/stats` out of every full backup **in code, unconditionally** — not through the seed-once `fullExcludes` config, which never reaches an existing installation (BACKUP-LIB-001). The raw lines carry a visitor key and live seven days; an archive that kept them for months would break that promise silently. `logs/` itself stays in the backup: the form log is a record. Files written before 2026-09-23 lie directly in `logs/` — see STATS-008 for the transition.

### the line — nine fields, nothing that names a person

| Field | Value |
|---|---|
| `at` | ISO-8601, server clock, application timezone |
| `path` | canonical path — language prefix stripped, the alias path after an alias hit (`/kontakt` for `/kontakt` and `/fr/contact`); query dropped except `utm_source` / `utm_medium` / `utm_campaign` (`StatsClassifier::CAMPAIGN_KEYS`, sorted, values slugged and cut at 60; a value with an `@` becomes `unknown`). An event line carries the page the browser reported, put on the SAME route (below), so page view and event of one page share one key |
| `status` | the status sent (200, 304); an event line carries the beacon's 204 |
| `lang` | `Request::getLanguage()` — for an event line the beacon request's language, not the page's |
| `visitor` | `sha256(ip + '|' + ua + '|' + daily salt)`, first 16 hex; `null` when the address or the salt is missing |
| `source` | `direct`, `internal` (own host), `campaign:{utm_source}`, `{search|social|referral}:{host}`, or bare `referral` when the referring host does not look like a hostname — the referring HOST, lower-case, `www.` and port stripped, validated as a hostname (`StatsClassifier::isHostname()`: RFC 1123 labels, no IP literal), never the path (see below) |
| `device` | `{mobile|tablet|desktop}/{browser family}` — e.g. `mobile/safari`; the rollup splits it |
| `country` | `CountryLookup::of(REMOTE_ADDR)` at request time, `null` when unknown or no database |
| `event` | `page` for a page view, else the declared event name |

- **No IP, no user agent, no referring URL, no cookie, no session id** — the three inputs are consumed at request time (`StatsHit` exists for the length of `record()`) and what is not classified now cannot be derived later. That is the design, and the privacy paragraph below promises exactly this list. **Do not widen the record without changing that text first.**
- **The salt** (`StatsSalt`, `var/lib/stats/salt`, content `YYYY-MM-DD <64 hex>`): one random value per calendar day, rotated by the first request of a new day (temp file + rename, re-read after the rename so two rotating requests agree), yesterday's value overwritten. `var/lib` because it may be deleted at any time (one day's visitors counted twice, nothing else), must be the SAME on both doors of a release layout and survive a switch within the day — the shared branch of `var/`, ADR-035; not `data/` (not a record), not `logs/` (would ride into the backup beside the lines it protects). The salt is never logged or shown. Consequence: two requests of one visitor on one day are one key; the next day the same person is a different key and cannot be matched to the day before (acceptance 2). An unwritable directory → `visitor: null`, the line is still written.
- **The visitor key is client-influenced — deliberately** (owner decision E3, 2026-09-23): the user agent is part of it so that an office behind one NAT address is not one visitor. The price: a client rotating its agent is a new key per request, and every per-key cap in the rollup is blind to it (probe: 1000 requests from one address = 1000 «visitors», 0 capped). Page-view floods cost the attacker real requests, which is brake enough; the beacon — cheap to call, a claim rather than an observation — gets a brake per ADDRESS (below), and the rollup a ceiling on the keys it keeps in memory.
- **The referring host is kept by name** (orchestrator decision 2026-09-23): `search:google.ch`, `social:linkedin.com`, `referral:immoscout24.ch` — the host only, never the referring URL (a search term or a token in a referer's query never reaches the line). It is the one thing in the statistic that names an outside party, and the aggregate keeps it for 24 months — the privacy text has to say so (below). A campaign (`utm_source`) wins over the referer and keeps no host. What parses as a host but is none (`a"b_c.example`, `192.0.2.7`) is a `referral` without a host (review B9).
- **Campaign values are free text from a link** and stay in the aggregate for 24 months, in `campaigns` and in `sources`. The one shape of personal data the code can tell apart — an e-mail address (`@`) — becomes `unknown` (review B8); an opaque recipient id (`utm_source=r-48213`) cannot be told from a campaign name, so **never a recipient identifier in `utm_*`** is a project rule (STATS-009). Newsletter tools that personalise links must be configured accordingly.

### events — the project declares, the framework counts

- **The declaration is a map `event name → German label`**, read from two additive sources per module — the `statsEvents` key of a module config, and every extension file `App/Config/statsEventsConfig.inc.php` under any of the module's source paths (`ModuleManager::getConfigExtensions()`, the `doctrineEntitiesConfig` pattern). A project therefore writes ONE small file and copies no module config — this is deliberately the additive path around BOOT-CONFIG-001 ([`bootstrap.md`](bootstrap.md)): `override/z77/module/frontend/src/App/Config/statsEventsConfig.inc.php` returning `['form-submitted' => 'Kontaktformular abgeschickt', 'floorplan-pdf' => 'Grundriss-PDF geöffnet', 'application-link' => 'Bewerbungslink geklickt']`. The framework packages ship no declaration; a project without the file counts page views only and configures nothing.
- **The list IS the security boundary.** `StatsEvents::isDeclared()` is asked in the controller — a name not in the map is dropped, whatever else the request says. A name is `[a-z0-9-]`, 1–40 characters; `page` is reserved. The framework stores and counts the NAME; the label is for the report (step 1.3, which reads `StatsEvents::declared()` — there is no lookup helper until then, «no just-in-case»). A malformed declaration (a list, an invalid name, an empty label, two sources disagreeing on a label) THROWS at the first read — fail-fast like a job declared twice — so the endpoint answers 500 into the error log instead of dropping every event silently.
- **The endpoint** `GET /frontend/main/stats/event?event={name}&path={path}` (`StatsController::eventAction`, `#[HttpMethod('GET')]`, answers 204 always — a beacon has nothing to learn from the answer, and an undeclared name must not be distinguishable). GET, not POST, because `navigator.sendBeacon()` cannot carry headers and every Fetch-mode POST dies at the AccessGuard's global CSRF check — right for a form, pointless for a counter that changes no state anyone can read back. Both parameters are type-checked, never cast (`event[]=x` arrives as an array — a cast would be `"Array"` plus an E_WARNING that DEBUG prints into the 204, review B6). Editor/admin sessions and bots post no events.
- **The event path is put on the page view's route** (owner decision E4, 2026-09-23 — the client asks «on which page was the floor plan opened», so page view and event of one page must be ONE key): `StatsRecorder::cleanPath()` cuts query and fragment, decodes percent-encoding once (the Request decodes `REQUEST_URI` the same way), allows UTF-8 (`/über-uns` is a page — the old printable-ASCII rule dropped the whole event), refuses control characters and spaces, collapses double slashes, strips the trailing slash and cuts at `PATH_MAX` (200 characters); what is not a path at all (empty, not starting with `/`, `javascript:…`) becomes `/` — the event is a real claim, only the page is unknown. Then `canonicalPath()` strips a language prefix and resolves an alias URL through the same `AliasPathResolver` the Request uses (`/fr/contact` → `/kontakt`); a technical path keeps its spelling. Without the routing services (the harness) the cleaned path stands.
- **The brake** (owner decision E3): `StatsRecorder::beaconAllowed()` counts beacon lines per address (IPv6 per /64) and hour with the shared `FileThrottle` under `var/lib/throttle/stats` — `BEACON_LIMIT_PER_HOUR` (300), the same mechanism as the member flows and the API rate limit, no second one. Beyond the limit the answer is still 204 and nothing is written. It never throws and fails OPEN: an unusable `var/lib` costs the brake, not the count — and it is the tree the salt lives in, so those lines carry no key, fall into the rollup's `-` bucket and meet `EVENT_DAY_CAP` there.
- **The project sends the beacon itself**: `fetch('/frontend/main/stats/event?event=floorplan-pdf&path=' + encodeURIComponent(decodeURIComponent(location.pathname)), {keepalive: true, cache: 'no-store'})` — `keepalive` survives the page unloading on an outbound click, `no-store` because a 204 to a GET is heuristically cacheable, and `location.pathname` is ALREADY percent-encoded, so it is decoded before it is encoded once (a plain `encodeURIComponent(location.pathname)` arrives double-encoded as `/%C3%BCber-uns`; the server's single decode still collapses it, the SAPI check pins both). The framework ships no script for it (Rule 7, and the events are the project's).

### aggregation — `stats-rollup`

- **`StatsRollup::run()`** (pure over three directories — the raw one, the aggregate one, and the legacy `logs/` it still reads; `StatsRollupJob` is the cron wrapper): every CLOSED day (day < today, application timezone — today's file is still being appended) that is not yet in its month's `days_done` is streamed line by line into `data/framework/stats/YYYY-MM.json`; the month is written temp-file + rename; then raw files older than `RAW_RETENTION_DAYS` (7) are deleted — **only when their month was saved**, never for a blocked month or a failed day — and aggregates whose month name is older than or equal to `AGGREGATE_RETENTION_MONTHS` (24) back are deleted (the NAME decides, never mtime — the GEOIP-002 lesson). At any time at most 24 month files exist, the running one included: the file of month M goes with the first run in month M+24. A rerun folds nothing twice (acceptance 5).
- **It fails loudly, never quietly** (review B5, 2026-09-23). A month file that exists but cannot be read or does not parse as that month BLOCKS the month: none of its days is folded, none of its raw files is deleted, the file is left in place for a hand fix, the job FAILS and names it (before: the torn file was loaded as «empty», overwritten, and 5000 views became 1 with «done»). A day whose raw file cannot be opened (a directory of that name, a permission) is reported in `failedDays`, stays out of `days_done`, is never swept, and fails the job (before: folded, then deleted seven days later). A day split across two directories (STATS-008) is folded in one pass or not at all.
- **The aggregate** carries `month`, `days_done`, `days` (per day: `views`, `visitors`, `visits`, `events`), `views`, `visitors`, `visits`, `capped`, and the tallies `pages` (path without the campaign query), `entries` (entry page per visit, same shape and cap as `pages`), `sources` (the CLASS: direct / internal / search / social / referral / campaign — `internal` is navigation within the site, kept as its own class in the data because merging it into «direkt» at write time would lose the distinction for good; the report groups it away), `referrers` (the referring HOST by name — the `MAX_REFERRERS_PER_MONTH` (50) most frequent, the rest summed into `other` (`REST_KEY`, an English data key like every key in the file; the report labels it), so a link-spam wave cannot blow the file up; a search engine's host is in it too, `sources` is what the report groups by), `devices`, `browsers`, `countries` (`??` for unknown), `languages`, `status`, `campaigns` (the utm query, apart from the hosts), `events` (declared names), and **`event_pages`** — `event name → (path → count)`, the answer to «on which page» (owner decision E4), each event's path list capped at `MAX_PATHS_PER_EVENT` (50) + `other` at save time and at `MAX_KEYS_PER_TALLY` while folding, exactly the referrer cap's character. Every tally is sorted by count. A malformed line is skipped.
- **Visits and entry pages** (orchestrator decision 2026-09-23, owner request «which page does a visit start on») are DERIVED in the rollup from the raw lines — no event, no change to the raw line, no new privacy fact: a visit is the consecutive page views of one visitor key with no gap longer than `VISIT_GAP_SECONDS` (30 minutes; exactly 30 continues, more starts anew), its entry page is the path of its first page view (`event = page` only — a beacon event neither starts nor extends a visit). A line without a visitor key counts no visit and no entry. **A visit spanning midnight counts as two visits with two entries**: the day file is the unit and the rollup carries no state across files, which slightly overstates visits and the entry list — accepted.
- **«Visitors per month» is the SUM of the daily distinct counts**, not a distinct count over the month — the visitor key is salted per day, so the same person on two days is two keys, by design. A monthly unique does not exist and the report must say «Besucher (Tagessumme)»; that is the price of «nobody can be followed across days», paid knowingly.
- **Two abuse caps and one ceiling** (orchestrator decision 2026-09-23, owner decision E3): `PAGE_VIEW_DAY_CAP` = 100 page views per visitor key and day, `EVENT_DAY_CAP` = 20 beacon events per visitor key, day AND event name — a page view is something the server saw, a beacon is something a client claims, so the claim is bounded tighter. Lines beyond a cap are dropped and tallied under `capped`. A line without a key falls into the bucket `-`, so a broken salt is not an open door either. Applied in the rollup, not at request time, because the recorder must stay a blind append (no read, no lock beyond the append); both numbers are above any real visitor's day. `MAX_KEYS_PER_DAY` (20 000) bounds the fold's MEMORY the same way: the per-key tables (`$perKey`, `$lastSeen`, the visitor set) grew with every new key, and a client rotating its agent makes every line a new key — a flood day would have grown them until the job died and the month was never saved. Beyond the ceiling a line with a key not yet seen is dropped and tallied under `capped`, the day lands in the result's `overflow`, and the job note STARTS with the warning («⚠️ visitor table full …») — saved, but never silent.
- **Registered in `backendConfig` as `stats-rollup`, `AuthRole::CRON_JOB`, WITH `defaultSchedule` `daily@04:40`** (owner decision E1, 2026-09-23 — [`jobs.md`](jobs.md) JOBS-SCHED-001). The job deletes the installation's data, which normally means «no schedule, the operator switches it on» (ADR-031 decision 4); here the deletion IS the privacy promise («Rohdaten werden nach 7 Tagen gelöscht»), and raw lines with visitor keys piling up for months until someone remembers the switch is the worse risk. The same kind of exception as `geoip-update` (a duty, not a convenience). The seeded record belongs to the operator afterwards: switching it off in Backend → Service → Jobs survives every update. 04:40 — after the day's last visitor, before the report mail of step 2.
- **Why `data/framework/stats/` and not the plan's `data/stats/`**: every framework-owned data directory lives under `data/framework/` (`jobs`, `geoip`, `forms`, `auth`); a successor looking for framework data looks there. `data/` is shared across releases and inside the `data` and `full` backups, so a deploy or a rollback keeps the history.

### cost per request (measured, Windows dev box, PHP 8.5, `tests/web-stats.php`)

| Part | Cost |
|---|---|
| classification + hash + JSON | ~50 µs |
| salt read (one `file_get_contents`) | ~450 µs |
| append with `LOCK_EX` | ~1 ms (the lock itself ~150 µs; the rest is NTFS + Defender) |
| GeoIP: open `MmdbReader` + metadata | ~1.7 ms |
| GeoIP: lookup | ~3–4 ms (one `fseek`+`fread` per tree node — 128 for an IPv4 address inside the IPv6 tree) |
| beacon only: `FileThrottle` (one `fopen` + `flock`) | ~1 ms, paid per event, not per page view |

Total ~1 ms without a database, ~6–9 ms with one — on Windows, where every file syscall is expensive; Linux (cyon) is expected an order of magnitude lower. The recorder runs AFTER `send()`, so this delays the connection close, not the first byte. The GeoIP lookup is the existing layer's cost (`FormLog` pays it per submit); with the statistic it is paid per page view — see pending.

## privacy paragraph (German, generic — a project copies it into its privacy content)

What a project's privacy text must say the day this ships, field by field: what is counted, no cookie and no third party, the IP becomes a daily non-reversible key that IS stored in the raw line and is not reversible, every field of the raw line, the two retentions and that the raw lines stay out of backups, the aggregate keeps the NAMES of referring websites and the campaign marks, the evaluation is aggregate. The wording below is the framework's generic version; a project adapts it in its own content document (zihlundsee: `privacy.de.json` / `privacy.fr.json`, section `tracking`, step 3 of the plan) — the framework never edits a project's content. **One edit per installation**: the country clause stands in square brackets — keep the words and drop the brackets when the installation has a GeoLite database, drop the whole clause when it has none (STATS-004 — the text must not promise a column that is empty).

```text
Statistik. Diese Website erhebt anonyme Nutzungsstatistiken, um zu sehen, wie viele
Personen sie besuchen, über welche Wege sie zu uns gelangen, welche Inhalte genutzt
werden und welche Aktionen auf welcher Seite ausgelöst werden (Seitenaufrufe und
einzelne Aktionen wie das Absenden eines Formulars oder das Öffnen eines Dokuments).
Die Zählung erfolgt auf unserem eigenen Server, ohne Cookies und ohne Dienste
Dritter. Ihre IP-Adresse wird dabei nicht gespeichert: Aus ihr wird zusammen mit
der Browser-Kennung und einem täglich wechselnden Zufallswert ein Kurzschlüssel
gebildet, der weder auf Sie zurückgeführt noch mit einem Besuch an einem anderen
Tag verknüpft werden kann. Gespeichert werden pro Aufruf: Zeitpunkt, dieser
```

## rules

- When adding a field to the raw line or the aggregate → MUST first change the privacy paragraph above (and every installation's copy) and MUST NOT add anything that names or re-identifies a person: no address, no user agent, no referring URL, no cookie or session id, no free text from the request — the nine fields are the contract (`tests/web-stats.php` pins them)
- When counting a request → MUST go through `StatsRecorder::observe()` from `Dispatcher::execute()` AFTER `$response->send()`; MUST NOT call the recorder from a controller, a template or inside `resolveResponse()` — a cache HIT would then be missed, and a failure could reach the page
- When something in the recording path can fail (a directory, a file, a lookup, the throttle) → MUST return null / false and let the line go; MUST NOT throw, log the address, or write a debug line that carries the IP or the user agent — not even temporarily
- When placing the raw files → MUST keep them under `logs/stats` (`StatsRecorder::DIR`) and MUST keep `BackupService::FIXED_EXCLUDES` naming that directory; MUST NOT move them into `logs/` itself (in the backup) or route the exclusion through the seed-once `fullExcludes` config (never reaches an existing installation, BACKUP-LIB-001)
- When a project wants clicks counted that never pass PHP → MUST declare the names in `App/Config/statsEventsConfig.inc.php` (map name → German label, `[a-z0-9-]`, not `page`) under `override/` and send `GET /frontend/main/stats/event?event=…&path=…` with `encodeURIComponent(decodeURIComponent(location.pathname))`; MUST NOT add a framework-level event, a free-text parameter, an id or a cookie to the endpoint (the declared list is the whitelist), and MUST NOT canonicalise the path in the browser — the server puts it on the page view's route
- When touching the endpoint → MUST keep the brake (`StatsRecorder::beaconAllowed()`, the shared `FileThrottle` under `var/lib/throttle/stats`, per address and hour) in front of the write, MUST keep the answer 204 in every case, and MUST type-check the parameters; MUST NOT invent a second throttle mechanism or cast request input to string
- When a page must not be counted → MUST put `data-stats="off"` on its `<html>` or `<body>` tag (within the first 4 KB); MUST NOT special-case it in the recorder
- When a module must not be counted → MUST leave its config without `'public' => true` (the backend); MUST NOT list modules in the recorder
- When changing the visitor key → MUST keep the daily salt in `var/lib/stats` (shared across releases, disposable) and MUST NOT move it into `data/`, `logs/` or a release-local `var/cache` / `var/state` (a release switch would split every visitor, ADR-035); MUST keep the user agent in the key (an office behind one address is many visitors, owner decision E3) and MUST NOT rely on per-key caps alone against a flood — the brake per address and `MAX_KEYS_PER_DAY` are the counterweight
- When touching the rollup → MUST keep `days_done` as the idempotency record, MUST delete a raw file only after its month was saved and never for a blocked month or a failed day, MUST apply `PAGE_VIEW_DAY_CAP` per (visitor, day), `EVENT_DAY_CAP` per (visitor, day, event) and `MAX_KEYS_PER_DAY` per day, and MUST report every unreadable month file, unreadable day file and overflow in the result so `StatsRollupJob` fails or warns loudly; MUST NOT load an unreadable month as empty (it would be overwritten), mark an unopened day as done, or count a month's visitors as distinct over the month (the keys rotate daily — sum the days and say so)
- When deriving visits or entry pages → MUST compute them in the rollup from `event = page` lines with a visitor key and the `VISIT_GAP_SECONDS` rule; MUST NOT add a beacon event for an «entry» (a second count of what the page view records, disagreeing whenever the beacon is blocked or late) and MUST NOT carry visit state across day files
- When naming a bucket or a key in the aggregate → MUST use an English data key (`other`, `visits`, `entries`, `event_pages`); MUST NOT write a German label into the file — the report translates
- When keeping referring hosts → MUST store the host only (lower-case, no port, no path, `www.` stripped, validated by `StatsClassifier::isHostname()`) and cap the monthly list at `MAX_REFERRERS_PER_MONTH` with the rest in `REST_KEY`; MUST NOT store the referring URL, an IP literal or a string that is not a hostname, or let the host list grow unbounded
- When building campaign links for a site → MUST put campaign names only into `utm_source` / `utm_medium` / `utm_campaign`; MUST NOT put a recipient id, an address or any per-person token there — the value stays 24 months in the aggregate, and only an `@` is filtered mechanically (STATS-009)
- When scheduling `stats-rollup` → MUST keep the shipped `daily@04:40` in `backendConfig` (the deletion is the privacy promise — JOBS-SCHED-001, the reasoning in [`jobs.md`](jobs.md) and ADR-031's addendum); the operator MAY switch it off in Backend → Service → Jobs, and that survives updates; MUST NOT treat this as a licence to schedule other deleting jobs — the rule stands, this is the second of two exceptions
- When reading the aggregate (the report, step 1.3) → MUST read `data/framework/stats/YYYY-MM.json` and MUST NOT read the raw day files — they hold visitor keys and live seven days; the aggregate is the product

## known issues

- **STATS-001**: don't assume a 304 respects `data-stats="off"`. The mark is read from the response body, and a 304 has none — a revalidation of a page marked off is still counted. Small (only pages both marked off and page-cached with a client copy) and accepted for step 1; the fix would read the cache entry's head on the 304 path.
- **STATS-002**: don't assume «visitors» in the aggregate is a monthly unique — it is the sum of daily distinct keys (see mental model). A report label must say so. Likewise `visits` / `entries` count a visit across midnight twice (the day file is the unit).
- **STATS-003**: don't assume the beacon can be posted: `sendBeacon()` (POST) dies at the AccessGuard's global Fetch-POST CSRF check. The endpoint is GET; a project script uses `fetch(url, {keepalive: true, cache: 'no-store'})`.
- **STATS-004**: don't assume the country is resolved on an installation without the GeoLite database — `country` is `null` (`??` in the aggregate) and nothing says so except the empty column; the database is per-installation handwork ([`geoip.md`](geoip.md)). The privacy paragraph's country clause must be deleted on such an installation.
- **STATS-005**: don't assume an iPad is `tablet`: iPadOS 13+ announces itself as a Mac and lands in `desktop`. Coarse by design.
- **STATS-006**: don't assume a bot with a browser user agent is filtered — the bot rule is a token blocklist over the agent string. Headless browsers that spoof a real agent are counted; the abuse caps bound what one of them can do per KEY and day, the beacon brake and `MAX_KEYS_PER_DAY` what one ADDRESS or one flood day can do (the key itself is client-influenced, see the line).
- **STATS-007**: don't assume `stats-rollup` follows the «a deleting job ships no schedule» rule — it ships `daily@04:40` on purpose (owner decision E1, 2026-09-23, JOBS-SCHED-001 in [`jobs.md`](jobs.md)). Here the deletion is the privacy promise; the operator can still switch it off, and until the first run after an update the schedule is seeded once like every other (ADR-031 decision 4). An installation whose operator switched it off keeps raw lines indefinitely and breaks its own privacy text — that is the operator's decision, visible on Service → Jobs.
- **STATS-008**: don't assume every raw file lies in `logs/stats/`. Until 2026-09-23 the recorder wrote directly into `logs/`; an installation updated after that has the morning of the deploy day in `logs/stats-YYYY-MM-DD.jsonl` and the afternoon in `logs/stats/`. `StatsRollup` reads both directories (`StatsRecorder::LEGACY_DIR`), folds a split day as ONE day (legacy file first — its lines are older) and sweeps the legacy file with the same retention, so nothing is left behind and nothing is counted twice. Transition length: `RAW_RETENTION_DAYS` + 1 after the first rollup run on the updated installation — every legacy file is gone by then, and until then those files are inside the full backup (they are not under `logs/stats`). The legacy read can be removed once every installation has run the rollup after its update — see pending.
- **STATS-009**: don't assume a utm value is harmless. `utm_*` values are stored slugged and stay 24 months in `campaigns` and `sources`. An e-mail address becomes `unknown` (the `@`); an opaque recipient id (`utm_source=r-48213`), a customer number or a name cannot be told from a campaign name by code. The rule «never a recipient identifier in `utm_*`» is a project rule for whoever configures a newsletter tool — the framework cannot enforce it.
- **STATS-010**: don't assume a corrupt month file heals itself. A month file that does not parse blocks its month (no folding, no deletion) and fails the job EVERY day until someone fixes or removes the file by hand (`data/framework/stats/YYYY-MM.json` — a removed file starts the month empty from the raw files that are still there; days already swept are lost for that month). That daily failure is the design: silent overwrite was the alternative (review B5).
- **STATS-011**: don't assume `MAX_KEYS_PER_DAY` (20 000) is only ever a flood. A site with more than 20 000 distinct visitor keys on one day is undercounted from the 20 001st key on, with the warning in the job log. The framework is built for small sites; raising the ceiling costs ~600 bytes of memory per key in the rollup — decide per installation, not by default.
- **STATS-012**: don't assume every real event is counted. `BEACON_LIMIT_PER_HOUR` (300) is per address and hour — a large office behind one NAT address that opens more than 300 documents in an hour loses the rest for that hour (page views are not affected). And the brake fails OPEN when `var/lib` is unusable: then the salt is gone too, the lines carry no key and meet `EVENT_DAY_CAP` in the `-` bucket — bounded, but not by the brake.

Until then STATS-008 applies.
- **GeoIP cost per page view — measure on cyon, and that measurement is the GATE before step 1.3 (owner decision 2026-09-23, no optimisation now).** `MmdbReader` opens the file and walks the tree with one syscall per node on every request (~5 ms on Windows, expected far less on Linux); the hook runs after `send()`, so it delays the connection close, not the page. Options IF the server number says so: read the node bytes of a walk in one buffered read, or memoise the IPv4 start node and the metadata offsets in APCu keyed by the database's `build_epoch`.

- **Count a form submission server-side, not with a beacon** — make this a framework building block instead of leaving every project to rediscover it. zihlundsee wired it in the observer of `PublicFormHandler` (2026-09-23) rather than on the submit button, because only the server can tell a real submission from one a honeypot rejected; a beacon on the button counts the bot and the number becomes worthless to the owner. An opt-in observer in `Forms/` that records a declared event name would make it one line per project ([`forms.md`](forms.md)).
