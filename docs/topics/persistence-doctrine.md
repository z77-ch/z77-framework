## mental model

`z77/persistence-doctrine` is the second driver behind `UnifiedEntityManager` (ADR-039): Doctrine ORM 3 on DBAL 4 against MariaDB 10.6+, in its own Composer package because the kernel carries no dependencies (ADR-001). The namespace `Z77\Persistence\Doctrine` keeps the resolver's `Z77\Persistence\{Driver}\Bootstrap` convention, so nothing registers itself — the kernel's driver map names `doctrine`, and the first `#[Entity('doctrine')]` of a request boots the driver. A request that touches only file entities never loads the package; an installation without the package runs as before and fails with a message naming the package the moment a Doctrine entity is requested.

- **Connection**: `config/client/database.inc.php` — the one place (decision 4). Seed-once, not fed from `composer.json` (credentials are per installation, the ADR-030 argument). Keys `host`, `port`, `name`, `user`, `password`; empty `name` = no database. The `db` backup reads the same file; `backup.inc.php` keeps only its `dump` block (`mysqldump` binary, optional read-only backup user).
- **Charset / collation**: `utf8mb4` / `utf8mb4_unicode_ci` on every connection (`SET NAMES … COLLATE …` on connect — a bare charset would take the server's default collation) and as default table options for schema tooling and migrations (decision 18). Not configurable.
- **Entities**: a module lists its Doctrine entity classes under `doctrineEntities` in its module config; `ModuleManager::getDoctrineEntities()` collects the union exactly like `importEntities` (a non-existent class throws). The list feeds Doctrine's `AttributeDriver` through a `ClassNames` locator — no directory scanning (decision 5).
- **A project's own entity**: the module config is resolved first-match — an override config replaces the package config as a whole — so a project would have to copy the whole config just to add one class (Rule 2 violation). Instead it places an **extension file** `override/z77/module/{module}/src/App/Config/doctrineEntitiesConfig.inc.php` returning a plain list of classes. `getDoctrineEntities()` is the union of every module's `doctrineEntities` (from its possibly overridden config) and every `App/Config/doctrineEntitiesConfig.inc.php` found under ANY of the module's source paths (`ModuleManager::getConfigExtensions()` over `FileFinder::getAllSourceMatches()` — override and package alike), deduplicated. Still an explicit list, still no scanning; a bad class names the file. The same mechanism serves `importEntities` (`importEntitiesConfig.inc.php`) — one code path, `collectEntityClasses()` — and the open-work registry (`openWorkChecksConfig.inc.php`, see below). `getConfigExtensions($moduleKey, $configKey)` is the one file lookup: it returns every extension file's array keyed by an origin label naming key, module and file; the caller checks the shape inside.
- **Entity shape**: `#[Entity('doctrine')]` (z77, no path) plus Doctrine's `#[ORM\Entity]`, `#[ORM\Table]`, `#[ORM\Column]`. No `ArrayMappable`, no proxies: native lazy objects (PHP 8.4) are switched on, which is why the package requires PHP 8.4 while the kernel stays at 8.2.
- **Repositories**: `DoctrineEntityManager::getRepository()` returns the convention repository (`…\Repositories\XRepository extends DoctrineRepository`) or the generic `DoctrineRepository`; reads are Doctrine's `find` / `findAll` / `findBy` / `findOneBy` with field names as criteria keys, like the File driver. Report SQL runs on the protected `connection()` — the DBAL connection of the SAME EntityManager, so it sees uncommitted writes and uses the one set of credentials (decision 8). A read that must hydrate entities with an association in one query (a list screen's fetch-join) runs as DQL on the protected `em()` — the second seam, also inside the repository only (added 2026-09-21 for module-contact's list).
- **Money**: `MoneyType` (`type: 'money'`) maps `Money` ↔ `DECIMAL(15,2)` as a decimal string in both directions; a float on either side is refused. The column carries no currency — every amount is read in the installation's base currency, `systemConfig.inc.php` → `baseCurrency` (default `CHF`), set on the type at boot (ADR-042 decisions 3 and 4) — so a `Money` in any other currency is refused on the way in, and so is an amount beyond ±9999999999999.99 (the column's range), before SQL.
- **Strict `sql_mode`** on every connection (`EntityManagerFactory::SQL_MODE`, MariaDB 10.6's own default pinned per session): an out-of-range DECIMAL or an over-long string is an error, never a silent clamp or truncation.
- **Announced entities only**: `DoctrineEntityManager` refuses `getRepository()`, `persist()` and `remove()` for a class missing from `doctrineEntities`, naming the key — Doctrine's attribute driver would map it on the spot, and the migrations would never see it.
- **Caches** (decision 11): metadata and query cache share one pool. Production: `symfony/cache` `PhpFilesAdapter` under the release-local `var/cache/doctrine/` (ADR-035) — every entry a PHP file OPcache keeps compiled; files rather than APCu because web and CLI never share an APCu pool (CACHE-CLI-001). DEBUG (`var/state/debug.flag`): an in-memory `ArrayAdapter`, rebuilt per request, so an entity change shows without «Cache leeren». `Bootstrap::buildEntityManager()` decides (`DEBUG` → null → memory; else `CacheManager::generatedPhp()->dir('doctrine')`); the harnesses pass the directory or null explicitly. No result, hydration or second-level cache.
- **The directory is the kernel's, not the package's**: `GeneratedPhpCache` (pool `CacheManager::generatedPhp()`, [`cache.md`](cache.md)) names `var/cache/doctrine` in `GeneratedPhpCache::DIRS`, hands the path out through `dir('doctrine')` and clears it with `clearAll()` — every file deleted AND `opcache_invalidate($file, true)`, because an `include()`d file outlives its deletion in OPcache when `validate_timestamps` is off. `SystemController::clearCacheAction()` and `toggleDebugAction()` call it (plain PHP, no Doctrine — a no-op when the directory does not exist), and `z77-db migrate` calls it after a successful run. Never `opcache_reset()` (shared hosting).
- **Schema: only through migrations, only from the CLI** (decisions 12–14): `php vendor/bin/z77-db migrate | status | diff | generate` (`packages/persistence-doctrine/bin/z77-db`, in this package because the kernel carries no Composer dependency and `doctrine/migrations` is one; not `z77-run`, which is the cron entry). The binary boots like `z77-run` (`Bootstrap` + `pullUpServices()`, no HTTP), builds the EntityManager through the same `Bootstrap::buildEntityManager()` the driver uses, and hands over to Doctrine's own commands under short names (`MigrationsApplication`, `WrappedCommand`). A non-CLI SAPI is refused twice: in the binary and in `MigrationsApplication::create()`. The harness creates its throwaway schema with `SchemaTool` — a test-only shortcut, never against an installation.
- **Where the migrations are** (`MigrationDirectories::collect()`): the package's `res/migrations` (namespace `Z77\Persistence\Doctrine\Migrations`, first migration `Version20260921000000` = `number_range`) and, for every module that declares `doctrineEntities` (config key or extension file), `res/migrations/` under the module's source path with namespace `{ModuleNamespace}Migrations` (derived through `ModuleManager::getNamespacePrefix()`, Rule 5). A module without the directory is skipped; a module whose directory exists under two source paths (package AND `override/`) is refused — Doctrine binds one directory per namespace.
- **What `z77-db` adds to Doctrine's stock commands**: `migrate` prints the resolved project root and database first (the guard against migrating `current` instead of `next`); the metadata table `schema_migration` is created in `utf8mb4_unicode_ci`, InnoDB, before Doctrine initialises it (Doctrine's own `new Table()` would take the database default — decision 18) and dropped again if the run ends without executing anything (operator answered «no», nothing recorded); `diff` and `generate` ALWAYS need `--namespace` — Doctrine would take the first or only configured one, this package's, and a module's first migration (written before its `res/migrations` exists) would land in `vendor/`; a module with entities but no directory yet is told «create {path} first» instead of Doctrine's «Path not defined»; migrations run in timestamp order across all namespaces (`ChronologicalComparator` — Doctrine's default orders by class name, i.e. module by module); after a successful `migrate` that was not `--dry-run` (`--write-sql` still executes in 3.9) the compiled cache is cleared as part of the command. What Doctrine already does on its own: `SqlGenerator` drops every statement naming the metadata table from a generated diff — no schema filter is needed (a global one would hide the table from Doctrine's own `tablesExist()` and `migrate` would create it twice; found the hard way).
- **The entity list for `diff`** is the EntityManager's: the modules' `doctrineEntities` plus `EntityManagerFactory::PACKAGE_ENTITIES` — the same list the driver runs on (decision 5). A `money` column diffs clean: DBAL 4 compares column declarations, and `MoneyType` declares the `NUMERIC(15, 2)` the database reports (DOCTRINE-TYPE-001, resolved).
- **Transaction port** (decision 10): `UnifiedEntityManager::getTransaction(SomeDoctrineEntity::class)` returns the kernel's `TransactionInterface` — `run(callable): mixed` and `isOpen(): bool`, nothing else. Implemented by `DoctrineTransaction` (one per driver); the File driver throws a `LogicException`. `run()` opens ONE database transaction at depth 0, flushes the EntityManager and commits when the outermost unit of work returns, rolls back and rethrows on any exception. `isOpen()` answers from the port's own depth (what `LedgerService::post()` asserts), not from DBAL's nesting level, and stays true until the outermost commit is through (also during that flush). At depth 0 `run()` refuses with a `LogicException` when the connection already has a transaction the port did not start — it would nest into a savepoint and «commit» with `RELEASE SAVEPOINT`. After a rollback the port checks that DBAL and the server agree nothing is open; if the rollback threw or DBAL's level is still above zero (a server-side rollback after a deadlock discarded the savepoints), it closes the DBAL connection — DBAL reconnects lazily — and rethrows the ORIGINAL exception (DOCTRINE-TX-005).
- **Nesting joins — without savepoints.** DBAL 4.4 always nests with savepoints (`SAVEPOINT DOCTRINE_n`; nesting without them was removed), and an inner `rollBack()` there rolls back to the savepoint only, after which the outer may still commit. The port therefore counts its own depth and never calls DBAL's nested `beginTransaction()`: a nested `run()` is a plain call inside the open transaction. An exception in ANY nesting level marks the whole rollback-only; if the outer code catches it and returns normally, the outermost `run()` rolls back and throws `TransactionRolledBackException` (kernel, `Z77\Persistence\Exception`) instead of committing. Doctrine's own `flush()` inside a unit of work still uses a savepoint (its UnitOfWork does that on its own); a failed `flush()` closes Doctrine's EntityManager and poisons the unit of work the same way (`DoctrineTransaction::markRollbackOnly()`, called by the driver's `flush()` and by `NumberRangeRepository::next()` before they rethrow), even when the caller swallowed the exception. A failed report statement on `connection()` does not (DOCTRINE-TX-006).
- **After a rollback the EntityManager is replaced** (`EntityManagerHolder::replace()`: a new `EntityManager` over the SAME connection and configuration — no second connection), also after a failed `flush()` outside any unit of work. The driver, its repositories and the port hold the holder, never the EntityManager, so a repository obtained before the rollback keeps working. Entities loaded before are detached: they read, they do not write.
- **`NumberRange`** (decision 15, ADR-042 decision 9): table `number_range` (`name VARCHAR(64)` PK, `last_number INT UNSIGNED`), the entity `Entities\NumberRange` is the table definition. `getRepository(NumberRange::class)->next('invoice')` — `INSERT … ON DUPLICATE KEY UPDATE` (creates the row on the first draw, takes an EXCLUSIVE lock on an existing one), `SELECT … FOR UPDATE`, `UPDATE`; refused outside an open transaction; integer from 1; a rolled-back unit of work releases the lock with the old value, so the number is not consumed; any failed statement in `next()` (deadlock, lock wait timeout) marks the unit of work rollback-only before the exception leaves, so a swallowed failure cannot end in a half-committed unit of work. Not deadlock-free: the first draw of a NEW range under contention when the creator rolls back (DOCTRINE-NR-003) — which is why a range is created ahead of concurrent use with `create($name)`: idempotent, inserts the row at 0, consumes no number, inside or outside a unit of work, and answers whether the row was NEW (`true` = inserted, `false` = it existed and was left untouched — the affected rows of the `INSERT … ON DUPLICATE KEY UPDATE`), so a caller for whom an existing range is a conflict can refuse instead of continuing an old sequence (the ledger's fiscal-year opening does, review M1 2026-09-22). The counterpart is `dropUnused($name)`: inside an open transaction only (refused outside, like `next()`), it reads the row `FOR UPDATE` and deletes it only while `last_number = 0`, and answers whether the range is gone (`true` = deleted now or there was no row, `false` = it has drawn a number and was kept untouched); the lock holds until the caller's commit, so a `next()` waiting on it sees either the untouched row (rollback) or no row. Its production caller is the ledger's deletion of a wrongly opened, still empty fiscal year (`FiscalYearService::delete()`, FIN-FY-002), which takes it FIRST in its unit of work (verified: `tests/persistence-doctrine-tx.php` J20–J24, `tests/module-financial.php` Y). Key model: ONE string the module composes (`invoice`, `credit-note`, `journal-entry.2026` — the ledger names its range by the fiscal year's CODE, e.g. `journal-entry.2026-27` for a deviating year, `FiscalYear::journalEntryRange()`) — `next()` returns a bare integer; prefix, year segment and zero padding belong to the document (a column there if stored), never to `number_range` (owner, 2026-09-21). Verified gapless with four parallel PHP processes drawing from one fresh range while rolling back every fifth draw (`tests/persistence-doctrine-tx.php` K).
- **The package's own entities** are listed in `EntityManagerFactory::PACKAGE_ENTITIES` and mapped in front of the modules' `doctrineEntities` on every EntityManager; `DoctrineEntityManager` takes the announced set from the metadata driver, so there is one list — and `z77-db diff` sees the same one.
- **Open-work check registry** (decision 15, plan §2): `OpenWork\OpenWorkChecks` — a module declares under its config key `openWorkChecks` which classes answer which scope (`'period-close' => [InvoicingInProgressCheck::class]`), `OpenWorkChecks::fromModules(DI::getModuleManager())` collects the union, `ask(scope, parameters)` returns an `OpenWork` with `isEmpty()`, `isBlocked()`, `blocking()`, `warnings()`, `all()`. A check implements `OpenWorkCheckInterface::check(string $scope, array $parameters): iterable<Finding>`, is instantiated without arguments and yields `Finding::blocking(...)` / `Finding::warning(...)` with a message and an opaque reference. Registration is configuration like `doctrineEntities` and `jobs` — no runtime `register()` — and a bad entry fails at the first question naming scope and module (and the file, for an extension file). A project adds a check of its own through the extension file `override/z77/module/{module}/src/App/Config/openWorkChecksConfig.inc.php`, returning the same shape as the config key (scope => list of check classes); `fromModules()` unions it with the module config's entries, deduplicated per scope, module config first. The scope name and its parameters belong to the asking module (financial: `period-close`; stock: `stocktake`). The registry has no Doctrine dependency of its own but stays in this package (owner, 2026-09-21): only Doctrine-backed modules close periods or take stock.
- **Where the harness runs**: `composer install` in the monorepo root installs Doctrine into the gitignored `vendor/` (the root manifest requires `z77/persistence-doctrine`; the `packages/*` path repository wins over Packagist, so the moving kernel is what gets tested). Credentials come from `%USERPROFILE%\.z77\mariadb.txt` or `Z77_TEST_DB_*` environment variables; the schema `z77test_<random>` is created with `utf8mb4_general_ci` on purpose and dropped at the end.

## rules

- When a module needs a relational entity → MUST mark it `#[Entity('doctrine')]`, MUST add Doctrine's mapping attributes, and MUST list the class under `doctrineEntities` in the module config; MUST NOT rely on a directory being scanned
- When a project adds a Doctrine entity of its own (a new class under `override/z77/module/{module}/src/…`) → MUST announce it in `override/z77/module/{module}/src/App/Config/doctrineEntitiesConfig.inc.php` (`<?php return [MyEntity::class];`); MUST NOT copy the module config into `override/` just to extend `doctrineEntities` (Rule 2 — the file records only the addition). Shadowing an existing entity (same FQCN) needs no announcement
- When a project adds an open-work check of its own → MUST register it in `override/z77/module/{module}/src/App/Config/openWorkChecksConfig.inc.php` (`<?php return ['period-close' => [MyCheck::class]];`); MUST NOT copy the module config into `override/` just to extend `openWorkChecks` (Rule 2)
- When reading or writing a Doctrine entity from a service or controller → MUST go through `UnifiedEntityManager` (`getRepository()`, `persist()`, `flush()`, `remove()`); MUST NOT obtain or hold Doctrine's `EntityManager` (ADR-039 decision 6)
- When a repository needs SQL (reports, aggregates) → MUST extend `DoctrineRepository`, run it on `$this->connection()` and mark the method Doctrine-only in its docblock; MUST NOT open a second connection or read the credentials elsewhere (decision 8, Rule 2)
- When a repository must HYDRATE a list with an association (a screen that renders every row's association — the N+1 case) → MUST run a DQL fetch-join on the protected `$this->em()` inside the repository (`ContactAddressRepository::findForContacts()` is the model), marked Doctrine-only; MUST NOT hand the EntityManager further up or let a template touch a lazy proxy per row
- When changing an EXISTING (managed) Doctrine entity from user input → MUST validate BEFORE mutating it — apply the values to a detached draft (`clone`, or a new object built from the input), validate the draft, then apply to the managed entity and flush (`ContactService::update()` / `saveAddress()` are the model; a new child is attached to a managed collection only after it passed); MUST NOT `mapFromArray()` or call setters on the loaded entity first. Why: flush scope (decision 9) — Doctrine writes every managed entity that changed, `persist()`ed or not, so a rejected change stays in the EntityManager and is written by the NEXT flush of anything else in the same request, and inside `run()` by the port's own flush (DOCTRINE-TX-007). On the File driver the same code is harmless, which is why it looks right
- When mapping an amount → MUST use `#[ORM\Column(type: MoneyType::NAME)]` on a `Money` property; MUST NOT map money as `decimal` (string), `float` or `integer` (ADR-042 decision 3)
- When touching the connection parameters → MUST keep `utf8mb4` / `utf8mb4_unicode_ci` on the connection AND in `defaultTableOptions`; MUST NOT make charset or collation configurable (decision 18)
- When the `db` backup or any other reader needs the database → MUST read `config/client/database.inc.php` through the split lookup (`ConfigManager` → `config/database`, or `ConfigLocator::path()` with an explicit root like `BackupService::readConfig()`); MUST NOT copy host, name or credentials into another config (decision 4)
- When an entity carries an amount in a currency other than the base currency (a foreign-currency document) → MUST NOT map it with `MoneyType`; the type refuses it, and the mapping for such amounts is undecided (see pending)
- When calling `reorder()` → MUST NOT do so for a Doctrine entity; sort order is a mapped column there (decision 9)
- When writing a test that needs the driver → MUST run it against a throwaway schema per run in `tests/persistence-doctrine.php` style (decision 16); MUST NOT point a test at an installation's database, and MUST NOT write a password into any repository file
- When a use case must be atomic (a number plus a document, several flushes, DBAL SQL plus ORM writes) → MUST run it through `UnifiedEntityManager::getTransaction(Entity::class)->run(fn() => …)` and let exceptions propagate; MUST NOT catch an exception from a nested `run()` or a failed `flush()` and go on — the outermost `run()` rolls back and throws `TransactionRolledBackException` anyway (decision 10)
- When a service requires its caller to own the transaction (`LedgerService::post()`) → MUST assert `getTransaction(Entity::class)->isOpen()` and refuse otherwise; MUST NOT open a transaction of its own there
- When code runs after a rollback in the same request → MUST re-read what it needs through a repository; MUST NOT persist or mutate an entity loaded before the rollback (detached — silently not written)
- When a document or entry needs a gapless number → MUST draw it with `getRepository(NumberRange::class)->next($name)` as the FIRST write of the unit of work (lock order, decision 10) and keep that unit of work short; when one unit of work needs several ranges → MUST draw them in a fixed order, sorted by name, so two use cases never hold two range locks in opposite order; MUST NOT draw it outside `run()` (refused), MUST NOT draw it speculatively before validation, and MUST NOT read or write the `number_range` table any other way
- When a range becomes valid (the ledger's `journal-entry.{code}` at the opening of a fiscal year — done by `FiscalYearService::open()` since P2 part 1, see `financial.md`) → MUST create it with `getRepository(NumberRange::class)->create($name)` before anyone draws from it (DOCTRINE-NR-003) and MUST check its return value when a range that already exists would be a conflict (`false` = the row existed — refuse, do not continue its sequence silently); MUST NOT draw and commit a first number to create it (that consumes number 1)
- When a range must go away again (it became valid by mistake — the ledger's empty fiscal year) → only the module that OWNS the range MUST drop it, with `getRepository(NumberRange::class)->dropUnused($name)` as the FIRST lock of its unit of work, and MUST refuse its own action on `false`; MUST NOT drop a range that has drawn a number (`dropUnused()` keeps it — every number handed out is referenced or documented as a gap), MUST NOT drop another module's range, and MUST NOT delete `number_range` rows any other way
- When a document shows a formatted number (prefix, year segment, zero padding) → MUST derive or store it on the document; MUST NOT encode it in `number_range` or ask `next()` for anything but the bare integer
- When choosing a range name → MUST compose ONE string of at most 64 bytes without surrounding whitespace, lower-case kebab with an optional dotted segment (`invoice`, `credit-note`, `journal-entry.2026`); MUST NOT rely on case to separate two ranges (names compare case-insensitively)
- When a module wants to block or warn before another module's close-like action (period close, stocktake) → MUST implement `OpenWorkCheckInterface` and declare the class under `openWorkChecks` → `{scope}` in its module config; MUST NOT call into the other module or register at runtime
- When a module asks «anything open?» before its own action → MUST use `OpenWorkChecks::fromModules(DI::getModuleManager())->ask($scope, $parameters)` and refuse the action on `isBlocked()` while showing `warnings()`; MUST document the scope name and the parameter keys it passes where the action is documented, and MUST keep its own refusal as the last line of defence (ADR-042 decision 11)
- When the schema has to change → MUST write a migration under the owning module's `res/migrations/` (namespace `{Module}\Migrations`, `php vendor/bin/z77-db diff --namespace="Z77\Module\X\Migrations"` writes the draft, `generate` an empty one) and apply it with `php vendor/bin/z77-db migrate` on the CLI; MUST NOT run `SchemaTool`, `orm:schema-tool:update` or any DDL from a web request or a job (decision 12)
- When authoring a migration → MUST keep it expand/contract: `current` and `next` run against ONE database (ADR-035), so add first, switch the release, remove in a LATER release; MUST NOT rename or drop a column or table the running release still reads, and MUST NOT put a data migration and a DROP into the same file (decision 14)
- When authoring a migration → MUST review the generated `up()` before committing (a table no entity maps is proposed for DROP, and that is only right if the entity is gone), MUST keep `utf8mb4` / `utf8mb4_unicode_ci` and MUST NOT name another charset or collation (decision 18); `down()` is for development only — a release never rolls the schema back
- When adding or changing a Doctrine entity → MUST run `z77-db diff` afterwards and commit the migration with the entity; MUST NOT rely on the metadata cache being rebuilt — in production it is compiled and cleared only by «Cache leeren», the DEBUG toggle and `migrate`
- When a package compiles PHP files it will `include()` (a cache, generated code) → MUST write them under `CacheManager::generatedPhp()->dir($name)` with `$name` listed in `GeneratedPhpCache::DIRS` and MUST NOT compose a `var/cache` path itself; a directory the pool does not know is a directory «Cache leeren» never clears
- When deploying a release with pending migrations → MUST run `php vendor/bin/z77-db migrate` on the NEW release (`next`) before switching `current` to it, and MUST NOT run it on `current` first (decision 14: the migration must leave the running release working — that is what expand/contract guarantees, and the order is what proves it)

## known issues

- **DOCTRINE-CFG-001** — don't assume a `database` block in `config/backup.inc.php` still works: `BackupService::fromProjectRoot()` refuses it with a message pointing at `config/client/database.inc.php` (ADR-039 consequence). No installation had one when the block moved (2026-09-21); an existing seed-once file with `'database' => null` is fine.
- **DOCTRINE-CUR-001** — don't assume a `Money` column knows its currency: it is read in `systemConfig.baseCurrency` (default `CHF`) regardless of what wrote it, which is why `MoneyType` refuses to store any other currency. A document in a foreign currency keeps its own currency and rate fields; the ledger posts converted (ADR-042 decision 4).
- **DOCTRINE-TYPE-001** — resolved 2026-09-21. A `money` column diffs clean: DBAL 4 has no `DC2Type` comment hint any more and compares column DECLARATIONS (`AbstractPlatform::columnsEqual()`), and `MoneyType::getSQLDeclaration()` yields the same `NUMERIC(15, 2)` the introspected `decimal(15,2)` does. Verified in `tests/persistence-doctrine-migrations.php` G11: `diff` after `migrate` reports «No changes detected» for an entity with a `money` column. Nothing to fix; the precision and scale fixed in the type are what make it hold.
- **DOCTRINE-MIG-001** — don't assume `z77-db diff` knows which tables are yours: it compares the WHOLE database against the mapping. A table no announced entity maps (a wdv table imported next to the new ones, a table of a module whose package is not installed on this machine) is proposed for `DROP TABLE` in the generated `up()` (verified: `tests/persistence-doctrine-migrations.php` G11b). Review the draft; delete the statement unless the entity is really gone. Only `schema_migration` is excluded — by Doctrine's own `SqlGenerator`, not by z77.
- **DOCTRINE-MIG-005** — don't assume the files `z77-db migrate` deletes and the files the web process writes belong to the same user: on a host where the CLI runs as the shell user and PHP-FPM as another, `var/cache/doctrine/` written by the web process may not be deletable from the CLI (`GeneratedPhpCache: cannot delete …`) — and the other way round after a CLI run compiled metadata. Same class as any release-local runtime state (ADR-035): run both sides as one user (cyon: they are), or clear from the backend after a CLI migrate. Not verified on a host with split users.
- **DOCTRINE-MIG-006** — don't follow the hints Doctrine prints after `diff` («you can use `migrations:execute --up …`») literally: `z77-db` exposes `migrate`, `status`, `diff` and `generate` only; there is no `execute`. Apply a fresh draft with `z77-db migrate` (it is the only new version), revert it in development with `z77-db migrate prev`.
- **DOCTRINE-MIG-002** — don't assume migrations run module by module: they run in TIMESTAMP order across all namespaces (`ChronologicalComparator`), so a `Version20260315…` of `module-debtor` runs before a `Version20260601…` of `module-contact`. The timestamp is the class name's `Version{YmdHis}` — `diff`/`generate` set it to now. Don't hand-pick a timestamp older than a migration that is already applied on an installation: it would sort BEFORE the current version and be reported as executed-unavailable / skipped. Decided (owner, 2026-09-21): Doctrine's class-name order would run a later-created migration of an alphabetically earlier module (`Debtor`) before the migration of a later module (`Vat`) that creates the table it reads — a fresh install then fails. Disabling `FOREIGN_KEY_CHECKS` was considered and rejected: it accepts a foreign key to a misspelt table and does not help a data step (`UPDATE … SELECT`, expand/contract) that reads another module's table.
- **DOCTRINE-MIG-003** — don't put a migration under `override/z77/module/{module}/res/migrations`: the collector refuses a module whose directory exists under two source paths, because Doctrine binds one directory per namespace. How a project ships a migration for an entity it adds through `doctrineEntitiesConfig.inc.php` is undecided (pending).
- **DOCTRINE-MIG-004** — don't assume `z77-db` is in `vendor/bin` after `composer install` on an EXISTING project: a new `bin` entry reaches `vendor/bin` only through `composer update z77/persistence-doctrine` (packaging.md PKG-005). `php vendor/z77/persistence-doctrine/bin/z77-db` works regardless.
- **DOCTRINE-CACHE-001** — don't assume a CLI `migrate` reaches the WEB process's OPcache. `opcache_invalidate()` acts on the calling process tree's pool only — the CLI's (usually none: `opcache.enable_cli = 0`), never PHP-FPM's. `migrate` deletes the files; whether the web process stops serving their compiled copies depends on `opcache.validate_timestamps`: on (PHP's default, `revalidate_freq` 2 s) → dropped at the next check; off → served until «Cache leeren» or the DEBUG toggle runs in the backend (web SAPI, where `opcache_invalidate()` hits the right pool) or FPM restarts. Same class as CACHE-CLI-001 (two process trees, two pools), and the stamp-file bridge of `DataCache` has no OPcache equivalent. In practice harmless: `migrate` runs on `next`, whose release-local cache the web process has not compiled yet (owner, 2026-09-21, see pending).
- **DOCTRINE-TX-001** — don't assume a nested `run()` gives you a savepoint to recover from: it does not. There is no partial rollback through the port; an inner failure ends the whole unit of work, whether or not the outer code caught it. DBAL's own savepoint nesting exists underneath (Doctrine's `flush()` uses it) but is not exposed and not a feature.
- **DOCTRINE-TX-002** — don't assume `isOpen()` sees every database transaction: it reports the port's own depth. A transaction started any other way (a repository calling `beginTransaction()` on `connection()`, which nothing should do) is invisible to it; `NumberRangeRepository::next()` therefore checks the DBAL connection, the level the row lock actually lives on.
- **DOCTRINE-TX-003** — don't assume the exception you threw inside `run()` is the one that comes out when a `flush()` failed first inside it: the flush failure is Doctrine's exception, and if you swallowed it, the outermost `run()` throws `TransactionRolledBackException`. Also, a File-driver write inside `run()` happens at once and is not rolled back (ARCH-A007).
- **DOCTRINE-TX-004** — don't hold a Doctrine entity across a rollback: the EntityManager behind it is gone (replaced), the object is detached, `persist()` of it or of anything referencing it does nothing or fails at flush. The same applies after a failed `flush()` outside a unit of work.
- **DOCTRINE-NR-001** — don't assume two writers of one range run in parallel: `next()` serialises them for the length of the caller's transaction (the lock holds until commit — that is what makes the sequence gapless). A long unit of work after drawing a number holds every other writer of that range. Under the MariaDB default `innodb_lock_wait_timeout` (50 s) a waiter times out with the driver's exception; there is no retry (decision 10).
- **DOCTRINE-NR-002** — don't assume a deadlock is impossible if some other use case locks a document row first and then draws a number: lock order is `NumberRange` FIRST, always; the harness proves gaplessness with that order only.
- **DOCTRINE-TX-005** — don't expect a `DeadlockException` at the top when the deadlock hits inside `flush()`: InnoDB rolls back the whole server transaction and discards every savepoint, Doctrine's UnitOfWork then tries `ROLLBACK TO SAVEPOINT` on a savepoint that is gone, and what surfaces is DBAL's `DriverException` (1305, «SAVEPOINT … does not exist») with the `DeadlockException` further DOWN the `getPrevious()` chain (PHP appends the exception a `finally` block replaced). Inside `NumberRangeRepository::next()` the `DeadlockException` surfaces as is. Either way the port closes the DBAL connection (DBAL's nesting level would otherwise stay above zero and every later `run()` would «commit» with `RELEASE SAVEPOINT` only) and DBAL reconnects lazily with the same parameters and init command — SESSION settings set by hand on that connection (`SET innodb_lock_wait_timeout …`) are gone after that. Verified in `tests/persistence-doctrine-tx.php` O.
- **DOCTRINE-TX-006** — don't rely on the port to notice a failed REPORT statement: SQL a repository runs on `connection()` cannot be intercepted by the port. A failed `flush()` and a failed statement in `next()` mark the unit of work rollback-only before rethrowing; a failed report query does not, so a caller that swallows its exception inside `run()` could still commit. A report is a read and the rule is to let exceptions propagate; a subclass that WRITES on `connection()` calls `markTransactionRollbackOnly()` in its catch, as `next()` does.
- **DOCTRINE-TX-007** — don't assume `run()` writes only what happened inside it: the flush before the outermost commit writes EVERYTHING the Doctrine EntityManager manages, including an entity loaded and mutated BEFORE `run()` in the same request (ARCH-A004 applied to the port). And the asymmetry: a File entity persisted inside `run()` is not flushed by the port — it still needs an explicit `UnifiedEntityManager::flush()`, and it is not rolled back (ARCH-A007). The auto-flush is decided behaviour (owner, 2026-09-21): without it a `persist()` without `flush()` inside `run()` would be lost silently.
- **DOCTRINE-NR-003** — don't assume the FIRST draw of a NEW range is deadlock-free under contention (verified against MariaDB 10.6.28): while the creating transaction holds its fresh row, waiters queue in the `INSERT … ON DUPLICATE KEY UPDATE` duplicate check; if the creator then rolls back, the row vanishes and the waiters race to insert it — all but one get a deadlock (1213), see their exception and are marked rollback-only. Gaplessness holds (nothing was consumed). An EXISTING row never deadlocks here. Mitigation (owner, 2026-09-21): ranges are created explicitly ahead of concurrent use with `NumberRangeRepository::create()` — for the ledger at fiscal-year opening (`FiscalYearService::open()`, P2 part 1 — done 2026-09-22, formerly a pending item here; `tests/module-financial.php` D9/D19/D23/D26); a range created and committed that way never takes the new-row path. Not in the harness — the outcome depends on timing; `create()` itself is, including its return value (`tests/persistence-doctrine-tx.php` J13–J19b).
- **DOCTRINE-OW-001** — don't assume the open-work registry filters by anything but the scope name: every parameter is passed through untouched, and a check that ignores `$parameters` reports the same findings for every period. The asking module owns the scope name and the parameter keys; nothing validates them.
