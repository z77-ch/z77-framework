## mental model

`z77/module-debtor` (plan §6, ADR-040) is the receivables side: it owns invoicing and the open amounts, and it reaches the bookkeeping only through a port — the package *suggests* `z77/module-financial` and requires kernel, `persistence-doctrine`, `module-vat` and `module-contact` (plan §2). **P3 part 1** built the MASTER DATA: the debtor profile per contact, and the three file-based types an invoice, a payment and a dunning notice are built from. **P3 part 2, this state, builds the documents**: `InvoicingService` as the single entry for every source, `Invoice` (invoices AND credit notes, one entity), the states `invoicing` / `final`, the 0.05 rounding line, the two number ranges, the full snapshot, and the accounting port `AccountingGateway` with its ledger adapter and its Null implementation. PDF with QR-bill and the document screens are part 3; payments, discount and loss, CAMT.054 and the dunning runs are P4 — there is no `OpenItem` table yet, the open amount is derived. Nothing here exists without a caller in this state (guiding rule: nothing in stock). The package is required in the monorepo ROOT `composer.json` only — NOT in `skeleton/composer.json`, like `module-contact` and `module-financial`; a project requires it when it needs it. There are therefore no `RUNTIME=` paths: the seeded `data/framework/debtor/*.json` come into being in a PROJECT that installs the package, not in the skeleton.

### `DebtorProfile` (Doctrine)

- Table `debtor_profile`: `contact_id` (FK to `contact`, **unique** — `uniq_debtor_profile_contact`), `payment_terms_code` (VARCHAR 16, indexed `idx_debtor_profile_terms`), `dunning_block`, `active`. Keyed by the contact's id in DEBTOR's table — not one column of it lives on `contact` (plan §2, §4a: contact knows no module).
- **At most one profile per contact**: `DebtorProfileValidator` asks first so the screen gets a field error; the unique index decides under a race, and `DebtorProfileService::flushOrRefuse()` turns its violation into the same field error (the `AccountService` model).
- **A NEW profile needs an ACTIVE contact** (decided 2026-09-22 on review): the reference rule of ADR-043 decision 19 applied to the party — a new reference needs an active row, and a debtor is a reference to a contact. An EXISTING profile on a contact deactivated SINCE keeps working and stays editable, because open items and documents are already written against it. The list therefore offers «Debitor anlegen» only on an active contact, and `addAction()` refuses a hand-built URL with the same sentence.
- **No `language`** (decided 2026-09-22): `Contact::$language` already says which language a document to this party is written in (plan §4a). A second field would be a second truth about one fact (Rule 2).
- **No `currency`** (decided 2026-09-22): the Bauplan §6.1 lists it, but Q6 decided against foreign-currency invoicing and §6.2 puts currency and rate on the DOCUMENT, not on the party. On the profile it would be an unread column with no caller; part 2 adds it to the invoice, where it is read. Adding it later is a new column on a new table, not a change to issued documents.
- **Payment terms are REQUIRED**, not «deviation from a default» (decided 2026-09-22): there is no global default payment terms setting, and inventing one before `InvoicingService` reads it would be a setting nobody uses. A profile without terms would leave part 2 with nothing to fall back on.
- Write path `DebtorProfileService`: `save($new)`, `update($profile, $values)` (values onto a detached clone, validated, only then applied to the managed entity — ADR-039 decision 9), `setActive()`, `forContact()`. **No delete anywhere** — invoices and open items are written against the party.

### File-based master data (three types, one rule set)

All three follow `module-vat`'s `TaxCode` pattern exactly (including `setActive()`, below): `#[Entity('file', 'framework/debtor/…json')]`, seeded once on first install from `data/**/*.default.json` (ADR-024 seed-once, no installer change needed — the installer walks every framework package's data root), referenced BY `code`, code immutable, **deactivated and never deleted** (ADR-043 decision 19), UTF-8 without BOM (DATA-JSON-001). Their one write path is `DebtorMasterData`, which has no remove method at all.

**`set*Active()` is a PURE STATE CHANGE** (decided 2026-09-22 on review, the `VatMasterData::setActive()` model): it checks the code and writes the row — the field validator does NOT run. A row must be switchable off exactly when it has become invalid, and that is the normal reason to switch it off: a payment target whose ledger account was deactivated in the bookkeeping, or a row whose document text stands in a language the installation has since dropped. Running the full validator there would let the rule meant for NEW input forbid the cleanup. The validator runs where new input arrives — on a form save (`saveTerms()` / `saveTarget()` / `saveLevel()`). The three `toggleActiveAction`s still catch `DebtorException` and answer with a `fetchError`, so the one rule `setActive()` keeps (an unchanged code) never becomes a 500.

- **`PaymentTerms`** (`payment_terms.json`): `code`, `label` (German, for the backend list), `dueDays`, `discounts` (a list of `{days, percent}`, at most `MAX_TIERS` = 2, percent as an INTEGER IN HUNDREDTHS like the VAT rates — 2 % = `200`), `documentText` (per language), `active`. Seed: `net-30` «30 Tage netto» and `disc-2-10` «10 Tage 2 %, 30 Tage netto» — **without a `document_text`** (owner, 2026-09-22): an empty text stays allowed, so an installation in any language starts with valid rows and writes its own wording. Two tiers are supported because three-step terms («3 % / 10 Tage, 2 % / 20 Tage, 30 Tage netto») exist in Swiss practice; the seeded example needs one tier plus `dueDays`.
- **`PaymentTarget`** (`payment_targets.json`): `code`, `label`, `iban` (normalized upper-case without spaces), `accountNumber` (the ledger account that bank account is booked on), `active`. **Not seeded** — an IBAN cannot be guessed and a placeholder would end up printed on a QR-bill; the file comes into being with the first row the backend writes.
- **`DunningLevel`** (`dunning_levels.json`): `code`, `label`, `level` (unique, the order a dunning run walks), `daysAfterDue`, `fee` (INTEGER MINOR UNITS — plan §3, `Money` is not a JSON row), `documentText`, `active`. Seed: `reminder` (level 1, 10 days, 0.00), `dunning-1` (level 2, 30 days, 20.00), `dunning-2` (level 3, 50 days, 40.00) — **without a `document_text`**, for the same reason as the payment terms. **No tax code and never one**: a dunning fee compensates the effort of chasing a debt, it is not a supply (plan §6.5).

### Shared shapes (Rule 8)

Three pieces exist once instead of two or three times: `Entities/HasDocumentText` (the property, its normalising setter and its getter — `PaymentTerms` and `DunningLevel` both carry it), `Validators/ValidatesMasterDataRow` (the identical `code` / `label` rules of all three file entities, with the repository supplied by the using validator through `masterDataRows()`), and `Validators/DocumentTextRule` (the per-language rule itself).

### Text per language, label in German

Two texts, two audiences (decided 2026-09-22): `label` is the German name the BACKEND list shows, exactly as `TaxCode::$label` and `AddressType::$label` are; `documentText` is what prints on the customer's invoice or notice and is therefore kept per language. The languages are the installation's (`I18n::getLanguages()`, `i18n.md`), the default language first, and `DocumentTextRule` enforces both halves: a key must be a language this installation serves, and as soon as ANY language is filled the DEFAULT language must be too — it is what every other language falls back to (the `ContentService::find()` fallback part 2 will use). Leaving the text empty everywhere stays allowed. The **fallback RESOLVER is deliberately not built yet** — it arrives with the document in part 2, like `AddressTypes::resolve()` did for the address snapshot.

### `Iban` — what is checked, and why separately

`Services/Iban` is pure: `normalize()`, `format()` (groups of four), `isWellFormed()` (shape plus the exact registry length for CH / LI: 21), `hasValidCheckDigits()` (ISO 7064 MOD-97-10 on the DIGIT STRING in seven-character chunks — a 34-character IBAN expands to ~70 digits and would overflow `int`), `isSwissArea()`, `iid()` (positions 5–9) and `isQrIban()` (IID **30000–31999**, the range SIX reserved for QR-IBANs). The three checks are separate so the German message says what is actually wrong. A QR-IBAN carries a QR reference (QRR), a normal IBAN a creditor reference (SCOR) or none — part 2 needs the difference to print the right reference; part 1 records and shows it.

### The soft boundary to financial

`LedgerAccountCheck` is one of the TWO classes in debtor that name module-financial (the other is the port adapter `LedgerAccountingGateway`, part 2), and it names it as a STRING (`LEDGER_SERVICE`), so its absence is a lookup miss and not a fatal (ADR-040 decision 5: the package only `suggest`s financial). Every answer is three-valued: `true` postable and active, `false` financial refuses, **`null` financial is not usable here and the caller may not treat that as a failure**.

**«Installed» means TWO things** (decided 2026-09-22 on review), and the second one decides: the class must autoload AND `financial` must be a REGISTERED module (`ModuleManager::getModuleConfig('financial')`). A package sitting in `vendor/` but missing from the project's `moduleManager` config has no config, no announced entities and no booted Doctrine metadata for `Account` — asking it would not answer «no», it would fatal, and with it every debtor list. Registration is also what a project actually switches when it decides to keep its books elsewhere, which is why the harness proves the branch by unregistering the module rather than through a constructor seam. It wraps `LedgerService::accountExists()` (plan §5.4, «for configuration validation»), whose second production caller this is. It is the READ half of the `AccountingGateway` boundary (plan §6.6, part 2 below); `InvoicingService::invoice()` asks it for every revenue account a draft names.

### `debtorAccounts` — the account settings

`debtorConfig → debtorAccounts` is a map key → account NUMBER, read only through `Services/DebtorAccounts` — the `LedgerService::vatAccountFor()` model, key for key (Rule 2). Defaults verified against `packages/module-financial/res/charts/kmu.json`:

| key | default | account |
|---|---|---|
| `receivable` | `1100` | Forderungen aus Lieferungen und Leistungen (Debitoren) |
| `discount` | `3800` | Erlösminderungen (Skonto is one) |
| `loss` | `3805` | Verluste aus Forderungen, Veränderung Delkredere |
| `rounding` | `3809` | Rundungsdifferenzen — the invoice's 0.05 line (plan §6.2), its own account in group 38 |
| `dunningFee` | `6950` | Finanzertrag — the fee, without VAT (plan §6.5) and not turnover |

- `number($key)` reads the configured number and fails loudly on a malformed value (`UnexpectedValueException`) — a typo in a config file is reported, never skipped. `postableNumber($key)` additionally asks `LedgerAccountCheck` and refuses with a German message NAMING THE KEY; `status()` is what the debtor screen shows so a wrong account is found before an invoice is posted. Everything is asked AT THE POINT OF USE, never at boot.
- **`rounding` has its OWN account** (owner, 2026-09-22): `3809 «Rundungsdifferenzen»` was added to the KMU chart in group 38 next to `3800` and `3805`, because rounding and discount must stay separable in the reports. This is NOT financial's VAT-return rounding account — that is its own setting (plan §5.1, the two are named apart on purpose).
- **`dunningFee` stays on `6950 Finanzertrag`** (owner, 2026-09-22): a dunning fee is **damages for the delay, not a service** — so it carries no VAT (plan §6.5) and it is not turnover, which is why it belongs outside the revenue classes 3 the VAT return reads by code.
- ⚠️ **BOOT-CONFIG-001** (`bootstrap.md`): a project override of `debtorConfig.inc.php` REPLACES the package config rather than merging, so an override must carry the FULL `debtorAccounts` map. A dropped key is then an `AccountNotConfiguredException` at the point of use — the loud failure this caveat needs until the merge is built (harness H7).

### Documents — `Invoice`, `InvoiceLine`, `InvoiceTax` (part 2)

- **One entity for invoice and credit note** (`InvoiceKind`: `invoice` | `credit-note`, decided 2026-09-23): §6.2 makes a credit note «the same mechanics with opposite sign» — same lines, same VAT summary, same snapshot, same states, same number mechanics on its own range. Two entities would duplicate every column and rule to differ in one word. The lines of a credit note are stored AS PRINTED (a positive «Gutschrift 50.00»); `InvoiceKind::sign()` flips the posting and the open amount. A credit note names the FINAL invoice it corrects (`creditNoteOf`, self FK); an invoice names none.
- **Two states** (`InvoiceState`, plan §6.2): `invoicing` — number and snapshot exist, the content may be replaced under the same number, NOTHING is posted, no open amount; `final` — immutable, posted through the port, the open amount exists. One way only; no cancelled or deleted state (plan §1, correction principle).
- **Table `invoice`**: `kind` + `number` (bare integer from the kind's range, `uniq_invoice_kind_number`), `state`, `contact_id` (FK — the party BY ID), `credit_note_of_id`, the **address snapshot** `addr_*` (below), `language` (the contact's language at issue — a later language change must not re-language an issued document), `invoice_date`, `service_from` / `service_to` (the VAT rate resolves by `service_from`, ADR-041 decision 4), **`currency` + `exchange_rate` — carried without logic and without a reader ON PURPOSE** (plan §6.2, Q6, confirmed on review 2026-09-23: the document owns them, the ledger never does — ADR-042 decision 4 —, and an issued document is immutable data, so adding them later would be a migration on issued documents; today currency = base and the rate is NULL; `exchange_rate` is a `DECIMAL(12,6)` STRING, never a float; the reason stands next to the column so no reviewer raises it again), `price_mode` (net | gross), `payment_terms_code` (BY CODE) with the terms AS APPLIED — `due_date`, `discount_tiers` (JSON `[{days, percent, until}]`) and `terms_text` (the printed sentence in the document's language) —, the totals `net_total` / `tax_total` / `rounding` / `gross_total` (`MoneyType`, stored, never recomputed), the opaque origin `source_type` / `source_ref`, `ledger_entry_ref`, `created_by/at`, `changed_by/at`, `version` (`#[ORM\Version]`). **No setters**: the header is written whole by `Invoice::issue()` / `reissue()`, the state by `finalize()` — and both refuse a `final` document in the entity itself.
- **The address snapshot is an EMBEDDABLE** (`Entities/AddressSnapshot`, `#[ORM\Embedded(columnPrefix: 'addr_')]`, decided 2026-09-23 — closes `contact.md`'s «snapshot shape (P3)»): the ten fields of module-contact's `Address`, one flat column each — readable and searchable with a query tool like the `DECIMAL` amounts (ADR-042), no JSON to parse — and one class the dunning notice (P4) and the quote (P7) reuse (Rule 8). No reference to `address` or `contact_address`: copied, never linked (§4a). The service snapshots the contact's `invoice`-typed address, else `main`, else the first; a draft may pass its own snapshot (an order whose invoice address was chosen at order time). Getters and `isComplete()` only — the printed block (line order, country prefix) arrives with the PDF in part 3.
- **Table `invoice_line`**: `position` (children directly after their parent; NOT unique — Doctrine inserts before it deletes on a re-issue, the `journal_line` argument), `parent_line_id` (self FK, ONE level: a priced line carries lines beneath it — a package with its contents at 0.00, §13 / A-Pos), `type` (`LineType`: `service` | `lump-sum` | `text` | `rounding`; `subtotal` is named in the plan and not built — nothing prints it), `text` (TEXT, the editable snapshot, may span lines), `quantity` (`DECIMAL(12,3)` string — three decimals, negative allowed, null on lump sum / text / rounding), `unit`, `unit_price` (money, null on text / rounding), `discount_percent` (hundredths, 2 % = `200`), `amount` (STORED, as printed — net or gross per the document's mode; rounded once per step: quantity × price, then the discount), `tax_code` + `tax_rate` + `tax_label` (the `vat.md` rule: a DOCUMENT line snapshots rate AND label), `revenue_account` (BY NUMBER), `source_type` / `source_ref`. A priced line needs unit price, tax code and account; a text line has none of them and no amount; the rounding line is the ONE system line (never in a draft — refused), at the top level, on `debtorAccounts → rounding` (3809), without tax.
- **Table `invoice_tax`**: the tax summary STORED, one row per code — `tax_code`, `tax_category` (what the adapter resolves the VAT account from), `tax_label`, `tax_rate`, `tax_base` (Σ of the code's lines, net), `tax_amount` (rounded ONCE, half away from zero — ADR-041 decision 5). This is `TaxSummaryEntry` of module-vat persisted; module-vat carries no serialisation (`vat.md`'s deferred item, closed here). The tax per LINE is deliberately not stored; when the posting needs it, each code's tax is distributed over its lines with `Money::allocate()`.
- **Migration** `Version20260923043935` (`res/migrations`): generated with `z77-db diff` against the module's first migration, reviewed — `utf8mb4_unicode_ci`, `ENGINE = InnoDB` spelled out, Doctrine-named FKs and indexes kept, expand only — plus ONE data step: `INSERT … number_range ('invoice', 0), ('credit-note', 0) ON DUPLICATE KEY UPDATE` (below). `tests/module-debtor.php` A applies both migrations and proves `diff` reports «No changes» afterwards, embedded and decimal columns included.

### `InvoicingService` — the single entry for every source

- **`invoice(InvoiceDraft): Invoice`** (plan §6.2, ADR-040 decision 3): everything is decided BEFORE the unit of work (`compose()` — the party, its profile and terms, the address, the lines with their amounts, VAT once through `VatCalculator` by the SERVICE date, the accounts softly against financial, the totals and the rounding), so a refused draft never takes a lock or draws a number (the `LedgerService::post()` order). Inside `getTransaction(Invoice::class)->run()`: the number from `NumberRangeRepository::next('invoice' | 'credit-note')` as the FIRST write (lock order), the entity, `issue()`, `persist()`. Joins an open unit of work (an order that changes its status and invoices in one — nesting joins) or opens its own. **Nothing is posted.**
- **The draft** (`Invoicing/InvoiceDraft`, `LineDraft`): kind, contact BY ID, invoice date, service date or period (null on a credit note = the invoice's), currency, price mode, payment terms code (null → the profile's default), an optional address snapshot, the lines (`LineDraft::service()` / `lumpSum()` / `text()`, `->beneath(...)` for children), an opaque origin, and for a credit note the invoice it corrects. Plain data — the rules live in the service and come back as `InvoiceRefusedException` with a stable `reason` (`contact-unknown`, `contact-inactive`, `no-debtor-profile`, `debtor-inactive`, `terms-unknown`, `terms-inactive`, `no-address`, `address-incomplete`, `currency`, `dates`, `no-lines`, `negative-total`, `credit-note-target`, `credit-note-rate`, `not-invoicing`, `not-found`, `kind-changed`, `line`, `line-tax-share`, `tax-code-unknown`, `tax-code-inactive`, `no-tax-rate`, `account-not-postable`) and a German message the part-3 screens print as it is.
- **The reference rule on a document** (ADR-043 decision 19): a NEW document needs an ACTIVE contact, an ACTIVE debtor profile, ACTIVE payment terms and ACTIVE tax codes; a re-issue keeps what the document already carries (its contact, its terms code, its tax codes) even if deactivated since. A contact without a debtor profile is not invoiced (`no-debtor-profile`) — the profile carries the terms, and there is no global default.
- **Money and rounding**: the line amount = unit price × quantity (`Money::multiply()` with the decimal string), then minus the discount (`multiplyByRatio()`), each rounded once; the tax on the sum per code once (`VatCalculator`); the document total to 0.05 once — `Money::roundTo(5)` on the gross, the difference as the rounding line; a rounding of 0.00 writes no line. The 0.05 step applies to **CHF** (`InvoicingService::ROUNDING_STEPS`, a constant map — the one currency there is, Q6); another base currency rounds to 0.01 (no line). An invoice's gross must not be negative (`negative-total` — that is a credit note), a credit note's must be positive.
- **`reinvoice(int $id, int $expectedVersion, InvoiceDraft): Invoice`** — only in `invoicing`: the row is re-read under an exclusive lock (`InvoiceRepository::lockForUpdate()`, the `ManualEntryService` model), a stale version is `InvoiceConflictException`, a `final` document `not-invoicing`, a changed kind `kind-changed`, another party or target `credit-note-target`; then `Invoice::reissue()` replaces the header snapshot, the lines and the tax rows whole (orphan removal deletes the old rows at flush), stamps `changed_by/at` and bumps `version`. The same number; nothing to reverse — nothing was posted. The snapshot MOVES with a re-issue (the address and terms as they read now): a re-issue is a new document under an old number.
- **`finalize(list<array{id, version}> $documents): list<Invoice>`** — a batch, ONE unit of work, all or nothing: (1) every row locked `FOR UPDATE` in **id order**, missing → `not-found`, at another VERSION than the caller saw → `InvoiceConflictException` (review 2026-09-23, DEBTOR-FINAL-001 closed: the part-3 screen is the first caller and carries `version` per row, so a document re-issued between the caller's look and its finalize is refused instead of being finalized with content nobody checked — the `reinvoice()` model), already final → `not-invoicing`; a bare id is a programming error (`InvalidArgumentException`); (2) per document, in the order given: `PostingBuilder::build()` → `AccountingGateway::post()` → `Invoice::finalize($ref)`.
- **Lock order in `finalize()` (decided 2026-09-23):** the rows are locked BEFORE any number is drawn. Two overlapping batches that each locked one row and then drew from `journal-entry.{code}` would deadlock (A holds row 1 and the range, waits for row 2; B holds row 2, waits for the range); with all rows locked first in one order, B waits at row 1 until A commits. The locks in play today: `invoice()` draws the kind's range (`invoice` or `credit-note`, exclusive) and then INSERTs the row — and for a credit note that insert takes an **implicit SHARED lock on the referenced invoice row** through the `credit_note_of_id` foreign key; `finalize()` takes the document rows exclusive and then draws `journal-entry.{code}`; `reinvoice()` takes one row and draws nothing; financial's `post()` locks accounts shared after its range. So `invoice(credit note)` holds `credit-note` → wants invoice row (S), while `finalize()` holds invoice row (X) → wants `journal-entry.*`: two DIFFERENT ranges, no cycle — **only because `finalize()` never draws the `credit-note` range**. A later «finalize plus automatic credit note» inside one `finalize()` (holding invoice rows X, then drawing `credit-note`) would meet a concurrent `invoice(credit note)` (holding `credit-note`, waiting for the invoice row's S lock) head-on: a deadlock. Whoever builds it draws every range FIRST or issues the credit note in its own unit of work (ADR-039 decision 10, `NumberRange` first).
- **Finalizing twice is REFUSED**, not idempotent (decided 2026-09-23): a batch that names a final document is a stale list, and the caller should see that rather than a silent «done» — the `already-reversed` model of `reverse()`, not the idempotency of `post()`.
- **What the port sees** (`Invoicing/PostingBuilder`, plan §6.2 «receivable / revenue per line + VAT per code + rounding», ADR-041 decision 7 net method): `receivable` (`debtorAccounts`) DEBIT gross; per priced line with an amount CREDIT its revenue account with the line's NET amount carrying `taxCode`, `taxRate`, `taxBase` = that net and `taxAmount` = the line's SHARE of its code's tax; per tax code CREDIT the VAT account of its CATEGORY (`PostingLine::vatCredit()` — the number is the bookkeeping's setting, resolved by the adapter); the rounding line CREDIT (rounded up) or DEBIT (rounded down) 3809 without tax. A negative line posts on the opposite side with negative tax data (the sign convention of financial's manual forms); a credit note swaps every side and negates every tax figure. Σ debit = Σ credit by construction (gross = net + tax + rounding). Text = `{Rechnung|Gutschrift} {number} · {address name}` (deterministic — FIN-IDEM-002), origin = kind / number, key = `{kind}:{id}:final`. A document whose posting would have fewer than two lines (a text-only document) posts nothing and keeps a NULL ledger reference.
- **The per-line tax share** (`Invoicing/TaxShares::distribute()`, decided 2026-09-23): each code's tax (the tax row, rounded once) is distributed over its lines with `Money::allocate()` by the lines' absolute amounts — largest remainder, Σ per code = the tax row exactly (33.33 / 33.33 / 33.34 at 8.1 % → 2.70 / 2.70 / 2.70 = 8.10). Lines of one code with MIXED signs are split first: the positive group takes the tax on ITS sum (`VatCalculator::taxOf()` / `taxIn()`), the negative group the remainder, so a deduction carries a negative share and the code's total still equals the row (+100 / −30 → 8.10 / −2.43 = 5.67). In gross mode a line's net is its gross minus its share. **Gross mode, Rappen lines** (review 2026-09-23): a share ≥ its line's gross would leave a net of 0.00 or less — the posting would drop that line and the VAT return sum less tax than the VAT line carries. Such a share is set to 0 and moved to the LARGEST line of the same sign group, which must keep a positive net (20 × 0.01 + 0.30 → the 0.04 sits on the 0.30 line, the Rappen lines post at 0.01 without tax); when no line can absorb it (100 × 0.01, tax 0.07) there is no honest per-line split and the DRAFT is refused at issue (`line-tax-share`, `compose()` runs the same distribution) — decided over «fix at finalize» because a refusal after the number is drawn would leave a document that can never be finalized. In net mode a share is always smaller than its line; nothing moves.
- **`openAmount(Invoice): Money`** — DERIVED (plan §6.3, never stored in parallel): gross − Σ gross of the FINAL credit notes referencing the invoice (`InvoiceRepository::sumOfFinalCreditNotes()`, one SQL aggregate); P4 subtracts payments, discount and loss. Zero while `invoicing` (§6.2: no open item yet) and for a credit note (it reduces one). Negative = more was credited than invoiced. **No `OpenItem` table** (decided 2026-09-23 against §6.1's row): nothing in this state reads one — the `final` invoice row IS the open item (identity, amount, due date, party are all on it), and building the table now would fix a shape P4 has not needed yet (the dunning fee «as its own open item», §6.5, is P4's design). If P4 wants the entity, it is a new table fed from `finalize()`, not a change to issued documents.
- **The credit note** (plan §6.2): `InvoiceDraft::creditNote($invoiceId, …)`, refused against an invoice still `invoicing` (`credit-note-target` — nothing is posted there, the correction is `reinvoice()`, and a credit note would mirror a posting that does not exist), against another party's invoice, against a credit note, or at 0.00. Nothing caps the credited amount (decided 2026-09-23, see known issues). Its posting mirrors the invoice's; the invoice's open amount drops by its gross once it is `final`.
- **A credit note follows the RATE of the original supply** (review 2026-09-23, ADR-041 decision 4 — a reduction of consideration is taxed as the supply was): `creditNote()` takes `serviceFrom` / `serviceTo` from the INVOICE unless the draft names its own (a partial period); a credit note issued in 2026 against a 2023 invoice therefore resolves 7.7 %, and 2200 goes back to zero instead of keeping the 0.40 an own 2026 date would leave (the return would report the reduction under 8.1 %). When the draft names its own date, `compose()` compares every code the invoice carries: a resolved rate that differs from the invoice's snapshot is refused (`credit-note-rate`, the message names both rates); a code the invoice never carried resolves by the date given.
- **Who**: `Services/Actor` — the same resolution as financial's (`AuthUser` name, refuses to guess); a CLI caller passes the name. Repeated rather than imported because financial may be absent (Rule 8 deferred: it moves to the kernel `shared` when a third module needs it — pending).
- **`DocumentText::resolve(texts, language, default)`** — the per-language resolver part 1 left out: the document's language, else the installation's default language, else ''. The invoice snapshots the result as `terms_text`.

### The accounting port (plan §6.6)

- **`Accounting\AccountingGateway { post(PostingRequest): ?string }`** — the port; **`PostingRequest` / `PostingLine` are DEBTOR'S OWN DTOs** (decided 2026-09-23, a deviation from §6.6's wording «the DTO is financial's»): if the interface named financial's class, `InvoicingService` would build a financial object and an installation without module-financial would fatal at `finalize()` — the very case `NullAccountingGateway` exists for. Debtor's DTO mirrors financial's shape (date, text, opaque origin, key, lines with account / debit / credit / tax data) and validates the same invariants (≥ 2 lines, one currency, balanced); the adapter translates 1:1. The one addition: a line may name its account by **VAT category** instead of a number (`PostingLine::vatCredit()` / `vatDebit()`) — which account the VAT of a category goes to is financial's `vatAccounts` (Rule 2, the one place), so debtor names the category and the adapter resolves the number through `LedgerService::vatAccountFor()`, refusing a missing or non-postable one with `AccountingRefusedException` `vat-account-missing` naming the config key.
- **`LedgerAccountingGateway`** (the default): joins the caller's unit of work, calls `LedgerService::post()`, answers `EntryRef` as ONE string `{fiscal-year}/{number}` — how the document stores it (`invoice.ledger_entry_ref`, `VARCHAR(32)`; closes financial's pending «EntryRef storage shape»). Financial's `PostingRefusedException` (no fiscal year, period closed / VAT-settled, account unknown / group / inactive, tax code unknown, idempotency conflict) comes back as `AccountingRefusedException` with the same `reason` and the original as `getPrevious()`. Deliberately NO catch of the unique-index failure at commit and NO retry (`financial.md`, the race contract): both end the caller's unit of work, no journal number is consumed, the documents stay `invoicing`; a retry is a new `finalize()`. Its constructor refuses to run when `financial` is not a REGISTERED module (`AccountingUnavailableException`, through `LedgerAccountCheck::available()`).
- **`NullAccountingGateway`**: `finalize()` sets `final`, the open amount exists, nothing is booked, `ledger_entry_ref` stays NULL. Configured EXPLICITLY — never a fallback for a missing financial: an installation that keeps its books elsewhere says so.
- **Selection by config** (`debtorConfig → accountingGateway`, a class name — the `memberConfig` hook pattern, ADR-038; read by `Accounting\AccountingGateways::fromConfig()` at the point of use): the package config names `LedgerAccountingGateway`; a project without z77 bookkeeping writes `NullAccountingGateway::class` into its override — which, BOOT-CONFIG-001, must carry the FULL config. A missing key is `UnexpectedValueException`, an unknown class or one that is no gateway `AccountingUnavailableException`. Every gateway takes `(UnifiedEntityManager $em, string $actor)`. `InvoicingService` accepts a gateway in its constructor (the harness injects the Null one) and builds the configured one otherwise.
- **Idempotency**: the key `{kind}:{id}:final` is stable across retries and the content deterministic, so a `finalize()` retried after a failed commit returns the existing entry from the ledger — and is then refused by debtor anyway, because the document is `final` only when that commit went through.

### Number ranges

**`invoice` and `credit-note`**, one per kind, gapless each (`uniq_invoice_kind_number`), drawn in `InvoicingService::invoice()` as the FIRST write of its unit of work; a re-issue draws nothing. **Created by the migration** `Version20260923043935` at 0 with the statement `NumberRangeRepository::create()` runs (decided 2026-09-23): DOCTRINE-NR-003 wants a range created and committed ahead of concurrent use, and the documents have no «opening» event like the ledger's fiscal year — the install is theirs. `down()` deletes the rows only while `last_number = 0` (the `dropUnused()` rule). The number is the bare integer; the document prints `Rechnung 12` / `Gutschrift 3` (`Invoice::documentName()`) — no prefix, no year segment (`persistence-doctrine.md`).

## rules

- When storing a percentage in this module (a discount tier) → MUST store an INTEGER IN HUNDREDTHS OF A PERCENT (2 % = `200`), as `TaxRate::$rate` does; MUST NOT store a float or a decimal string.
- When storing an amount on a FILE-based entity (the dunning fee) → MUST store integer minor units and build `Money` with the currency the caller passes (`DunningLevel::fee($currency)`); MUST NOT let the entity read `systemConfig` itself and MUST NOT store a decimal string.
- When a module-debtor class needs the base currency → MUST read it through `Services/DebtorCurrency::base()`; MUST NOT call `LedgerService::baseCurrency()` (module-financial is only `suggest`ed and may be absent) and MUST NOT hardcode `CHF`.
- When referencing payment terms, a payment target or a dunning level from a database row → MUST reference it BY `code` with no foreign key and MUST snapshot what it shows at the moment of use; MUST NOT add a cross-driver foreign key (ADR-043 decision 19).
- When a NEW reference to a file master-data row is created (a new profile, or an update that CHANGES the code) → MUST require the row to be ACTIVE; an UNCHANGED reference MUST be allowed to keep a deactivated row (`DebtorProfileValidator::$requireActiveTerms`).
- When a master-data row is no longer wanted → MUST deactivate it through `DebtorMasterData::set*Active()`, which checks the code and writes — MUST NOT run the field validator there, because a row that has BECOME invalid is exactly the one that has to be switchable off; MUST NOT add a delete method to `DebtorMasterData`, a repository or a screen.
- When a screen switches a master-data row active or inactive → MUST catch `DebtorException` and answer with a `fetchError`; MUST NOT let the refusal reach the user as a 500.
- When creating a NEW `DebtorProfile` → MUST require the contact to be ACTIVE (the reference rule on the party) and MUST NOT offer «Debitor anlegen» for an inactive one; MUST NOT block an EXISTING profile whose contact was deactivated since — it stays editable.
- When the `code` of an existing master-data row would change → MUST refuse it (`MasterDataCodeChangedException`) and create a new row instead; the edit form MUST render the code field read-only.
- When changing an EXISTING `DebtorProfile` → MUST hand `DebtorProfileService::update()` the cleaned VALUES so a detached clone is validated first (ADR-039 decision 9); MUST NOT mutate the managed entity in a controller before validation.
- When a screen or a service needs an account this module posts to → MUST ask `DebtorAccounts::number()` / `postableNumber()`; MUST NOT read `debtorConfig → debtorAccounts` anywhere else and MUST NOT name an account number inline (Rule 2).
- When asking whether an account may be posted to → MUST treat `LedgerAccountCheck::isPostable()` returning `null` as «cannot tell» and raise NO error; MUST NOT `use` a `Z77\Module\Financial\…` class anywhere outside `LedgerAccountCheck` and `LedgerAccountingGateway` (ADR-040 decision 5).
- When deciding whether module-financial can be asked → MUST require BOTH that the class autoloads and that `financial` is a registered module (`LedgerAccountCheck::available()`); MUST NOT rely on `class_exists()` alone — an unregistered package in `vendor/` has no config and no booted metadata, and asking it fatals.
- When validating an IBAN → MUST check shape, MOD-97-10 check digits and CH / LI origin separately through `Services/Iban` so the message says what is wrong; MUST NOT accept a non-Swiss IBAN as a payment target (a QR-bill names a CH or LI creditor account).
- When deciding whether an IBAN is a QR-IBAN → MUST read the IID (positions 5–9) and test 30000–31999 through `Iban::isQrIban()`; MUST NOT infer it from the bank name or the reference type.
- When adding a per-language master-data text → MUST run it through `Validators/DocumentTextRule` (a language of this installation, and the default language filled as soon as any other is); MUST NOT store a text under a language the installation does not serve.
- When seeding a master-data row → MUST leave `document_text` out (an empty text is valid), so an installation in any language starts with valid rows; MUST NOT ship German wording an installation would have to correct before it can save the row.
- When a second entity in this module needs a per-language text or the same `code` / `label` rules → MUST use `Entities/HasDocumentText` and `Validators/ValidatesMasterDataRow`; MUST NOT copy the setter or the two validate methods (Rule 8).
- When a dunning fee is modelled or posted → MUST keep it free of VAT (plan §6.5); MUST NOT add a tax code to `DunningLevel` or a tax line to its posting.
- When adding a backend screen to this module → MUST build it as a fragment trait + layout in `module-debtor` with a thin host in `module-backend` under the `finance` group (ADR-018), German labels and no JavaScript (Rule 7); MUST NOT change anything in `module-contact` to reach a contact-related screen (plan §2).
- When a document range is needed → MUST be created by the migration that ships the documents that draw from it (`invoice`, `credit-note` in `Version20260923043935`, at 0, the `create()` statement); MUST NOT draw a first number to create it and MUST NOT read or write `number_range` any other way than through `NumberRangeRepository::next()` in `InvoicingService::invoice()`.
- When ANY source issues an invoice or a credit note (an order, a manual screen, a contract or fee run, a script) → MUST build an `InvoiceDraft` and call `InvoicingService::invoice()`; MUST NOT `persist()` an `Invoice`, draw from `invoice` / `credit-note`, or post to the ledger itself (ADR-040 decision 3, one write path). The ONE exception is the wdv import (ADR-040 decision 9, plan §8), which writes documents directly and posts nothing.
- When a document in `invoicing` is wrong → MUST re-issue it through `InvoicingService::reinvoice($id, $version, $draft)` with the version the caller saw; MUST NOT mutate a loaded `Invoice`, its lines or its tax rows (there are no setters), and MUST NOT expect a re-issue to keep the old address or terms — the snapshot moves with it.
- When a `final` document is wrong → MUST issue a credit note against it (`InvoiceDraft::creditNote()`), lines as printed, positive; MUST NOT edit, delete, cancel or re-issue it — the entity and the service both refuse (plan §1, correction principle), and no such method exists.
- When calling `InvoicingService::finalize()` → MUST hand it `['id' => …, 'version' => …]` pairs with the version the caller SAW (the hidden field of the screen, `Invoice::getVersion()`) for documents still `invoicing`, and let `InvoiceRefusedException` / `InvoiceConflictException` / `AccountingRefusedException` (and a unique-index failure at commit) end the call; MUST NOT pass the version stored NOW instead of the one seen, MUST NOT catch inside and retry, and MUST NOT treat a repeated `finalize()` of a final document as success (it is refused with `not-invoicing`).
- When issuing a credit note → MUST leave `serviceFrom` / `serviceTo` out of `InvoiceDraft::creditNote()` unless the credit note covers a partial period of the invoice, so the rate of the ORIGINAL supply applies (ADR-041 decision 4); MUST NOT date the supply of a credit note by its own issue date — a rate that differs from the invoice's is refused (`credit-note-rate`).
- When a gross-mode draft is refused with `line-tax-share` → MUST merge the Rappen lines into one or capture the document net; MUST NOT weaken `TaxShares` to let a posted line carry a net of 0.00 (the VAT return would then sum less than the VAT line) and MUST NOT move the check to `finalize()`.
- When a future `finalize()` variant would issue a document of its own (an automatic credit note, a fee) → MUST draw every range it needs BEFORE it locks any document row, or issue the document in its own unit of work; MUST NOT draw `credit-note` while holding invoice rows exclusive — a concurrent `invoice(credit note)` holds that range and waits for the FK share lock on the invoice row (the lock-order paragraph above).
- When posting from this module → MUST go through the `AccountingGateway` port with debtor's `Accounting\PostingRequest`; MUST NOT `use` a `Z77\Module\Financial\…` class anywhere but `LedgerAccountCheck` and `LedgerAccountingGateway` (harness I16 counts exactly two), and MUST NOT resolve a VAT account number in debtor — name the tax CATEGORY on the line (`PostingLine::vatCredit()`) and let the adapter ask financial's `vatAccounts` (Rule 2).
- When an installation keeps its books outside z77 → MUST set `debtorConfig → accountingGateway` to `NullAccountingGateway::class` in the project's override (carrying the FULL config, BOOT-CONFIG-001); MUST NOT unregister module-financial and expect a silent fallback — the default gateway refuses to run (`AccountingUnavailableException`).
- When a new implementation of `AccountingGateway` is written (another bookkeeping, an export queue) → MUST join the caller's unit of work and never commit, MUST keep the idempotency key and the opaque origin, MUST raise `AccountingRefusedException` on a refusal and MUST take `(UnifiedEntityManager $em, string $actor)` in its constructor; MUST NOT retry inside.
- When a document needs a snapshot of an address (an invoice, a dunning notice, a quote) → MUST embed `Entities/AddressSnapshot` (`#[ORM\Embedded(columnPrefix: '…')]`) and fill it with `AddressSnapshot::of($address)` at issue; MUST NOT hold a foreign key to `address` or `contact_address` on the document (plan §4a, `contact.md`).
- When a line's tax must reach the ledger per line → MUST distribute the code's tax row with `Money::allocate()` (positive and negative lines as two groups) as `PostingBuilder::taxShares()` does; MUST NOT compute tax per line from the rate (ADR-041 decision 5) or round per line and sum.
- When rounding a document total → MUST round the GROSS once with `Money::roundTo()` at the document level and write the difference as the `rounding` line on `debtorAccounts → rounding`; MUST NOT round per line, inside the tax summary or in the calculator, and MUST NOT put a tax code on the rounding line.
- When a draft line needs a quantity → MUST pass a decimal STRING with at most three decimals (`'1.500'`, `'-1.000'`); MUST NOT pass a float (refused) or more decimals than the column holds.
- When reading a document's VAT, address, terms or totals anywhere (PDF, posting, dunning, discount) → MUST read the document's snapshot (`invoice.*`, `invoice_line.tax_rate` / `tax_label`, `invoice_tax`); MUST NOT resolve the tax tables, the contact's address or the terms row again (ADR-041 decision 6, plan §4a).
- When a document's payment-terms sentence is printed → MUST take `Invoice::getTermsText()` (snapshotted through `DocumentText::resolve()` in the document's language with the default-language fallback); MUST NOT read the terms row's text at print time.
- When deciding whether a document has an open amount → MUST call `InvoicingService::openAmount()` (derived: gross − final credit notes; P4 adds payments and allocations); MUST NOT store an open balance in parallel (plan §6.3) and MUST NOT count a document still `invoicing` as a receivable.
- When this module needs the current actor's name → MUST use `Services/Actor::current()` or pass the name explicitly (CLI, import, harness); MUST NOT import financial's `Actor` (financial may be absent) and MUST NOT invent a placeholder name.

## known issues

- **DEBTOR-ROUNDING-001** — resolved 2026-09-22 (owner): the invoice rounding gets its OWN account. `3809 «Rundungsdifferenzen»` was added to `packages/module-financial/res/charts/kmu.json` in group 38 and `debtorAccounts.rounding` points at it, so rounding and discount stay separable in the reports. Don't assume an installation that adopted the chart BEFORE this row exists has it — the chart is adopted by button into an empty chart and is never re-applied; such an installation adds 3809 by hand or repoints the key.
- **DEBTOR-FEE-ACCOUNT-001** — resolved 2026-09-22 (owner): the dunning fee stays on `6950 Finanzertrag`. Reason on record: the fee is damages for the delay, not a service — no VAT and no turnover, so it belongs outside the revenue classes 3.
- **DEBTOR-TEXT-DROP-001** — don't assume a document text survives a language being dropped from the installation. `DocumentTextForm::posted()` builds the texts from `I18n::getLanguages()`, so the next EDIT of a row silently drops what stands in a language the installation no longer serves; the row is saved without it and nothing says so. The row can still be deactivated (`set*Active()` is a pure state change), and re-adding the language does NOT bring the text back — it is gone from the file at the first save.
- Don't assume a document text resolves by itself — `PaymentTerms::getDocumentText()` / `DunningLevel::getDocumentText()` return the RAW map. The fallback to `defaultLanguage` arrives in part 2 with the document that prints it; validation already guarantees the default language is filled whenever anything is.
- Don't assume an account number in `debtorAccounts` or on a `PaymentTarget` was verified. Without a REGISTERED module-financial `LedgerAccountCheck` answers `null` and nothing is checked — the number is an unverified string until part 2 posts with it. Nor does a check that passed stay true: the account can be deactivated or turned into a group afterwards, which is one reason `set*Active()` does not validate.
- Don't assume `DebtorProfile` is a complete debtor record. Part 1 carries what §6.1 names minus language and currency; the documents arrived in part 2, payments and dunning history arrive in P4.
- BOOT-CONFIG-001 applies to `debtorConfig.inc.php` like every module config: a project override REPLACES it, so it must carry the full `debtorAccounts` map AND `accountingGateway` — a dropped `accountingGateway` is an `UnexpectedValueException` at the first `finalize()`.
- **DEBTOR-FINAL-001** — resolved 2026-09-23 (review): `finalize()` takes `{id, version}` pairs and refuses a stale version with `InvoiceConflictException` before anything is posted. What remains: don't expect the conflict to name what changed — the caller reloads the list and sees the current document, like `reinvoice()`.
- **DEBTOR-CREDIT-RATE-001** — resolved 2026-09-23 (review): a credit note resolves its rates by the INVOICE's service date unless the draft names its own, and an own date that yields another rate for a shared code is refused (`credit-note-rate`). What remains: don't assume the check covers a code the invoice never carried — that code resolves by the date given, because there is no original rate to follow.
- **DEBTOR-RAPPEN-001** — resolved 2026-09-23 (review): in gross mode a tax share that would zero a line moves to the largest line of its sign group, and a code whose lines cannot carry the tax at all refuses the draft (`line-tax-share`). Don't assume the same for net mode: there a share is always smaller than its line, and nothing is moved or refused.
- **DEBTOR-PERIOD-001** — don't assume a service PERIOD spanning a VAT rate change (2023-12 → 2024-02) is apportioned: the rate resolves by `service_from` for the whole document (one service date per document, `VatCalculator`). A period across a rate change is two documents (or two lines on two documents); the source decides.
- **DEBTOR-ROUND-001** — decided 2026-09-23 (orchestrator): the 0.05 step STAYS a constant (`InvoicingService::ROUNDING_STEPS = ['CHF' => 5]`); every other currency rounds to 0.01 and writes no rounding line. A setting arrives with a second base currency, not before. Don't add a config key for it.
- **DEBTOR-CREDIT-001** — decided 2026-09-23 (orchestrator): the credited amount stays UNCAPPED — several credit notes against one invoice may exceed its gross, and `openAmount()` then goes NEGATIVE (a refund is owed). Goodwill happens; a screen may show the negative value, nothing refuses it.
- **DEBTOR-ACTOR-002** — decided 2026-09-23 (orchestrator): `Actor` exists twice (financial, debtor) on purpose until a THIRD module needs it; then it moves to the kernel `shared` in one change. Don't lift it earlier, don't make debtor import financial's.
- **DEBTOR-OPEN-001** — don't look for an `open_item` table: the open amount is derived (`InvoicingService::openAmount()`) and covers credit notes only. Payments, discount and loss (P4) are not subtracted yet, so the value is «open before any payment» until P4 exists.
- **DEBTOR-TEXT-001** — don't assume the journal text of a posting is stable across an address change: it is built from the document's SNAPSHOT (`{kind} {number} · {addr_name}`), so it is stable for a given document (FIN-IDEM-002) — but a re-issue that changes the address name changes the text of the posting that follows. Harmless: a re-issue happens before the one posting.
- **DEBTOR-ACTOR-001** — don't assume `InvoicingService` can be constructed without a session or an explicit actor: `new InvoicingService($em)` resolves `Actor::current()` in the constructor and refuses (`LogicException`) in a CLI without a logged-in user — pass the name (`new InvoicingService($em, 'import:wdv')`).
