## mental model

`z77/module-debtor` (plan §6, ADR-040) is the receivables side: it owns invoicing and the open amounts, and it reaches the bookkeeping only through a port — the package *suggests* `z77/module-financial` and requires kernel, `persistence-doctrine`, `module-vat`, `module-contact` and — since owner decision E2, 2026-09-23 — `module-mandator`, whose one record carries the account settings this module posts with ([`mandator.md`](mandator.md)) (plan §2). **P3 part 1** built the MASTER DATA: the debtor profile per contact, and the three file-based types an invoice, a payment and a dunning notice are built from. **P3 part 2, this state, builds the documents**: `InvoicingService` as the single entry for every source, `Invoice` (invoices AND credit notes, one entity), the states `invoicing` / `final`, the 0.05 rounding line, the two number ranges, the full snapshot, and the accounting port `AccountingGateway` with its ledger adapter and its Null implementation. **P3 part 3 (2026-09-30)** added the payment part of a document (the QR-bill DATA, from the snapshot — the PDF itself waits for the owner's decision on a PDF library) and the document screens; **P4 (2026-10-06/07)** added the settlements — payments, discount and loss with their postings, correctable while the year is open (part 1) —, the CAMT.054 import (part 2) and the dunning with the fee as a document kind (part 3); there is no `OpenItem` table, the open amount is derived. Nothing here exists without a caller in this state (guiding rule: nothing in stock). The package is required in the monorepo ROOT `composer.json` only — NOT in `skeleton/composer.json`, like `module-contact` and `module-financial`; a project requires it when it needs it. There are therefore no `RUNTIME=` paths: the seeded `data/framework/debtor/*.json` come into being in a PROJECT that installs the package, not in the skeleton.

### `DebtorProfile` (Doctrine)

- Table `debtor_profile`: `contact_id` (FK to `contact`, **unique** — `uniq_debtor_profile_contact`), `customer_number` (INT, **unique** — `uniq_debtor_profile_number`, since `Version20261006100000`), `payment_terms_code` (VARCHAR 16, indexed `idx_debtor_profile_terms`), `dunning_block`, `price_mode` (VARCHAR 5, `net` | `gross`, DEFAULT `net` — since `Version20261018130000`, «The debtor carries the PRICE MODE» below), `active`. Keyed by the contact's id in DEBTOR's table — not one column of it lives on `contact` (plan §2, §4a: contact knows no module).
- **The customer number** (owner 2026-10-06: an OWN number range, not the record id — offices identify a customer by a number of their own, the wdv-630 `client_no` model): drawn from the gapless range `customer` by `DebtorProfileService::save()` as the FIRST write of its unit of work (the `InvoicingService::invoice()` model — validation before, the draw and the insert together, a refused insert rolls the draw back), assigned once through `DebtorProfile::assignCustomerNumber()`, **never typed and never changed** — there is no setter, so no form body and no import array reaches it. It is the second field of the QR reference (positions 11–16, `Invoicing/QrReference`). Shown on the debtor list and read-only on the form. **Numbers start at 1000** (owner 2026-10-06, `Version20261006100000::FIRST_NUMBER`): existing profiles were numbered 1000, 1001 … in id order by the migration, the range seeded at 999. The numbers of an existing business are NOT drawn — they come with the wdv import (`## pending`). DOCTRINE-NR: the number is the bare integer; padding belongs to the reference.
- **At most one profile per contact**: `DebtorProfileValidator` asks first so the screen gets a field error; the unique index decides under a race, and `DebtorProfileService::flushOrRefuse()` turns its violation into the same field error (the `AccountService` model).
- **A NEW profile needs an ACTIVE contact** (decided 2026-09-22 on review): the reference rule of ADR-043 decision 19 applied to the party — a new reference needs an active row, and a debtor is a reference to a contact. An EXISTING profile on a contact deactivated SINCE keeps working and stays editable, because open items and documents are already written against it. The role «Debitor» in the contact editor therefore cannot be switched on for an inactive contact (since 2026-10-12; before, «+ Debitor» offered only active contacts) and its `switchOn()` refuses with the same sentence; the validator says it again on save.
- **No `language`** (decided 2026-09-22): `Contact::$language` already says which language a document to this party is written in (plan §4a). A second field would be a second truth about one fact (Rule 2).
- **No `currency`** (decided 2026-09-22): the Bauplan §6.1 lists it, but Q6 decided against foreign-currency invoicing and §6.2 puts currency and rate on the DOCUMENT, not on the party. On the profile it would be an unread column with no caller; part 2 adds it to the invoice, where it is read. Adding it later is a new column on a new table, not a change to issued documents.
- **Payment terms are REQUIRED** on every profile (decided 2026-09-22): a profile without terms would leave a document with nothing to fall back on. The 2026-09-22 half «there is no default» is **REPLACED for new debtors by the owner decision of 2026-10-12** (next bullet).
- **Default payment terms for a NEW debtor** (owner decision 2026-10-12, «neue Debitoren erhalten standardmässig 30 Tage netto»): the default is a **`default` marker on exactly one `PaymentTerms` row** — not a debtor or mandator setting naming a code. Why the row (Rule 2): the terms are maintained on the payment-terms screen, so the marker is set where the terms live; a setting naming a code could point to a row that does not exist or is inactive, the marker cannot; and it needs no second place to keep in step. **Read in ONE place**: `PaymentTermsRepository::defaultForNewDebtor()` — the marked row, or null when none is marked or the marked row is INACTIVE (an inactive row is never given to a new reference, ADR-043 decision 19). **Used by** (1) `InvoicingService::profileToOpen()` — the profile a first draft opens gets the default (DEBTOR-CONTACT-001), (2) the editor — `?contact=` of a contact without a profile preselects it, and «wie beim Debitor» shows what it means for a new debtor, (3) the contact editor's role «Debitor» (owner 2026-10-12, below) — the profile it opens gets it; until 2026-10-12 «+ Debitor» preselected it, (4) the wdv import (not built) — a profile without terms falls back to it. **Profile = default, the draft may deviate** (decided 2026-10-12): the profile is the STANDING agreement and gets the default even when the first draft names other terms; terms a draft names apply to that document only (the document already carries its terms by code, «Documents» below). **No active default** → the behaviour before: the profile takes the terms the draft names, a draft without terms is refused with what to choose, the role «Debitor» cannot be switched on (it names what to mark). Nothing is ever invented.
- **The debtor carries the PRICE MODE** (owner decision 2026-10-18, [ADR-043 addendum 2026-10-18](../02-decisions/adr-043-order-status-and-stock-movements.md) «price mode»; after the bug report of the day: an order showed an article of 16.65 gross as 15.40 whatever its «Preise», because every order started `net`): `price_mode` `net` | `gross` (module-vat's `PriceMode`, `DebtorProfile::priceMode()`; validator `validatePriceMode()` — «Preise netto oder brutto wählen.»). A NEW order or invoice with a preset customer starts with it, a customer CHOICE sets the document's «Preise» (`customerChosenAnswer()` → core.js `set-value` on the editor's `select[name="price_mode"]`); the document may deviate — its own `price_mode` stays the truth. **The invoice editor converts typed prices at once** when «Preise» changes (owner 2026-10-19, the order window's behaviour): core.js «price mode» with the form as the scope, each row's MWST select carrying its rate per option (`data-rate` from module-vat's `VatRates::shownRates()` on the service date, else the invoice date; `taxCodeSelect` `rates`), core.js «dated rates» re-reads the rates when «Leistung ab» changes and keeps the CODE labels (`data-rate-keep-label`). The invoice has no article prices, so every price converts with its row's rate — module-vat's `VatCalculator::convertPrice()`, the ONE rule the order uses too (2 decimals, half away from zero). Server safety net (Rule 7): the hidden `prices_mode` — when it names the other mode (no script, a stale client) `InvoiceForm::toDraft(VatRates)` converts the prices by the same rule; an unknown `prices_mode` is refused on `price_mode`, a code without a rate on that day on the row's price. Edited in the profile dialog («Preise»), asked in «Debitor anlegen» (the customer picker below), `net` for every profile that existed (the column default) and for the role «Debitor» (its summary says «Preise netto» / «brutto»).
- Write path `DebtorProfileService`: `open($contact, $termsCode, $priceMode = 'net')` (since 2026-10-18 — THE path that makes a contact a debtor: the role «Debitor», `InvoicingService::openDebtorProfile()` and the picker's «Debitor anlegen» all call it; a new profile through `save()`), `save($new)` (draws the customer number, one unit of work), `update($profile, $values)` (values onto a detached clone, validated, only then applied to the managed entity — ADR-039 decision 9), `setActive()`, `delete()` (since 2026-10-12, next bullet). The 2026-09-22 rule «no delete anywhere» is **narrowed by the owner decision of 2026-10-12**: a profile is deleted only while NOTHING references its contact; once one document exists, invoices and open items are written against the party and the profile is only deactivated.
- **«Debitor» is a ROLE of the contact, switched in the CONTACT editor** (owner decision 2026-10-12: «Stammdaten › Aufträge › Debitoren › + Debitor ist falsch und zu kompliziert — ein Kontakt, wo auch immer erstellt, wird im Kontakt-Editor als Debitor festgelegt; solange keine Belege daran hängen, kann der Debitor-Status wieder entfernt werden»). module-contact offers a generic, opt-in extension point — the **contact-role registry** `Contact\Roles\ContactRoles` (config key `contactRoles`, the `openWorkChecks` pattern, `contact.md`); this module registers `'contactRoles' => ['debtor' => Roles\DebtorContactRole::class]` in `debtorConfig`. module-contact renders the role and calls it, knowing nothing about debtor; the dependency stays debtor → contact (plan §2). `DebtorContactRole` answers:
  - **state**: on = a profile exists; the line «Kundennummer 1000 · 30 Tage netto» (« · inaktiv» for a deactivated profile), for a contact without one «erhält die nächste Kundennummer · 30 Tage netto»; a button «Debitor bearbeiten …» opens this module's profile dialog (`DebtorProfileLayout::BASE` + `/edit?id=`) for the further settings (terms, dunning block).
  - **on** — `switchOn()`: the server decides. Refused with a German sentence when the contact is INACTIVE (ADR-043 decision 19 on the party), is ALREADY a debtor, or no ACTIVE terms are marked «Standard» («… unter Stammdaten › Aufträge › Zahlungskonditionen eine aktive Kondition als «Standard» markieren»). Otherwise a new profile with the DEFAULT terms and price mode `net` through `DebtorProfileService::open()` → `save()` — the customer number drawn from `customer` in its own unit of work; the validator runs as for every profile.
  - **off** — `switchOff()` → `DebtorProfileService::delete()`: only while NO document — invoice, credit note, fee; any state, drafts included — is written to the contact (`InvoiceRepository::countForContact()`); payments (their allocations) and dunning notices hang on documents, so none of them can exist either. Then the row is DELETED, not deactivated. Otherwise refused (`DebtorProfileInUseException`): «… hat n Belege — der Debitor kann nicht mehr entfernt, nur deaktiviert werden (Stammdaten › Aufträge › Debitoren, Schalter der Zeile)» — the existing active switch of the master-data row is the offered alternative; the state shows the switch disabled with that reason.
  - **The customer number of a deleted profile is NOT reused**: `customer` is never lowered, the number stays a gap (DOCTRINE-NR: a range only counts up; a number once drawn is never handed out again — even one that was printed nowhere yet). Switching the same contact on again draws a NEW number.
  - **Compatible with ADR-043 decision 19 and the correction principle**: the decision forbids deleting referenced MASTER-DATA rows (file-based types); a debtor profile with no document references nothing and is referenced by nothing (`debtor_profile` is the referencing side, documents reference the CONTACT) — deleting it leaves no reference dangling, and the correction principle is about issued documents, of which there are none. No ADR is changed.
  - **Race «off» vs. a first draft** (lock pair): `delete()` locks the profile row EXCLUSIVE (`DebtorProfileRepository::lockForContact()`), then counts the documents with a locking read (`FOR UPDATE`); `InvoicingService::invoice()` locks the row of an EXISTING profile SHARED before it inserts the document (lock order profile row → invoice rows). Whichever comes second waits and sees the other's result: the delete counts the new draft and refuses, or the draft finds no profile and is refused `no-debtor-profile` — never a document without a profile.
  - **Where the switch appears**: the contact dialog of `/backend/contact/contact` — «Bearbeiten» (acts at once, answered in place) and «Kontakt anlegen» (a field, applied AFTER the contact is saved; a refusal leaves the saved contact and says why in the flash). NOT in the «+ Kontakt» window of the invoice editor: its save answers «Debitor anlegen» (since 2026-10-18; until then the first draft opened the profile, `invoice(openProfile: true)` — removed 2026-10-19) — a switch there would duplicate that path.

### File-based master data (three types, one rule set)

All three follow `module-vat`'s `TaxCode` pattern exactly (including `setActive()`, below): `#[Entity('file', 'framework/debtor/…json')]`, seeded once on first install from `data/**/*.default.json` (ADR-024 seed-once, no installer change needed — the installer walks every framework package's data root), referenced BY `code`, code immutable, **deactivated and never deleted** (ADR-043 decision 19), UTF-8 without BOM (DATA-JSON-001). Their one write path is `DebtorMasterData`, which has no remove method at all.

**`set*Active()` is a PURE STATE CHANGE** (decided 2026-09-22 on review, the `VatMasterData::setActive()` model): it checks the code and writes the row — the field validator does NOT run. A row must be switchable off exactly when it has become invalid, and that is the normal reason to switch it off: a payment target whose ledger account was deactivated in the bookkeeping, or a row whose document text stands in a language the installation has since dropped. Running the full validator there would let the rule meant for NEW input forbid the cleanup. The validator runs where new input arrives — on a form save (`saveTerms()` / `saveTarget()` / `saveLevel()`). The three `toggleActiveAction`s still catch `DebtorException` and answer with a `fetchError`, so the one rule `setActive()` keeps (an unchanged code) never becomes a 500.

- **`PaymentTerms`** (`payment_terms.json`): `code`, `label` (German, for the backend list), `dueDays`, `discounts` (a list of `{days, percent}`, at most `MAX_TIERS` = 2, percent as an INTEGER IN HUNDREDTHS like the VAT rates — 2 % = `200`), `documentText` (per language), `active`, `default` (since 2026-10-12 — the terms a new debtor gets, at most one row, only an ACTIVE one; `DebtorMasterData::saveTerms()` MOVES the marker: saving a marked row unmarks every other row in the same flush and returns them, so the screen re-renders both rows; `PaymentTermsValidator::validateDefault()` refuses the marker on an inactive row; deactivating the marked row leaves the marker on it, and `defaultForNewDebtor()` then answers null). Seed: `net-30` «30 Tage netto» (**marked `default`** since 2026-10-12) and `disc-2-10` «10 Tage 2 %, 30 Tage netto» — **without a `document_text`** (owner, 2026-09-22): an empty text stays allowed, so an installation in any language starts with valid rows and writes its own wording. Two tiers are supported because three-step terms («3 % / 10 Tage, 2 % / 20 Tage, 30 Tage netto») exist in Swiss practice; the seeded example needs one tier plus `dueDays`.
- **`PaymentTarget`** (`payment_targets.json`): `code`, `label`, **two IBAN fields since P3 part 3** — `iban` (the PLAIN IBAN, reference type NON) and `qr_iban` (the QR-IBAN, QRR), both normalized upper-case without spaces, both optional, at least one set, each refused in the other's field —, the **creditor block** `holder_name` / `holder_street` / `holder_house_no` / `holder_zip` / `holder_city` / `holder_country` (the ACCOUNT HOLDER as registered with the bank, QR lengths 70 / 70 / 16 / 16 / 35 / 2 and the QR character set; empty = the mandator's field, `Services/Creditor`), `accountNumber` (the ledger account that bank account is booked on), `active`. **Not seeded** — an IBAN cannot be guessed and a placeholder would end up printed on a QR-bill; the file comes into being with the first row the backend writes.
- **`DunningLevel`** (`dunning_levels.json`): `code`, `label`, `level` (unique, the order a dunning run walks), `daysAfterDue`, `daysAfterPrevious` (owner 2026-10-13: the level is due no earlier than this many days after the invoice's LAST notice; no effect on an invoice's first notice; 0–365; a row without the key reads `DunningLevel::DEFAULT_DAYS_AFTER_PREVIOUS` = 10, so an installation's file needs no migration), `fee` (INTEGER MINOR UNITS — plan §3, `Money` is not a JSON row), `documentText`, `active`. Seed: `reminder` (level 1, 10 days, 0.00), `dunning-1` (level 2, 30 days, 20.00), `dunning-2` (level 3, 50 days, 40.00), each 10 days after the previous notice — **without a `document_text`**, for the same reason as the payment terms. **No tax code and never one**: a dunning fee compensates the effort of chasing a debt, it is not a supply (plan §6.5).

### Shared shapes (Rule 8)

Three pieces exist once instead of two or three times: `Entities/HasDocumentText` (the property, its normalising setter and its getter — `PaymentTerms` and `DunningLevel` both carry it), `Validators/ValidatesMasterDataRow` (the identical `code` / `label` rules of all three file entities, with the repository supplied by the using validator through `masterDataRows()`), and `Validators/DocumentTextRule` (the per-language rule itself).

### Text per language, label in German

Two texts, two audiences (decided 2026-09-22): `label` is the German name the BACKEND list shows, exactly as `TaxCode::$label` and `AddressType::$label` are; `documentText` is what prints on the customer's invoice or notice and is therefore kept per language. The languages are the installation's (`I18n::getLanguages()`, `i18n.md`), the default language first, and `DocumentTextRule` enforces both halves: a key must be a language this installation serves, and as soon as ANY language is filled the DEFAULT language must be too — it is what every other language falls back to (the `ContentService::find()` fallback part 2 will use). Leaving the text empty everywhere stays allowed. The **fallback RESOLVER is deliberately not built yet** — it arrives with the document in part 2, like `AddressTypes::resolve()` did for the address snapshot.

### `Iban` — what is checked, and why separately

`Services/Iban` is pure: `normalize()`, `format()` (groups of four), `isWellFormed()` (shape plus the exact registry length for CH / LI: 21), `hasValidCheckDigits()` (ISO 7064 MOD-97-10 on the DIGIT STRING in seven-character chunks — a 34-character IBAN expands to ~70 digits and would overflow `int`), `isSwissArea()`, `iid()` (positions 5–9) and `isQrIban()` (IID **30000–31999**, the range SIX reserved for QR-IBANs). The three checks are separate so the German message says what is actually wrong. A QR-IBAN ALWAYS carries a QR reference (QRR), a normal IBAN carries NONE (reference type NON) — the only two reference types z77 prints (owner, 2026-09-23); part 3 needs the difference to print the right bill, part 1 records and shows it.

### The soft boundary to financial

`LedgerAccountCheck` — built here in part 1 and MOVED to `module-mandator` on 2026-09-23 with the account settings (E2, Rule 8: the mandator's account fields need the same soft check as the payment target, so it exists once and debtor imports `Z77\Module\Mandator\Services\LedgerAccountCheck`) — names financial as a STRING (`LEDGER_SERVICE`), so its absence is a lookup miss and not a fatal (ADR-040 decision 5: the package only `suggest`s financial). In debtor itself two classes name module-financial (harness I16): the port adapter `LedgerAccountingGateway`, and since 2026-10-13 `Close/ReceivablesReconciliation`, which implements financial's close port and is loaded only by financial's own registry. Every answer is three-valued: `true` postable and active, `false` financial refuses, **`null` financial is not usable here and the caller may not treat that as a failure**.

**«Installed» means TWO things** (decided 2026-09-22 on review), and the second one decides: the class must autoload AND `financial` must be a REGISTERED module (`ModuleManager::getModuleConfig('financial')`). A package sitting in `vendor/` but missing from the project's `moduleManager` config has no config, no announced entities and no booted Doctrine metadata for `Account` — asking it would not answer «no», it would fatal, and with it every debtor list. Registration is also what a project actually switches when it decides to keep its books elsewhere, which is why the harness proves the branch by unregistering the module rather than through a constructor seam. It wraps `LedgerService::accountExists()` (plan §5.4, «for configuration validation»), whose second production caller this is. It is the READ half of the `AccountingGateway` boundary (plan §6.6, part 2 below); `InvoicingService::invoice()` asks it for every revenue account a draft names.

### Documents — `Invoice`, `InvoiceLine`, `InvoiceTax` (part 2)

- **One entity for invoice and credit note** (`InvoiceKind`: `invoice` | `credit-note`, decided 2026-09-23): §6.2 makes a credit note «the same mechanics with opposite sign» — same lines, same VAT summary, same snapshot, same states, the same number series (owner 2026-10-10: ONE series for every kind, «Number ranges» below). Two entities would duplicate every column and rule to differ in one word. The lines of a credit note are stored AS PRINTED (a positive «Gutschrift 50.00»); `InvoiceKind::sign()` flips the posting and the open amount. A credit note names the FINAL invoice it corrects (`creditNoteOf`, self FK); an invoice names none.
- **Two states** (`InvoiceState`, plan §6.2): `invoicing` — a DRAFT: snapshot yes, number NO (owner 2026-10-10, «Buchungsdruck» below), the content may be replaced as often as needed, its PDF is a preview, NOTHING is posted, no open amount; `final` — numbered and posted in one step (the booking print), immutable, the open amount exists. One way only; no cancelled or deleted state (plan §1, correction principle). **On screen `final` is «Verbucht»** and the step that reaches it «Buchungsdruck …» (owner 2026-10-10 — that morning «Verbuchen …», until then «definitiv» / «Definitiv stellen»: there is no booking without the print any more); the code keeps `finalize()` and the stored value `final` (a rename of DB values and of the service API would buy nothing).
- **Table `invoice`**: `kind` + `number` (`YYMMnnnn`, ONE series across kinds since 2026-10-10, unique across kinds `uniq_invoice_number` — «Number ranges» below; NULLABLE since `Version20261010170000`: NULL while `invoicing`, drawn at the booking print), `state`, `contact_id` (FK — the party BY ID), `credit_note_of_id`, the **address snapshot** `addr_*` (below), `language` (the contact's language at issue — a later language change must not re-language an issued document), `invoice_date`, `service_from` / `service_to` (the VAT rate resolves by `service_from`, ADR-041 decision 4), **`currency` + `exchange_rate` — carried without logic and without a reader ON PURPOSE** (plan §6.2, Q6, confirmed on review 2026-09-23: the document owns them, the ledger never does — ADR-042 decision 4 —, and an issued document is immutable data, so adding them later would be a migration on issued documents; today currency = base and the rate is NULL; `exchange_rate` is a `DECIMAL(12,6)` STRING, never a float; the reason stands next to the column so no reviewer raises it again), `price_mode` (net | gross), `payment_terms_code` (BY CODE) with the terms AS APPLIED — `due_date`, `discount_tiers` (JSON `[{days, percent, until}]`) and `terms_text` (the printed sentence in the document's language) —, the totals `net_total` / `tax_total` / `rounding` / `gross_total` (`MoneyType`, stored, never recomputed), the opaque origin `source_type` / `source_ref`, `ledger_entry_ref`, `created_by/at`, `changed_by/at`, `version` (`#[ORM\Version]`). **No setters**: the header is written whole by `Invoice::issue()` / `reissue()`, the number and the numbered payment part by `assignNumber()` (once, at the booking print), the state by `finalize()` (only with a number) — and all refuse a `final` document in the entity itself.
- **The address snapshot is an EMBEDDABLE** (`Entities/AddressSnapshot`, `#[ORM\Embedded(columnPrefix: 'addr_')]`, decided 2026-09-23 — closes `contact.md`'s «snapshot shape (P3)»): the ten fields of module-contact's `Address`, one flat column each — readable and searchable with a query tool like the `DECIMAL` amounts (ADR-042), no JSON to parse — and one class the dunning notice (P4) and the quote (P7) reuse (Rule 8). No reference to `address` or `contact_address`: copied, never linked (§4a). The service snapshots the contact's `invoice`-typed address, else `main`, else the first; a draft may pass its own snapshot (an order whose invoice address was chosen at order time). Getters, `isComplete()` and — since P3 part 3 — `lines()`, the PRINTED block: salutation, title + first name + name, the address row, street + number, zip + city, and the country (ISO code) only when it is not the home country (Swiss Post: foreign addresses only).
- **Table `invoice_line`**: `position` (children directly after their parent; NOT unique — Doctrine inserts before it deletes on a re-issue, the `journal_line` argument), `parent_line_id` (self FK, ONE level: a priced line carries lines beneath it — a package with its contents at 0.00, §13 / A-Pos), `type` (`LineType`: `service` | `lump-sum` | `text` | `rounding`; `subtotal` is named in the plan and not built — nothing prints it), `text` (TEXT, the editable snapshot, may span lines), `quantity` (`DECIMAL(12,3)` string — three decimals, negative allowed, null on lump sum / text / rounding), `unit`, `unit_price` (money, null on text / rounding), `discount_percent` (hundredths, 2 % = `200`), `amount` (STORED, as printed — net or gross per the document's mode; rounded once per step: quantity × price, then the discount), `tax_code` + `tax_rate` + `tax_label` (the `vat.md` rule: a DOCUMENT line snapshots rate AND label), `revenue_account` (BY NUMBER), `source_type` / `source_ref`. A priced line needs unit price, tax code and account — except on a document WITHOUT VAT (a fee; a mandator not liable to VAT, owner 2026-10-21 — «Documents without VAT» below), whose lines carry no code; a text line has none of them and no amount; the rounding line is the ONE system line (never in a draft — refused), at the top level, on the mandator's `rounding` account (`DebtorAccounts`, KMU 3809), without tax.
- **The line code — stored and offered, not printed** (owner decision 2026-10-22, the wdv `shop_positions.code`): `invoice_line.code` VARCHAR(16) NULL (`Version20261022120000`, schema only — NULL = no code, every existing document prints as before). `LineDraft(code:)` — the last named parameter, also on `service()` / `lumpSum()` / `text()`, kept by `beneath()` — any line type; `compose()` trims it, '' → null, more than `InvoiceLine::CODE_LENGTH` (16, `mb_strlen`) is refused `line` «Position n: der Code hat höchstens 16 Zeichen.» (never cut); the entity guards it once more. Part of the line SNAPSHOT (ADR-041 decision 6 and its addendum): a re-issue replaces it with the lines, a booked document keeps it, `getCode()`. It travels: order line → invoice line (`OrderInvoiceDraft`), invoice → credit note and every edit through `InvoiceForm` (row key `code`, posted as a HIDDEN input — no visible field, owner: storage only, `## pending`). **The print:** the framework's layouts (`pdf/invoice`, module-order's `pdf/order` / `pdf/deliveryNote`) do NOT print it; each line row they hand to `pdf/table` carries it as `code` (`DocumentColumns` keeps extra row keys), so «ob der Code auf der Rechnung erscheint, entscheidet der Gestalter im Override» — an override of the layout reads `$line->getCode()`, an override of `pdf/table` reads `$row['code']` (pdf.md). The importer passes `code:` from `shop_positions.code` (`LineDraft::service(…, code: …)`, `OrderLineDraft(…, code: …)`). Verified: `tests/module-debtor.php` A12f, LC1–LC5, O8.
- **Table `invoice_tax`**: the tax summary STORED, one row per code — `tax_code`, `tax_category` (what the adapter resolves the VAT account from), `tax_label`, `tax_rate`, `tax_base` (Σ of the code's lines, net), `tax_amount` (rounded ONCE, half away from zero — ADR-041 decision 5). This is `TaxSummaryEntry` of module-vat persisted; module-vat carries no serialisation (`vat.md`'s deferred item, closed here). The tax per LINE is deliberately not stored; when the posting needs it, each code's tax is distributed over its lines with `Money::allocate()`.
- **Migration** `Version20260923043935` (`res/migrations`): generated with `z77-db diff` against the module's first migration, reviewed — `utf8mb4_unicode_ci`, `ENGINE = InnoDB` spelled out, Doctrine-named FKs and indexes kept, expand only — plus ONE data step: `INSERT … number_range ('invoice', 0), ('credit-note', 0) ON DUPLICATE KEY UPDATE` (below). `tests/module-debtor.php` A applies both migrations and proves `diff` reports «No changes» afterwards, embedded and decimal columns included.

### `InvoicingService` — the single entry for every source

- **`invoice(InvoiceDraft): Invoice`** (plan §6.2, ADR-040 decision 3): everything is decided BEFORE the unit of work (`compose()` — the party, its profile and terms, the address, the lines with their amounts, VAT once through `VatCalculator` by the SERVICE date, the accounts softly against financial, the totals and the rounding, the invoice date within 2000–2099 for the number to come), so a refused draft never takes a lock (the `LedgerService::post()` order). Inside `getTransaction(Invoice::class)->run()`: the entity WITHOUT a number, `issue()` with the payment part of a draft (target, account, reference type, creditor — no reference, no message), `persist()`. **No number range is touched** (owner 2026-10-10: the number is drawn at the booking print, `finalize()`). Joins an open unit of work (an order that changes its status and invoices in one — nesting joins) or opens its own. **Nothing is posted.**
- **The draft** (`Invoicing/InvoiceDraft`, `LineDraft`): kind, contact BY ID, invoice date, service date or period (null on a credit note = the invoice's), currency, price mode, payment terms code (null → the profile's default), an optional address snapshot, the lines (`LineDraft::service()` / `lumpSum()` / `text()`, `->beneath(...)` for children), an opaque origin, and for a credit note the invoice it corrects. Plain data — the rules live in the service and come back as `InvoiceRefusedException` with a stable `reason` (`contact-unknown`, `contact-inactive`, `no-debtor-profile`, `debtor-inactive`, `terms-unknown`, `terms-inactive`, `no-address`, `address-incomplete`, `target-unknown`, `target-inactive`, `no-payment-part`, `currency`, `dates`, `no-lines`, `negative-total`, `credit-note-target`, `credit-note-rate`, `not-invoicing`, `not-found`, `kind-changed`, `line`, `line-tax-share`, `tax-code-unknown`, `tax-code-inactive`, `no-tax-rate`, `account-not-postable`, `account-not-revenue`, `account-not-selectable`; at the booking print also `number-range-full` and `payment-part` — the full list is `InvoiceRefusedException`'s constants) and a German message the part-3 screens print as it is.
- **The reference rule on a document** (ADR-043 decision 19): a NEW document needs an ACTIVE contact, an ACTIVE debtor profile, ACTIVE payment terms and ACTIVE tax codes; a re-issue keeps what the document already carries (its contact, its terms code, its tax codes) even if deactivated since. A contact without a debtor profile is not invoiced (`no-debtor-profile`, «… ist noch kein Debitor — zuerst als Debitor anlegen.» — `DebtorProfileService::notDebtor()`) — the profile carries the terms. **No document without a debtor, in the service** (owner 2026-10-19): `invoice()` no longer opens a profile (`$openProfile` removed — DEBTOR-CONTACT-001's path; the editor asks «Debitor anlegen» since 2026-10-18), so every caller — the editor, an import, a later shop — is bound alike. **Integration rule:** an importer or a shop creates the contact (`ContactService`) AND the debtor (`DebtorProfileService::open()`, the one creation path) FIRST, then the document. The ONE remaining fallback is module-order's booking print of an OLD order whose customer has no profile: `preview($draft, openProfile: true)` composes against the unsaved profile (nothing written), `openDebtorProfile()` opens it for real before the booking (plan D9).
- **Only revenue accounts** (owner finding 2026-10-10, «nur ertragsrelevante Konten», built 2026-10-12): a priced line posts to an account of the chart's TYPE «Ertrag» (`revenue` — financial's `AccountType`, the chart's own classification; KMU: class 3 plus 6950, 7000, 7500, 8100, 8510), never by number range. For every kind: an invoice line, a credit note (it reverses the same revenue) and a fee (the dunning-fee account, see `DebtorAccounts`). **And, for an invoice line, flagged «auf Belegen wählbar» in the chart** (owner decision 2026-10-12, [`financial.md`](financial.md)): the revenue deductions 3800 Erlösminderungen, 3805 Verluste aus Forderungen and 3809 Rundungsdifferenzen are typed revenue but ship switched OFF, every other revenue account is ON by default, a new one included — the set grows with the chart, there is no list here or in the mandator (Rule 2). The editor's account `<datalist>` lists only those (`LedgerAccountCheck::documentAccounts()`, [`mandator.md`](mandator.md)) — for a credit note PLUS the revenue accounts the corrected invoice's lines carry (rounding line excluded), in chart order (`InvoiceControllerTrait::invoiceLineAccounts()`); the field stays a text input, so a stored other value still SHOWS and is not dropped. The guard is the service: `compose()` (`invoice()` / `reinvoice()`) refuses `account-not-revenue` — «Position n: Konto 1020 ist kein Ertragskonto …» — after the existing `account-not-postable`, then `account-not-selectable` — «Position n: Konto 3800 ist im Kontenplan nicht «auf Belegen wählbar» — ein anderes Ertragskonto wählen oder das Konto im Kontenplan freigeben.» (`isDocumentAccount()`); and `finalize()` re-checks the STORED lines of each locked draft (`assertStoredRevenueAccounts()`, the rounding line excluded — it is the mandator's rounding account), so a draft saved before the rule, or whose account changed type or was switched off since, is refused at the booking print with the document named and nothing posted. **A FEE document is checked for the type only** (`assertRevenueAccounts(…, documentChoice: false)`): its line carries the mandator's dunning-fee account, a setting and not a pick, so switching 6950 off for invoice lines never blocks a dunning run (the dunning-fee key itself stays on `hasType()`, `DebtorAccounts::REQUIRED_TYPES`). **A CREDIT NOTE is checked for the type only too** (owner decision 2026-10-13): it mirrors the invoice it corrects, and a later chart setting must never block a correction — at issue, at re-issue and at the booking print; an invoice keeps the full check everywhere. Revenue type stays required (1020 on a credit note → `account-not-revenue`). Soft like every account check: without financial (`null`) nothing is refused. Harness J26b, J26c, L0d, L0e, H16, H16b (unexecuted, see pending); verified on z77.ch 2026-10-10 (1020 / 4200 / 2200 refused) and 2026-10-12 (datalist 14 accounts — 17 revenue minus 3800 / 3805 / 3809; 3800, 3805, «3400 + 3809» (Position 2) refused `account-not-selectable`, 1020 `account-not-revenue`, the booking print of a draft moved to 3800 refused — all in a rolled-back unit of work, counts and ranges unchanged) and 2026-10-13 (invoice on 3400 booked, 3400 switched off: the credit note on it issued and booked, a new invoice on 3400 refused `account-not-selectable`, a credit-note line on 1020 refused `account-not-revenue` — rolled back). Harness X1, X2 for the credit note.
- **Money and rounding**: the line amount = unit price × quantity (`Money::multiply()` with the decimal string), then minus the discount (`multiplyByRatio()`), each rounded once; the tax on the sum per code once (`VatCalculator`); the document total to 0.05 once — `Money::roundTo(5)` on the gross, the difference as the rounding line; a rounding of 0.00 writes no line. The 0.05 step applies to **CHF** (`InvoicingService::ROUNDING_STEPS`, a constant map — the one currency there is, Q6); another base currency rounds to 0.01 (no line). An invoice's gross must not be negative (`negative-total` — that is a credit note), a credit note's must be positive.
- **`reinvoice(int $id, int $expectedVersion, InvoiceDraft): Invoice`** — only in `invoicing`: the row is re-read under an exclusive lock (`InvoiceRepository::lockForUpdate()`, the `ManualEntryService` model), a stale version is `InvoiceConflictException`, a `final` document `not-invoicing`, a changed kind `kind-changed`, another party or target `credit-note-target`; then `Invoice::reissue()` replaces the header snapshot, the lines and the tax rows whole (orphan removal deletes the old rows at flush), stamps `changed_by/at` and bumps `version`. Still no number — and so the invoice date may move into another month (the rule of cf8abc3 that refused it is gone, owner 2026-10-10); nothing to reverse — nothing was posted. The snapshot MOVES with a re-issue (the address and terms as they read now). The payment target must be ACTIVE here too (owner 2026-10-13, review M4: the former «a re-issue keeps the target it carries» is gone — the booking print refuses an inactive target, so such a draft could never be booked).
- **`discard(int $id, int $expectedVersion): string`** (owner 2026-10-13, review H3; ADR-040 addendum 2026-10-13) — only in `invoicing`: the row locked (`lockForUpdate()`, no range, no journal), a stale version or a missing row `InvoiceConflictException`, a `final` document `not-invoicing`; then the draft is DELETED with its lines and tax rows (cascade) — a real `DELETE`, no state. The correction principle binds what was BOOKED; a draft has no number, nothing posted, and nothing references it (a credit note, a payment, a dunning notice need a final document). Returns the draft's name for the flash. Why: a forgotten draft blocked the year close (`InvoicingInProgressCheck`) forever and kept the «Debitor» role from being switched off. On screen: «Entwurf löschen …» in the draft's mask (since 2026-10-21; a `data-window-link` to `confirm-discard`, the entity token `invoice:<id>` + the version shown, `discard` closes the window and reloads the list behind). Not in the list's selection bar: a bulk delete is not the list's most frequent action (backend-screen recipe), and one draft at a time is what the owner asked for.
- **`finalize(list<array{id, version}> $documents): list<Invoice>`** — the BOOKING PRINT (owner 2026-10-10), a batch, ONE unit of work, all or nothing: (0) before the unit of work the batch's invoice dates are read in SQL (`InvoiceRepository::invoiceDatesOf()` — not as entities, so the locked re-read is not served stale from the identity map) and each month's range `document.YYMM` is created with `NumberRangeRepository::create()` (idempotent, committed at once — DOCTRINE-NR-003); inside: (1) those ranges locked FIRST, in NAME order (`create()` inside a unit of work holds the existing row exclusively); (2) every row locked `FOR UPDATE` in **id order**, missing → `not-found`, at another VERSION than the caller saw → `InvoiceConflictException` (DEBTOR-FINAL-001), already final → `not-invoicing`, re-dated into a month not locked → `InvoiceConflictException`; the payment part each document will PRINT taken again (`bookedPaymentPart()`) and checked by `QrBill` — an unknown / inactive target (`target-unknown` / `target-inactive`) or any problem of the would-be bill (`payment-part`, the document and the problem named) refuses the whole batch BEFORE a number is drawn (owner 2026-10-13, review H5); a bare id is a programming error (`InvalidArgumentException`); (3) the NUMBERS drawn — the first writes — in a fixed order, **invoice date, then id**: `next('document.YYMM')`, `YYMMnnnn` composed (the 10000th of a month refused `number-range-full`), `Invoice::assignNumber()` with the numbered payment part (`PaymentSnapshot::numbered()`: the QR reference from customer number and document number, the message «Rechnung n»); (4) per document, in the same order: `PostingBuilder::build()` (the journal text carries the number) → `AccountingGateway::post()` → `Invoice::finalize($ref)`. Returns the documents in that order. A refusal at any step rolls back every number and every posting.
- **Lock order of the module (decided 2026-09-23, revised 2026-10-10 with the number at the booking print, completed 2026-10-13 after review H4): `document.YYMM` ranges (by name) → debtor profile rows (by contact id; SHARED for a new document, EXCLUSIVE for «Debitor» off) → the bank message row (CAMT writes only) → invoice rows (EXCLUSIVE, by id) → THEN every read that judges (levels, last notices, open amounts, transaction states) → THEN the writes and `journal-entry.*`.** No unit of work reads anything plainly before its last lock: MariaDB runs REPEATABLE READ, the FIRST plain read of a transaction fixes its read view, and a read view taken before a lock wait does not see what the holder committed (the duplicate level M1, the over-allocation M2 of the review). Locks are therefore taken with locking reads only (`InvoiceRepository::lockIds()`, `DebtorProfileRepository::lockForContact()`, `BankMessageRepository::lockRow()` — none takes a read view); what a unit of work must know to choose its locks (the parties of the dunned invoices, the documents a CAMT message touches) is read BEFORE it and judged again under the locks. Every writer of a notice or a payment holds the invoice row until commit, so a plain read after the locks sees all of them — no locking read of sums is needed (and none is wanted: a shared next-key lock on `payment_allocation` / `dunning_notice` followed by the insert of the next row deadlocks two writers on neighbouring invoices). Who takes what: `finalize()` — ranges → rows → journal (several months in one batch: by range name, so two batches never wait on each other crosswise; rows by id); **`invoiceAndFinalize()`** (P7 slim, 2026-10-14, a source that is its own draft — joined into the source's unit of work after the SOURCE's own row locks, e.g. `sales_order`) — ranges → the drafts' profiles SHARED (contact id order) → `compose()` and the receivable account → the new invoice rows → the numbers → the journal; **the dunning run** (`DunningService::run()`) — the run date's `document.YYMM` (only when the ladder carries a fee) → the profiles of the dunned invoices SHARED → the invoice rows → the latest run date, the last notices and the open amounts → the notices, the fee drafts (`invoice()`, whose own profile lock is then a no-op) booked with `finalize()` joined (which finds its range held) → the journal; **the CAMT booking** (`BankImportService::book()`) — the message row → the matched invoices AND the final fee documents of their debtors → the transactions re-read (`HINT_REFRESH`) and the open amounts → the payments and the journal; `assign()` / `ignore()` take the message row first as well, so they wait for a booking and the booking for them; `PaymentService` — rows → reads → journal (`record()` / `update()` lock the row first; `delete()` locks the rows of the payment's documents before it reads the payment); `invoice()` / `reinvoice()` take no range at all (a credit-note draft's INSERT holds only an implicit SHARED lock on the referenced invoice row through `credit_note_of_id`). Why ranges before rows: two overlapping batches that each locked one row and then drew a range would deadlock (A holds row 1, waits for the range; B holds the range… ); with the range first, B waits at the range until A commits. Why rows before the journal: the 2026-09-23 reasoning — `post()` draws `journal-entry.{code}` after the rows are held. The former deadlock between `invoice(credit note)` (holding `document.YYMM`, wanting the invoice row S) and `finalize()` (holding the row X, wanting a range) is gone with the draw: a draft draws nothing. Whoever adds a step that issues AND books a document in one unit of work keeps this order (ADR-039 decision 10, `NumberRange` first). A lock conflict that still happens (a lock wait timeout, a writer outside the module) rolls the whole unit of work back; the dunning and the CAMT screens recognise it (`Services/LockConflict::is()` — `RetryableException` anywhere down the `getPrevious()` chain, DOCTRINE-TX-005) and answer with a German «nichts gespeichert, neu laden und nochmals versuchen» instead of a 500 (verified on the dev DB: a row held by another connection → `LockWaitTimeoutException` → recognised). No automatic retry.
- **Finalizing twice is REFUSED** by the SERVICE, not idempotent (decided 2026-09-23): a batch that names a final document is a stale list (`not-invoicing`). The SCREEN makes the booking print idempotent on top (owner 2026-10-10, below): the same selection submitted again — every document final at the version it showed + 1 — reprints the PDF without calling `finalize()`.
- **What the port sees** (`Invoicing/PostingBuilder`, plan §6.2 «receivable / revenue per line + VAT per code + rounding», ADR-041 decision 7 net method): `receivable` (the mandator's, through `DebtorAccounts`) DEBIT gross; per priced line with an amount CREDIT its revenue account with the line's NET amount carrying `taxCode`, `taxRate`, `taxBase` = that net and `taxAmount` = the line's SHARE of its code's tax; per tax code CREDIT the VAT account of its CATEGORY (`PostingLine::vatCredit()` — the number is the bookkeeping's setting, resolved by the adapter); the rounding line CREDIT (rounded up) or DEBIT (rounded down) 3809 without tax. A negative line posts on the opposite side with negative tax data (the sign convention of financial's manual forms); a credit note swaps every side and negates every tax figure. Σ debit = Σ credit by construction (gross = net + tax + rounding). Text = `{Rechnung|Gutschrift} {number} · {address name}` (deterministic — FIN-IDEM-002), origin = kind / number, key = `{kind}:{id}:final`. A document whose posting would have fewer than two lines (a text-only document) posts nothing and keeps a NULL ledger reference.
- **The per-line tax share** (`Invoicing/TaxShares::distribute()`, decided 2026-09-23): each code's tax (the tax row, rounded once) is distributed over its lines with `Money::allocate()` by the lines' absolute amounts — largest remainder, Σ per code = the tax row exactly (33.33 / 33.33 / 33.34 at 8.1 % → 2.70 / 2.70 / 2.70 = 8.10). Lines of one code with MIXED signs are split first: the positive group takes the tax on ITS sum (`VatCalculator::taxOf()` / `taxIn()`), the negative group the remainder, so a deduction carries a negative share and the code's total still equals the row (+100 / −30 → 8.10 / −2.43 = 5.67). In gross mode a line's net is its gross minus its share. **Gross mode, Rappen lines** (review 2026-09-23): a share ≥ its line's gross would leave a net of 0.00 or less — the posting would drop that line and the VAT return sum less tax than the VAT line carries. Such a share is set to 0 and moved to the LARGEST line of the same sign group, which must keep a positive net (20 × 0.01 + 0.30 → the 0.04 sits on the 0.30 line, the Rappen lines post at 0.01 without tax); when no line can absorb it (100 × 0.01, tax 0.07) there is no honest per-line split and the DRAFT is refused at issue (`line-tax-share`, `compose()` runs the same distribution) — decided over «fix at finalize» because a refusal after the number is drawn would leave a document that can never be finalized. In net mode a share is always smaller than its line; nothing moves.
- **`openAmount(Invoice): Money`** — DERIVED (plan §6.3, never stored in parallel): gross − Σ gross of the FINAL credit notes referencing the invoice (`InvoiceRepository::sumOfFinalCreditNotes()`, one SQL aggregate); P4 subtracts payments, discount and loss. Zero while `invoicing` (§6.2: no open item yet) and for a credit note (it reduces one). Negative = more was credited than invoiced. **No `OpenItem` table** (decided 2026-09-23 against §6.1's row): nothing in this state reads one — the `final` invoice row IS the open item (identity, amount, due date, party are all on it), and building the table now would fix a shape P4 has not needed yet (the dunning fee «as its own open item», §6.5, is P4's design). If P4 wants the entity, it is a new table fed from `finalize()`, not a change to issued documents.
- **The credit note** (plan §6.2): `InvoiceDraft::creditNote($invoiceId, …)`, refused against an invoice still `invoicing` (`credit-note-target` — nothing is posted there, the correction is `reinvoice()`, and a credit note would mirror a posting that does not exist), against another party's invoice, against a credit note, or at 0.00. Nothing caps the credited amount (decided 2026-09-23, see known issues). Its posting mirrors the invoice's; the invoice's open amount drops by its gross once it is `final`.
- **A credit note follows the RATE of the original supply** (review 2026-09-23, ADR-041 decision 4 — a reduction of consideration is taxed as the supply was): `creditNote()` takes `serviceFrom` / `serviceTo` from the INVOICE unless the draft names its own (a partial period); a credit note issued in 2026 against a 2023 invoice therefore resolves 7.7 %, and 2200 goes back to zero instead of keeping the 0.40 an own 2026 date would leave (the return would report the reduction under 8.1 %). When the draft names its own date, `compose()` compares every code the invoice carries: a resolved rate that differs from the invoice's snapshot is refused (`credit-note-rate`, the message names both rates); a code the invoice never carried resolves by the date given.
- **Who**: `Services/Actor` — the same resolution as financial's (`AuthUser` name, refuses to guess); a CLI caller passes the name. Repeated rather than imported because financial may be absent (Rule 8 deferred: it moves to the kernel `shared` when a third module needs it — pending).
- **`DocumentText::resolve(texts, language, default)`** — the per-language resolver part 1 left out: the document's language, else the installation's default language, else ''. The invoice snapshots the result as `terms_text`.

### Documents without VAT — the mandator's «mehrwertsteuerpflichtig» (owner decision 2026-10-21)

- **The rule, ONE place**: `InvoicingService::chargesVat(InvoiceKind, ?Invoice $creditNoteOf)` — a fee never (plan §6.5); a credit note exactly when its INVOICE carries VAT (`Invoice::carriesVat()` — a reduction of consideration follows the original supply, the rule of the rate, ADR-041 decision 4; also when the flag changed in between); an invoice by the mandator's `liable_to_vat`, read through debtor's one reader `Creditor::mandator()`. No mandator saved, or a record that cannot be read, counts as LIABLE (today's behaviour — the absence of a record is no declaration). `compose()` applies it (so `invoice()`, `reinvoice()`, `preview()` and through the preview module-order's totals, PDFs and booking print — D11); the editors ask it to show or hide VAT. The flag is read at every compose: a draft follows it at its next save, an issued document keeps its snapshot and is never recomputed (ADR-041 decision 6).
- **Computed without VAT**: no `VatCalculator` call, no `invoice_tax` row, tax 0.00, net = Σ lines, gross = net + the 0.05 rounding; the price mode (net / gross) changes no amount (it is still stored on the snapshot). **The lines store NO tax code** (`tax_code` / `tax_rate` / `tax_label` NULL — the fee's shape, `InvoiceLine`'s all-or-none rule and the nullable columns hold it, no migration): the codes a source hands in (an order line carries its article's) are DROPPED, not refused, and the editor no longer asks for one. Chosen over «keep the article's code at rate 0»: a code on the line would put the revenue into the VAT return under that code at 0 % (financial reads the journal line's tax data — ADR-041 decision 7), would need a tax row of 0.00 and a snapshot label for a tax that does not exist; NULL keeps finalize, snapshot and posting on the existing fee path. The order keeps the article's code on ITS line (`sales_order_line.tax_code`, D3) — only the document has none.
- **Posted without VAT**: `PostingBuilder` posts receivable against revenue (and rounding) only — no line with tax data, no VAT account (there is no tax row to post); payments, discount and loss find no tax row and correct no VAT (`PaymentPostingBuilder::sharesPerCode()`, the fee's path).
- **Printed with ONE layout** (owner 2026-10-21, revised the same day from «two templates»): `pdf/invoice` gets `liableToVat` from `InvoicePdf` = `Invoice::carriesVat()` — from the SNAPSHOT, not today's flag, so a reprint reads what was issued (for a document computed by the rule it is the same answer). False: `Pdf\DocumentColumns::table(…, $withVat: false)` drops the MWST column (like the discount column, the text takes the width), the shared summary partial `pdf/documentSummary` (Netto · MWST rows · Rundung · Total — also `pdf/order`'s) omits the MWST rows, the fact «Preise zzgl. / inkl. MWST» is left out. The letterhead keeps its own UID rule (` MWST` only for a liable mandator). One file per document type to override (Rule 1); the summary partial is overridable too. A fee now prints without the empty MWST column and without «zzgl. MWST» as well (it carries no code). The detail screen hides «Preise» for such a document.
- **The editor** (`InvoiceForm(…, withVat:)`, set by `InvoiceControllerTrait` from `chargesVat()` for add / edit / credit note): without VAT no MWST column, no rate schedule — so core.js «price mode» keeps every price (a row without a rate keeps its price) —, no «MWST-Code wählen», and no server conversion between the price modes. The server stays authoritative: `compose()` drops a posted code anyway (Rule 7). No core.js change was needed.
- **A draft composed under the other liability is REFUSED at the booking print** (owner 2026-10-21): `finalize()` compares the draft's `carriesVat()` with `chargesVat()` now and refuses `vat-liability-changed` («… neu speichern, dann verbuchen») before any number is drawn — never recomposed there, so what is booked is what the user last saw (MV10). The order's booking print composes afresh and is not affected.
- **Without VAT the «Preise» select is hidden** (its value still posted) and the editor's help drops the price-mode section and the MWST wording (owner 2026-10-21; MV11).
- **The note «Hinweis ohne MWST» — snapshotted** (owner decision 2026-10-22; ADR-041 addendum): a document composed WITHOUT VAT says that its issuer is not liable. The text is the MANDATOR's (`mandator.vat_exempt_note`, next to the switch — mandator.md); `compose()` reads it through `Creditor::mandator()?->documentVatNote()` (the text only while the company is NOT liable and a text is stored) and stores it on the document — `invoice.vat_note` VARCHAR(255) NULL (`Version20261022100000`), `DocumentSnapshot::$vatNote`, `Invoice::getVatNote()`; NULL for a document computed WITH VAT or when the mandator has no text. Part of the snapshot like the subject: a reprint reads as issued, whatever the mandator says today (ADR-041 decision 6) — a booked document keeps its note after the text was changed or the switch turned on (MV13). **Per kind**: an invoice — by `chargesVat()`; a credit note of a no-VAT invoice takes the text as the mandator has it at COMPOSING (it is composed afresh; a credit note of a VAT invoice carries VAT and no note); a fee (dunning) never carries VAT and gets the note too while the company is not liable — judged 2026-10-22: a fee is no supply, but the sentence «nicht mehrwertsteuerpflichtig» is about the issuer and still true; while liable none (the fee's missing VAT is the fee's nature, not the company's state). **Never from a source**: `InvoiceDraft` / order's `OrderDraft` carry no note field (MV12) — Rule 7, the server reads the mandator. **Printed** by the shared `pdf/documentSummary` (`note`, optional): under the total, 8 pt, muted, wrapped to the table's width, kept with the total (`ensureSpace`); `pdf/invoice` hands `getVatNote()`, module-order's `pdf/order` the mandator's current text — the two layouts differ only through the input (Rule 9). **Shown** in the mask's facts block (`_facts`) as one muted row «MWST» for a document that stores one (MV14), so the user sees what was printed; the editors need nothing.

### The accounting port (plan §6.6)

- **`Accounting\AccountingGateway { post(PostingRequest): ?string }`** — the port; **`PostingRequest` / `PostingLine` are DEBTOR'S OWN DTOs** (decided 2026-09-23, a deviation from §6.6's wording «the DTO is financial's»): if the interface named financial's class, `InvoicingService` would build a financial object and an installation without module-financial would fatal at `finalize()` — the very case `NullAccountingGateway` exists for. Debtor's DTO mirrors financial's shape (date, text, opaque origin, key, lines with account / debit / credit / tax data) and validates the same invariants (≥ 2 lines, one currency, balanced); the adapter translates 1:1. The one addition: a line may name its account by **VAT category** instead of a number (`PostingLine::vatCredit()` / `vatDebit()`) — which account the VAT of a category goes to is the mandator's VAT account, resolved by financial (Rule 2, the one place — `vatAccountFor()` on the mandator record since E2), so debtor names the category and the adapter resolves the number through `LedgerService::vatAccountFor()`, refusing a missing or non-postable one with `AccountingRefusedException` `vat-account-missing` naming the mandator.
- **`LedgerAccountingGateway`** (the default): joins the caller's unit of work, calls `LedgerService::post()`, answers `EntryRef` as ONE string `{fiscal-year}/{number}` — how the document stores it (`invoice.ledger_entry_ref`, `VARCHAR(32)`; closes financial's pending «EntryRef storage shape»). Financial's `PostingRefusedException` (no fiscal year, period closed / VAT-settled, account unknown / group / inactive, tax code unknown, idempotency conflict) comes back as `AccountingRefusedException` with the same `reason` and the original as `getPrevious()`. Deliberately NO catch of the unique-index failure at commit and NO retry (`financial.md`, the race contract): both end the caller's unit of work, no journal number is consumed, the documents stay `invoicing`; a retry is a new `finalize()`. Its constructor refuses to run when `financial` is not a REGISTERED module (`AccountingUnavailableException`, through `LedgerAccountCheck::available()`).
- **`NullAccountingGateway`**: `finalize()` sets `final`, the open amount exists, nothing is booked, `ledger_entry_ref` stays NULL. Configured EXPLICITLY — never a fallback for a missing financial: an installation that keeps its books elsewhere says so.
- **Selection by config** (`debtorConfig → accountingGateway`, a class name — the `memberConfig` hook pattern, ADR-038; read by `Accounting\AccountingGateways::fromConfig()` at the point of use): the package config names `LedgerAccountingGateway`; a project without z77 bookkeeping writes `NullAccountingGateway::class` into its override — which, BOOT-CONFIG-001, must carry the FULL config. A missing key is `UnexpectedValueException`, an unknown class or one that is no gateway `AccountingUnavailableException`. Every gateway takes `(UnifiedEntityManager $em, string $actor)`. `InvoicingService` accepts a gateway in its constructor (the harness injects the Null one) and builds the configured one otherwise.
- **Idempotency**: the key `{kind}:{id}:final` is stable across retries and the content deterministic, so a `finalize()` retried after a failed commit returns the existing entry from the ledger — and is then refused by debtor anyway, because the document is `final` only when that commit went through.

### The booking print — the number at booking, the preview (owner 2026-10-10, second decision of the day)

Owner, 2026-10-10: **«a printed invoice with a number IS a document»**. The morning's «Verbuchen …» + «Fakturiert» (`5f398b1`) let a draft carry a number and print it — a numbered paper that was not booked. Decided instead: a draft has NO number and prints only as a preview; the number is drawn, the document booked and its PDF opened in ONE step, the booking print. «Fakturiert» fell away (with the booking print every booked document was printed at that moment).

### Number ranges

**`document.YYMM` — ONE series for every document, per month (owner 2026-10-10).** Invoices, credit notes and fees share one number series in the format **`YYMMnnnn`**, stored and printed as a plain integer: `YY` the two-digit year and `MM` the month of the **invoice date** (the date printed on the document — not the day it is finalized: a March-dated document finalized in April continues March), `nnnn` the running number within that month from 0001, gapless. The 3rd document dated March 2026 is `26030003`. Independent of any order number. `Invoicing\DocumentNumber` composes it (`range()`, `compose()`); `number_range` holds only the bare running `nnnn` per month (`document.2603`, the `journal-entry.{code}` pattern) — the year-month prefix belongs to the document, never to the range (`persistence-doctrine.md`). The number is unique ACROSS kinds (`uniq_invoice_number`, `Version20261010100000`), so a number names exactly one document — what the QR reference (positions 17–26, eight of ten digits used), a payment message and the search rely on.

- **At most 9999 per month**: the 10000th draw — at the booking print — is refused inside the unit of work — `InvoiceRefusedException` `number-range-full` with a German message naming the month, the English `OverflowException` of `DocumentNumber::compose()` behind it — and the rollback leaves the range at 9999 and the draft unnumbered. Never carried into the next month's digits.
- **Years 2000–2099 only** (two-digit year): an invoice date outside is refused `dates` already at issue (`compose()`), not first at the booking print.
- **The number is drawn at the booking print** (owner 2026-10-10, second decision): a draft has none, so a re-issue may move its date into any month (the cf8abc3 rule «a re-issue stays in its number's month» is gone); the month is fixed when the document is booked — by its invoice date at that moment. Drafts that carried a number before `Version20261010170000` lost it (its data step, `Version20261010170001` since the split of 2026-10-13); the numbers they had are gaps in their month on an installation that printed them — the migration never lowers a range (on the z77.ch dev database `document.2610` was reset by hand, `## known issues` DEBTOR-NR-003).
- **How a month's range comes into being — decided 2026-10-10**: a month cannot be created ahead at install the way the former ranges were, and it has no «opening» event like the ledger's fiscal year — it becomes valid with its first booked document. So `InvoicingService::finalize()` creates the batch's month ranges with `NumberRangeRepository::create()` **before** opening its unit of work (idempotent, consumes no number; outside a unit of work committed at once — DOCTRINE-NR-003), locks them first inside and draws with `next()`. No framework feature was added: `create()` is the doctrine's own creation step, used per month instead of per install. Residual case (DEBTOR-NR-001): when `finalize()` JOINS a caller's open unit of work, `create()` runs inside it.
- **The former ranges `invoice` and `credit-note`** (2026-09-23 until 2026-10-10, one per kind, bare integers from 1, created at 0 by `Version20260923043935`): numbers issued from them **stay as they were** — they are printed and booked, nothing is renumbered. The rows stay: the running release still draws from them until the switch (expand/contract), and `invoice` has handed out numbers (the `dropUnused()` rule keeps it — it documents the old numbers). The unused `credit-note` (0) and the implied index `uniq_invoice_kind_number` go with the contract step (`## pending`). `down()` of `Version20260923043935` still deletes them only at 0.

**`customer`** (owner 2026-10-06), the customer numbers of the debtor profiles (`uniq_debtor_profile_number`), drawn in `DebtorProfileService::save()` as the FIRST write of its unit of work. Created by `Version20261006100000` the same way — at 0, then raised to the highest number the backfill of existing profiles handed out, at least 999 so the first draw is 1000 (`GREATEST`, so a re-run never lowers it); `down()` deletes the row only at 0. A number handed out is printed on QR-bills (positions 11–16 of the reference) and is therefore never reused — also not the number of a profile DELETED by «Debitor» off (2026-10-12) before any document: the range is never lowered, the number stays a gap.

### P4 part 1 — payments, discount and loss (2026-10-06, owner go of the same day)

- **The model** (plan §6.3): `Entities/Payment` is ONE settlement event — the value date, the money that moved (`amount`, 0.00 for a write-off), the payment target it arrived on (by code, '' without money), a note, `source_type` / `source_ref` (`manual`; the CAMT transaction in part 2) — with its `Entities/PaymentAllocation`s: what it clears on which FINAL invoice, of an `AllocationKind` (`payment` · `discount` «Skonto» · `loss` «Verlust»), each with the journal reference of its posting. No setters — but **CORRECTABLE while the fiscal year is open** (owner 2026-10-06: «manuelle Buchungen sind tippfehleranfällig; der Sachbearbeiter korrigiert, ohne Stornobuchungen»): `PaymentService::update()` / `delete()` are the one way, and they change or remove the POSTINGS with it through the port's `amend()` / `retract()` (ADR-042 addendum; `AccountingGateway` grew by the two methods, the Null gateway answers nothing) — the bookkeeping logs each change like a manual edit, the journal screen never touches a generated entry. `Payment` carries the LEDGER ACCOUNT the money went to (`account_number` — bank, cash register, a clearing account: the office chooses on the form, the target's account is the proposal), `changed_by` / `changed_at` and a `version` (the optimistic lock an edit names). A wrong payment is never countered: it is corrected or deleted (owner point 1). **The open amount stays DERIVED**: `InvoicingService::openAmount()` = gross − Σ final credit notes − Σ allocations of every kind (`PaymentAllocationRepository::sumAllocated()`), nothing stores it in parallel — the `OpenItem` question of `## pending` is answered with NO table. **The plan's fourth allocation kind `fee` does not exist**: a dunning fee is a DOCUMENT of its own kind (owner 2026-10-06 — «eigene Belegart», built in part 3), cleared like an invoice. Tables `payment` / `payment_allocation`, migration `Version20261006150000`.
- **The write path** `Services/PaymentService::record(PaymentDraft)` (ADR-040 decision 3 applied to settlements): ONE draft = one settlement on ONE invoice — payment, discount, loss, each ≥ 0.00, at least one > 0.00, in the invoice's currency, Σ ≤ the open amount (no overpayment in part 1; a receipt above the open amount is part 2's unmatched remainder), the value date not before the invoice date, money names an ACTIVE target whose ledger account the bookkeeping takes (`LedgerAccountCheck`, soft without financial). Refusals are `PaymentRefusedException` with a stable `reason` (`not-found`, `not-final`, `credit-note`, `currency`, `amount`, `nothing`, `over-allocation`, `target-required` / `-unknown` / `-inactive` / `-account`, `date`) — nothing written. Inside the unit of work: the invoice row LOCKED (`lockForUpdate`, the `finalize()` lock order — rows before any journal number), the open amount read under the lock, the payment and its allocations inserted and FLUSHED (their ids are the idempotency keys `allocation:{id}`), then each allocation POSTED through the accounting port; a ledger refusal (period closed, no fiscal year, account unknown) rolls the whole settlement back. **A settlement is a fact of the books the moment it exists** — there is no unbooked payment, so the period close has nothing of ours to check (part 2's CAMT transactions will register theirs). **`update($paymentId, $version, $draft)`** revises the header (date, amount, account, note) and reshapes the allocations kind by kind: a kind that stays is `reallocate()`d and its posting AMENDED under the same key `allocation:{id}` (the journal number stays); a kind that goes is withdrawn and its posting RETRACTED; a new kind is posted. The open amount is checked WITHOUT this payment's own allocations (`PaymentAllocationRepository::sumAllocatedBy()`). **`delete($paymentId, $version)`** retracts every posting and removes the rows. Both take the version the caller saw (`conflict` otherwise, also on Doctrine's optimistic-lock failure at flush); the ledger's refusals (period closed, entry frozen) roll the correction back whole. The money's account: the draft's `account` when given (the office chose), else the active target's (`target-…` refusals); `TARGET_REQUIRED` when neither.
- **The postings** (`Payments/PaymentPostingBuilder`, one journal entry per allocation, source `payment` / `{payment id}`, text «Zahlung Rechnung 12 · Name» built deterministically — FIN-IDEM-002): a **payment** debits the target's bank account and credits the receivable, no tax data. **Discount and loss** credit the receivable with the amount and debit the discount (or loss) account of the mandator PER TAX CODE of the invoice's tax summary with the NET share — carrying `taxCode`, `taxRate`, `taxBase` = −net and `taxAmount` = −tax, the credit note's sign convention, so the VAT return sees less turnover under the rate of the supply — plus a debit of the VAT account of the code's category with the tax share. Σ debit = Σ credit by construction. Example (`tests/module-debtor.php` Q3): 8.10 Skonto on a UN 8.1 % invoice → 3800 D 7.49 (UN 810, base −7.49, tax −0.61) | 2200 D 0.61 | 1100 C 8.10.

## rules

- When a document is composed or an editor decides whether to show VAT → MUST ask `InvoicingService::chargesVat($kind, $creditNoteOf)` (the mandator's `liable_to_vat` through `Creditor::mandator()`; a credit note follows its invoice; a fee never; no mandator = liable); MUST NOT read `isLiableToVat()` anywhere else in debtor or order, and MUST NOT store a tax code, a tax row or tax data on the posting of a document computed without it
- When a priced document is printed → MUST pass `liableToVat` = `Invoice::carriesVat()` (the snapshot) to the ONE layout, drop the VAT column through `DocumentColumns::table(…, $withVat)` and draw the totals with `pdf/documentSummary` — handing it `note` = `Invoice::getVatNote()` (the snapshotted «Hinweis ohne MWST», owner 2026-10-22); MUST NOT add a second layout per liability, decide the VAT presentation from today's mandator flag for an issued document, or read the mandator's current note for an ISSUED document
