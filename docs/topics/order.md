## mental model

`z77/module-order` holds the sales order of P7 slim (plan [`p7-order-plan.md`](../03-development/p7-order-plan.md), owner go 2026-10-14): quote and order are ONE record (D1), the status is DATA — a label in one of five FIXED PHASES that carry all behaviour (ADR-043 addendum 2026-10-15; until then behaviour flags per status, O4), every write ends in ONE call of the stock seam (O5), the invoice is drafted from the order by a pure mapper and booked by debtor (O1). Depends on kernel, persistence-doctrine, module-vat, module-contact, module-mandator, module-article and module-debtor; nothing depends on it (debtor and article never name it — harness N2). Built 2026-10-14: steps 3, 5 and 6 of plan §13, then steps 7–10 the same day — the list and the order window, the PDFs, the booking print `book()`, the year-close warning (see «screens, PDFs and the booking print»); the phases 2026-10-15.

- **Phase** (`Entities\OrderPhase`, an enum in code — the ladder, what wdv-630 called the *level*; ADR-043 addendum 2026-10-15): `new` (a quote — no stock, no booking print, PDF «Offerte») · `confirmed` (stock RESERVED, booking print) · `delivered` (stock CONSUMED — «bereitgestellt», «geliefert», «zu fakturieren»; booking print) · `closed` (consumed, locked — «gebucht», «erledigt») · `cancelled` (no stock, locked). `reservesStock()`, `consumesStock()`, `isQuote()`, `isBookable()`, `isLocked()`, `allowsDeliveryNote()`, `isStartable()`, `rank()`. Whether a LINE moves stock is the ARTICLE's (`stock_relevant`, the ledger decides per variant) — a service or a free line never does.
- **Order status** (`Entities\OrderStatus`, file `framework/order/order_statuses.json`, seed-once from `order_statuses.default.json`): `code` (key, immutable), German `label`, `phase`, `position` (the order within the phase, not unique), `phaseDefault` (the status an ACTION sets for its phase), `active`. No behaviour of its own — any number of statuses per phase, to order and find orders by. A stored phase the validator would refuse reads as `new` (`getPhase()`; `getPhaseValue()` is the raw value). Seed: Offerte (new, default) · Terminauftrag (confirmed, default) · Geliefert (delivered, default) · Zu fakturieren (delivered) · Gebucht (closed, default) · Erledigt (closed) · Storniert (cancelled — no default: no action cancels). Write path `Services\OrderMasterData::save()` / `setActive()` — no remove; the code of an existing row refused (`OrderStatusCodeChangedException`).
- **Validation** (`Validators\OrderStatusValidator`): code and label by debtor's shared master-data rule; the phase one of `OrderPhase` (field `phase`); position 0–999; across the rows at most ONE ACTIVE default per phase (`crossRowProblem()`, pure — field `phase_default`). `setActive(false)` is a pure state change (the debtor model); `setActive(true)` checks the cross-row rule. No in-row invariants any more — a phase cannot contradict itself.
- **Selection by phase** (`Services\OrderStatuses`, pure over the rows, ordered phase · position · id): `defaultOf(phase)` = the active `phaseDefault` row, else the first active row of the phase; `initial()` = the default of `new`; `startable()` = every active status of a phase that is not locked (the create form's choice — a service order may start as «Terminauftrag»); `actionTarget(current, phase)` = the default of `phase` when the order stands BEFORE it, else null (a reprint). A code comes only from OUTSIDE (the order's own status, a target the user picked) — no code path selects a status by a literal code (harness N1).
- **Transitions** (`OrderStatuses::refusal()`, by hand through «Status ändern …»): a phase at or after the current one (forward / lateral) always; backward only while the order has NO invoice (`backward-barred`); never to the default of `closed` (`booked-by-print-only` — the booking print's alone, no «gebucht» without an invoice); to `cancelled` only without an invoice (`cancel-barred`); never to an inactive one (`inactive-target`); the same status is `same-status`. An order keeps a deactivated status. `targets()` is the confirm list.
- **Schema** (`Version20261014140000`, schema only; `Version20261014140001` the range `order` at 0 — schema and data apart, debtor's rule): `sales_order` (number unique — range `order`, owner O2/Q5: 1, 2, …; `status_code` by code; subject 200; order date; service from / to nullable; contact FK; price mode; currency; payment target code nullable; `ship_*` = debtor's `AddressSnapshot` embeddable, all empty = none; `notes` internal; `total_net/tax/gross` nullable; `invoice_id` FK nullable, NOT unique (D5); `source_type` / `source_ref`; actor stamps; `version`), `sales_order_line` (order FK, position, `parent_line_id` one level, `type` = debtor's `LineType` without rounding, `variant_id` FK nullable (D2), `article_number` snapshot, text, `quantity` DECIMAL(12,3) negative allowed, unit, unit price, discount hundredths, tax code, revenue account), `sales_order_status_change` (order FK, from / to code, `change_trigger` — `create` · `status` · `delivery-note` · `booking-print`; the column is not `trigger`, a reserved word —, reason, who, when). Named after article's migration (the line references `article_variant`).
- **The write path** (`Services\OrderService`, actor named by the caller, optional `StockLedger` and `InvoicingService` injected for the harness): `create(OrderDraft)`, `update(id, version, OrderDraft, ?StockConfirmation)`, `changeStatus(id, version, toCode, ?StockConfirmation)`, `printConfirmation(id, version, ?StockConfirmation)`, `printDeliveryNote(id, version, ?StockConfirmation)`, `book(list<{id, version}>, invoiceDate, ?StockConfirmation)` (step 9); reads `statuses()`, `editRefusal(order)`, `preview(order, ?invoiceDate)` (debtor's transient invoice of the order — D11), `deliveryAddressOf(order)`, `articleDefaults()`; the static `assertPrintable(order, status, phase)`. Refusals: `InvalidOrderException` (German message per field, `lines.{path}.{field}`), `OrderConflictException` (stale version, gone, a line id that is not the order's), `OrderRefusedException` with a stable `reason` (`no-status`, `status-unknown`, `not-startable`, `not-editable`, `not-printable` + the five transition reasons; the booking print's `nothing-selected`, `no-booked-status`, `already-invoiced`, `not-invoiceable`, `invoice-refused`). Every write flushes before it returns — a caller that joins the unit of work reads the written state and version.
- **The draft** (`OrderDraft` / `OrderLineDraft`, typed strings, no `Request`): an ARTICLE line takes text / unit / unit price from the article when empty — the price valid at the ORDER date (`PriceRepository::validAt()`), converted to the order's price mode with the rate of the article's tax code on the SERVICE date (`VatRates`) — and ALWAYS tax code and revenue account from the article (D3). A FREE line names its tax code (active, or kept by the order) and account (digits + `ArticleService::accountProblem()` — soft, the binding check stays debtor's at the booking print). Contact, payment target, variant and tax code that the order already holds stay valid although deactivated since (ADR-043 decision 19).
- **Line identity is stable** (decided at build): `update()` rewrites a line IN PLACE when the draft carries its `id`, inserts the new ones, removes the ones left out (orphan removal). The line id is the stock seam's line reference; a «replace all lines» save (plan §5's `reinvoice()` model) would have given every line a new id on every edit, and in a consuming status the journal would have seen consumed stock come back on every save (`StockReasonRequiredException`).
- **Lock order** (plan §5): `order` range (create only — the first write) → `sales_order` row EXCLUSIVE (`SalesOrderRepository::lockIds()` returns the version; compared there) → the order re-read REFRESHED (`withLines()`, `HINT_REFRESH`) → the line rows flushed (new rows; their ids are the stock references) → the stock call → the totals → the commit. What the draft needs is read and judged BEFORE the unit of work; under the lock D7 and the transition rule are judged again. A lock conflict propagates — the screen answers it with debtor's `LockConflict::is()` / `MESSAGE`.
- **Stock** (`private syncStock()`, the only `bringTo()` in the package — harness N4): the COMPLETE state through `Stock\OrderStockTargets::of(lines, phase)` — every article line (children too) with `reserved` = quantity if the PHASE reserves, `consumed` = quantity if it consumes, else `0.000`; negative stays negative; a LUMP-SUM article line counts as one unit (decided at build); free and text lines not sent. Because the ledger books only the difference against what it holds for the order (ADR-043 decision 12), skipping a phase books the end state directly and a status edited later cannot corrupt anything (the wdv-630 finding, plan §8.4). Triggers: `create`, `lines`, `status:{from}>{to}` (also for the order confirmation and the delivery note). A `StockReasonRequiredException` rolls everything back; with `StockConfirmation` the reason is written to the status log row (a pure line edit has no log row — the journal of P7b keeps the reason there). Until P7b the ledger behind the seam is `PendingStockLedger` — it books nothing.
- **Totals** (D11): `OrderInvoiceDraft::of($order, $order->getOrderDate())` → `InvoicingService::preview(…, openProfile: true)` inside the unit of work, after the order's lock (preview reads, writes nothing); net / tax / gross stored for the list; a refusal (`DebtorException`, `VatException`) leaves them null.
- **Editable** (D7): no invoice and the phase not locked (`closed`, `cancelled`) — else `not-editable`; with an invoice only a forward status change. No delete (D8). «Erledigt» and «Storniert» by hand (Q6) through `changeStatus()`.
- **Order confirmation and delivery note** (D6, ADR-043 addendum 2026-10-15): `printConfirmation()` moves a quote into the default of `confirmed` (trigger `confirmation`), `printDeliveryNote()` a confirmed order into the default of `delivered` (trigger `delivery-note`) — only FORWARD (`actionTarget()`); in or past the phase nothing is written and the order is answered as it is (no version needed: a double click prints twice, moves once). `assertPrintable()` refuses (`not-printable`) a cancelled order and the delivery note of a quote.
- **Invoice mapping** (`Invoicing\OrderInvoiceDraft::of(order, invoiceDate)`, pure, harness D): kind invoice, contact, invoice date (a day), service from = head or the invoice date, service to, price mode, currency, payment target, terms null (the profile's), address null (debtor snapshots the invoice address), subject «Auftrag {nr} · {Betreff}» / «Auftrag {nr}», lines 1:1 with children beneath their parent, origin `order` / number, lines `order-line` / id.
- **Screen** Stammdaten › Aufträge › Auftragsstatus (`/backend/order/order-status/list`, host `Order/OrderStatusController`, group `order`): a standard list along the ladder (state icon · Code · Bezeichnung · Phase · Sortierung · Wird gesetzt durch — the ACTION that sets a default: neuer Auftrag, Auftragsbestätigung, Lieferschein, Buchungsdruck · Aktiv switch), action cell «+ Status». The status opens as a WINDOW with help (code fixed after creation, label, phase — a select of the fixed phases —, «Sortierung», the default switch worded by the phase — «Startstatus für neue Aufträge», «Wird gesetzt beim Druck der Auftragsbestätigung» … (`OrderPhase::defaultSwitchLabel()`; owner 2026-10-15: «Vorgabe der Phase» was understood by no one), none for a cancelled status; the help explains the phases) — deviation from plan §9.5's «⋮ → edit dialog», the article's reason: a modal popup cannot carry the field help (ADR-048). The switch answers with its row; a refused activation names the phase's other default.
- **Navigation**: seed `module-order.json` — `auftraege-liste` «Aufträge» (route `backend/order/order/list`, sort 0 under debtor's area `auftraege` — the FIRST entry; debtor's seed moved Rechnungen / Debitoren / Zahlungseingänge / Mahnungen to 1–4) and `auftragsstatus` «Auftragsstatus» under debtor's `stammdaten-auftraege`, sort 10. The area click opens its first entry, the order list; `groupDefaults['order']` → `order`. The merge is add-only (ADR-050): z77.ch received `auftraege-liste` through `composer install` (appended at sort 4) and was re-sorted by hand on 2026-10-14 (Aufträge 0, Rechnungen 1, Debitoren 2, Zahlungseingänge 3, Mahnungen 4 — NAV-SEED-002).

- **PDFs** (`Pdf\OrderPdf`, layouts `pdf/order` and `pdf/deliveryNote` — overridable under `override/`, Rule 1): `pdf` → «Offerte {nr}» / «Auftragsbestätigung {nr}» (`OrderPdf::orderTitle()` by the PHASE — `new` is a quote), letterhead, the invoice address the preview resolved, title, subject in bold, facts (Kundennummer if a debtor, Auftragsdatum, Leistung, Preise), the lines with the article number in front, Netto / MWST per code / Rundung / Total — all from `OrderService::preview()` (D11), no payment part, no side effect; a preview refusal answers a message PAGE (`printRefused`). `invoice-preview` → debtor's `InvoicePdf::of(preview)` («VORSCHAU», no number, no payment part), the invoice as the booking print would issue it TODAY. **The two prints that move the order** share the confirm window `confirmPrint` (in the order window): `confirm-confirmation` (a quote) and `confirm-delivery-note` say whether the print MOVES the order (into the default of the next phase, only forward) or is a reprint — the delivery note also to which address; the form POSTs into a NEW TAB (`confirmation` / `delivery-note`, `#[Csrf]`, the version shown) — the service FIRST (`printConfirmation()` / `printDeliveryNote()`), then the PDF (`pdf/order` as «Auftragsbestätigung»; `pdf/deliveryNote`: the delivery address, else `InvoicingService::invoiceAddressOf()` — debtor's one rule; article number, text, quantity, unit, NO prices; a signature line); when the status moves, `data-submit-navigate` sends the original tab to the list (the window would be stale), a reprint leaves it. File names kebab-case: `offerte-1.pdf`, `auftragsbestaetigung-1.pdf`, `lieferschein-1.pdf`, `vorschau-rechnung-auftrag-1.pdf`.
- **The booking print** (`OrderService::book(list<{id, version}>, invoiceDate, ?StockConfirmation)`, plan §7, D4): (1) before the unit of work, at the versions the screen showed — each order exists, has no invoice (`already-invoiced`), sits in a bookable phase — `confirmed` or `delivered` (`not-invoiceable`); the phase `closed` without an active status → `no-booked-status`; each customer's profile opened (`openDebtorProfile()`, D9 — its own unit of work); each order PREVIEWED (`preview()` without `openProfile`) so a refusal names the order («Auftrag 12: …», `invoice-refused`), and a payment part that could not be printed is refused the same way; `prepareDocumentRanges([invoiceDate])`. (2) The unit of work: `lockIds()` (versions compared → `OrderConflictException`) → the orders re-read refreshed and judged again → `invoiceAndFinalize($drafts)` joined (debtor's chain) → per booked invoice, matched to its order by `source_ref` = order number: `linkInvoice()`, `move()` to the default of `closed` («Gebucht») with the trigger `booking-print` (log row + the stock call + flush — link, status and stamp in ONE update, version + 1). A refusal inside names the order(s). Returns the invoices in number order.
- **The booking print on screen**: «Buchungsdruck …» from the window (one order) or the selection bar (several) → `confirm-book` (a PAGE: the orders with Nr., date, customer, subject, total, the sum, the INVOICE DATE — default today; stale ones named and left out) → its form POSTs into a NEW TAB (`book`, `#[Csrf]`, `data-submit-navigate` → «Gebucht») → the combined invoice PDF (`InvoicePdf::combined()`, `rechnung-{nr}.pdf` / `dokumente-…-bis-….pdf`), the success flash for the original tab's next page. **Idempotent** (`Ui\BookingSelection::bookedBy()`, pure): every order of the selection linked to a FINAL invoice at the version it showed + 1 → the same PDF again, nothing booked. Every refusal (conflict, the service's reasons, debtor's, a DBAL exception — `LockConflict` recognised, anything else logged) answers the message page `bookingRefused` naming the order and listing the orders of the selection that ARE booked by now.
- **Year close** (`Close\InvoiceableOrdersCheck`, `orderConfig` → `openWorkChecks['period-close']`): a WARNING per order dated in the year that sits in a bookable phase (`confirmed`, `delivered` — every confirmed order: a service order may never see a delivery note) — «Auftrag 1 vom 14.10.2026 an Test-Firma xy steht in «Zu fakturieren» — noch nicht fakturiert …», the first 10 named, the rest counted (`SalesOrderRepository::inStatusBetween()`). A warning, not a block: the books of the year are complete without the order; whether its invoice belongs into the closed year is the office's call (the service date decides the VAT period).

## rules

- When code needs «the» status for a step (a new order, the order confirmation, the delivery note, the booking print) → MUST take the DEFAULT of the step's PHASE through `OrderStatuses` (`initial()`, `defaultOf()`, `actionTarget()`); MUST NOT name a status code in code (harness N1), and MUST NOT give a status behaviour of its own — behaviour is the phase's (`OrderPhase`, ADR-043 addendum 2026-10-15)
- When an order, its lines or its status change → MUST go through `OrderService` with a named actor and the version the caller saw; MUST NOT persist `SalesOrder`, `SalesOrderLine` or `SalesOrderStatusChange` anywhere else, and MUST NOT call `moveTo()`, `describe()`, `write()` or `linkInvoice()` outside the service
- When an order write changes what the order holds in stock terms → MUST end in the ONE private `syncStock()` with the COMPLETE state of the order in the PHASE of its CURRENT status; MUST NOT call `StockLedger::bringTo()` from a controller, template, repository or a second place (harness N4)
- When a screen rewrites an order → MUST send every existing line back with its `id`; MUST NOT rebuild the lines without ids (every line would get a new stock reference)
- When an order status row is written → MUST go through `OrderMasterData::save()` / `setActive()`; MUST NOT delete a row or change an existing row's code, and MUST NOT edit `order_statuses.json` through Windows PowerShell (DATA-JSON-001)
- When the order's totals or its invoice are needed → MUST map with `OrderInvoiceDraft::of()` and ask debtor (`preview()`, later `invoiceAndFinalize()`); MUST NOT compute VAT, line amounts or the 0.05 rounding in module-order (D11)
- When module-order needs debtor or article → MUST use their public seams (`InvoicingService`, `PaymentStates`, the repositories, `StockLedgers::default()`); debtor and article MUST NOT name `Z77\Module\Order` (harness N2)
- When an order unit of work locks → MUST take the `sales_order` rows with `SalesOrderRepository::lockIds()` and compare the version there before reading the order with `withLines()`; MUST NOT read the order plainly inside the unit of work before that lock
- When an order is booked → MUST go through `OrderService::book()` (the order rows locked first, debtor's `invoiceAndFinalize()` joined, link + booked status + log row `booking-print` + stock in the SAME unit of work); MUST NOT call `InvoicingService::invoice()` / `finalize()` or `invoiceAndFinalize()` for an order from anywhere else, and MUST NOT set the `invoiceBooked` status any other way
- When a screen offers the booking print a second time for the same selection → MUST decide the repeat with `Ui\BookingSelection::bookedBy()` (every order linked to a FINAL invoice at the version shown + 1) and answer the same PDF without calling `book()`; MUST NOT rely on the service for idempotency — it refuses an order with an invoice (`already-invoiced`)
- When a screen shows the order list's tabs → MUST derive them from the PHASES (`OrderListing::viewOf()` / `codesOf()` / `counts()`); MUST NOT list status codes per tab (a new status must land in its tab without code)
- When an order PDF is drawn → MUST take every amount from `OrderService::preview()` and the title from the phase (`OrderPdf::orderTitle()`); the order confirmation of a quote and the delivery note MUST be printed through the POST that calls `printConfirmation()` / `printDeliveryNote()` first; MUST NOT print them from a GET when they move the order (the status move would be skipped)
