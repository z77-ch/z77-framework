## mental model

`z77/module-order` holds the sales order of P7 slim (plan [`p7-order-plan.md`](../03-development/p7-order-plan.md), owner go 2026-10-14): quote and order are ONE record (D1), the status is DATA — a label in one of five FIXED PHASES that carry all behaviour (ADR-043 addendum 2026-10-15; until then behaviour flags per status, O4), every write ends in ONE call of the stock seam (O5), the invoice is drafted from the order by a pure mapper and booked by debtor (O1). Depends on kernel, persistence-doctrine, module-vat, module-contact, module-mandator, module-article and module-debtor; nothing depends on it (debtor and article never name it — harness N2). Built 2026-10-14: steps 3, 5 and 6 of plan §13, then steps 7–10 the same day — the list and the order window, the PDFs, the booking print `book()`, the year-close warning (see «screens, PDFs and the booking print»); the phases 2026-10-15.

- **Phase** (`Entities\OrderPhase`, an enum in code — the ladder, what wdv-630 called the *level*; ADR-043 addendum 2026-10-15; names of the addendum 2026-10-16): `new` «Eröffnet» (a quote — no stock, no booking print, PDF «Offerte») · `confirmed` «Termin» (stock RESERVED, booking print) · `delivered` (stock CONSUMED — «bereitgestellt», «geliefert», «zu fakturieren»; booking print) · `closed` (consumed, locked — «gebucht», «erledigt») · `cancelled` (no stock, locked). `reservesStock()`, `consumesStock()`, `isQuote()`, `isBookable()`, `isLocked()`, `allowsDeliveryNote()`, `isStartable()`, `allowsStart()` (Eröffnet, Termin), `rank()`. Whether a LINE moves stock is the ARTICLE's (`stock_relevant`, the ledger decides per variant) — a service or a free line never does.
- **Order status** (`Entities\OrderStatus`, file `framework/order/order_statuses.json`, seed-once from `order_statuses.default.json`): `code` (key, immutable), German `label`, `phase`, `position` (the order within the phase, not unique), `start` (THE start status of new orders — one for all, in Eröffnet or Termin, owner 2026-10-16), `phaseDefault` (the status an ACTION sets for its phase — Termin, Geliefert, Abgeschlossen), `active`; a switch the phase does not know reads as off (`isStart()`, `isPhaseDefault()`), a file without `start` reads its `new` default as the start status. No behaviour of its own — any number of statuses per phase, to order and find orders by. A stored phase the validator would refuse reads as `new` (`getPhase()`; `getPhaseValue()` is the raw value). Seed: Offerte (new, start) · Terminauftrag (confirmed, default) · Geliefert (delivered, default) · Zu fakturieren (delivered) · Gebucht (closed, default) · Erledigt (closed) · Storniert (cancelled — no default: no action cancels). Write path `Services\OrderMasterData::save()` / `setActive()` — no remove; the code of an existing row refused (`OrderStatusCodeChangedException`).
- **Validation** (`Validators\OrderStatusValidator`): code and label by debtor's shared master-data rule; the phase one of `OrderPhase` (field `phase`); position 0–999. No cross-row refusal since 2026-10-16: **setting a switch takes it over** — `OrderMasterData::save()` clears the start switch on every other row and the action default on the other rows of the phase (`OrderStatuses::takeovers()`, pure), in the same flush; `setActive(true)` takes nothing (the reactivated row drops a switch another row holds). No in-row invariants any more — a phase cannot contradict itself.
- **Selection by phase** (`Services\OrderStatuses`, pure over the rows, ordered phase · position · id): `defaultOf(phase)` = the active `phaseDefault` row, else the first active row of the phase; `initial()` = THE start status, else the first active status of `new`; `startable()` = every active status of a phase that is not locked (the create form's choice — a service order may start as «Terminauftrag»); `actionTarget(current, phase)` = the default of `phase` when the order stands BEFORE it, else null (a reprint). A code comes only from OUTSIDE (the order's own status, a target the user picked) — no code path selects a status by a literal code (harness N1).
- **Transitions** (`OrderStatuses::refusal()`, by hand through «Status ändern …»): forward, lateral and backward — all only while the order has NO invoice; with a booked invoice NOTHING by hand (`invoiced`, owner 2026-10-20 — replaces `backward-barred` / `cancel-barred`; «Erledigt» is for an order never invoiced); never to the default of `closed` (`booked-by-print-only` — the booking print's alone, no «gebucht» without an invoice); never to an inactive one (`inactive-target`); the same status is `same-status`. An order keeps a deactivated status. `targets()` is the confirm list.
- **Schema** (`Version20261014140000`, schema only; `Version20261014140001` the range `order` at 0 — schema and data apart, debtor's rule): `sales_order` (number unique — range `order`, owner O2/Q5: 1, 2, …; `status_code` by code; subject 200; order date; service from / to nullable; contact FK; price mode; currency; payment target code nullable; `ship_*` = debtor's `AddressSnapshot` embeddable, all empty = none; `notes` internal; `total_net/tax/gross` nullable; `invoice_id` FK nullable, NOT unique (D5); `source_type` / `source_ref`; actor stamps; `version`), `sales_order_line` (order FK, position, `parent_line_id` one level, `type` = debtor's `LineType` without rounding, `variant_id` FK nullable (D2), `article_number` snapshot, text, `quantity` DECIMAL(12,3) negative allowed, unit, unit price, discount hundredths, tax code, revenue account), `sales_order_status_change` (order FK, from / to code, `change_trigger` — `create` · `status` · `delivery-note` · `booking-print`; the column is not `trigger`, a reserved word —, reason, who, when). Named after article's migration (the line references `article_variant`).
- **The write path** (`Services\OrderService`, actor named by the caller, optional `StockLedger` and `InvoicingService` injected for the harness): `create(OrderDraft)`, `update(id, version, OrderDraft, ?StockConfirmation)`, `changeStatus(id, version, toCode, ?StockConfirmation)`, `printConfirmation(id, version, ?StockConfirmation)`, `printDeliveryNote(id, version, ?StockConfirmation)`, `book(list<{id, version}>, invoiceDate, ?StockConfirmation)` (step 9); reads `statuses()`, `editRefusal(order)`, `preview(order, ?invoiceDate)` (debtor's transient invoice of the order — D11), `deliveryAddressOf(order)`, `articleDefaults()`; the static `assertPrintable(order, status, phase)`. Refusals: `InvalidOrderException` (German message per field, `lines.{path}.{field}`), `OrderConflictException` (stale version, gone, a line id that is not the order's), `OrderRefusedException` with a stable `reason` (`no-status`, `status-unknown`, `not-startable`, `not-editable`, `not-printable` + the five transition reasons; the booking print's `nothing-selected`, `no-booked-status`, `already-invoiced`, `not-invoiceable`, `invoice-refused`). Every write flushes before it returns — a caller that joins the unit of work reads the written state and version.
- **The draft** (`OrderDraft` / `OrderLineDraft`, typed strings, no `Request`): an ARTICLE line takes text / unit / unit price from the article when empty — the price valid at the ORDER date (`PriceRepository::validAt()`), converted to the order's price mode with the rate of the article's tax code on the SERVICE date (`VatRates`) — and ALWAYS tax code and revenue account from the article (D3). Since 2026-10-18 every priced line is an article and the type is `service` or `text` only (ADR-043 addendum «positions»): a new free priced line and `lump-sum` are refused; a FREE line the order already holds is kept while unchanged, with its stored tax code and account (`freeLineUnchanged()`). Contact, payment target, variant and tax code that the order already holds stay valid although deactivated since (ADR-043 decision 19).
- **Line identity is stable** (decided at build): `update()` rewrites a line IN PLACE when the draft carries its `id`, inserts the new ones, removes the ones left out (orphan removal). The line id is the stock seam's line reference; a «replace all lines» save (plan §5's `reinvoice()` model) would have given every line a new id on every edit, and in a consuming status the journal would have seen consumed stock come back on every save (`StockReasonRequiredException`).
- **Lock order** (plan §5): `order` range (create only — the first write) → `sales_order` row EXCLUSIVE (`SalesOrderRepository::lockIds()` returns the version; compared there) → the order re-read REFRESHED (`withLines()`, `HINT_REFRESH`) → the line rows flushed (new rows; their ids are the stock references) → the stock call → the totals → the commit. What the draft needs is read and judged BEFORE the unit of work; under the lock D7 and the transition rule are judged again. A lock conflict propagates — the screen answers it with debtor's `LockConflict::is()` / `MESSAGE`.
- **Stock** (`private syncStock()`, the only `bringTo()` in the package — harness N4): the COMPLETE state through `Stock\OrderStockTargets::of(lines, phase)` — every article line (children too) with `reserved` = quantity if the PHASE reserves, `consumed` = quantity if it consumes, else `0.000`; negative stays negative; a LUMP-SUM article line counts as one unit (decided at build); free and text lines not sent. Because the ledger books only the difference against what it holds for the order (ADR-043 decision 12), skipping a phase books the end state directly and a status edited later cannot corrupt anything (the wdv-630 finding, plan §8.4). Triggers: `create`, `lines`, `status:{from}>{to}` (also for the order confirmation and the delivery note). A `StockReasonRequiredException` rolls everything back; with `StockConfirmation` the reason is written to the status log row (a pure line edit has no log row — the journal of P7b keeps the reason there). Until P7b the ledger behind the seam is `PendingStockLedger` — it books nothing.
- **Totals** (D11): `OrderInvoiceDraft::of($order, $order->getOrderDate())` → `InvoicingService::preview(…, openProfile: true)` inside the unit of work, after the order's lock (preview reads, writes nothing); net / tax / gross stored for the list; a refusal (`DebtorException`, `VatException`) leaves them null.
- **Editable** (D7): no invoice and the phase not locked (`closed`, `cancelled`) — else `not-editable`; with an invoice only a forward status change. No delete (D8). «Erledigt» and «Storniert» by hand (Q6) through `changeStatus()`.
- **Order confirmation and delivery note** (D6, ADR-043 addendum 2026-10-15): `printConfirmation()` moves a quote into the default of `confirmed` (trigger `confirmation`), `printDeliveryNote()` a confirmed order into the default of `delivered` (trigger `delivery-note`) and fills an EMPTY «Leistung von» with the print day (`SalesOrder::deliveredOn()`, the totals rewritten — owner 2026-10-16; a set date stays) — only FORWARD (`actionTarget()`); in or past the phase nothing is written and the order is answered as it is (no version needed: a double click prints twice, moves once). `assertPrintable()` refuses (`not-printable`) a cancelled order and the delivery note of a quote.
- **Invoice mapping** (`Invoicing\OrderInvoiceDraft::of(order, invoiceDate)`, pure, harness D): kind invoice, contact, invoice date (a day), service from = head or the invoice date, service to, price mode, currency, payment target, terms null (the profile's), address null (debtor snapshots the invoice address), subject «Auftrag {nr} · {Betreff}» / «Auftrag {nr}» and the order's «Betreffname» with it (`subjectLabel`, owner 2026-10-21 — the invoice prints «Projekt: Auftrag 12 · Umbau»), lines 1:1 with children beneath their parent, origin `order` / number, lines `order-line` / id.
- **Screen** Stammdaten › Aufträge › Auftragsstatus (`/backend/order/order-status/list`, host `Order/OrderStatusController`, group `order`): a standard list along the ladder (state icon · Code · Bezeichnung · Phase · Sortierung · Wird gesetzt durch — the ACTION that sets a default: neuer Auftrag, Auftragsbestätigung, Lieferschein, Buchungsdruck · Aktiv switch), action cell «+ Status». The status opens as a WINDOW with help (code fixed after creation, label, phase — a select of the fixed phases —, «Sortierung», «Startstatus für neue Aufträge» (`start`, in Eröffnet and Termin) and the action default worded by the phase — «Wird gesetzt beim Druck der Auftragsbestätigung» … (`OrderPhase::defaultSwitchLabel()`; owner 2026-10-15: «Vorgabe der Phase» was understood by no one), none for Eröffnet and Storniert; setting either takes it from the status that held it (owner 2026-10-16); «Wird gesetzt durch» lists both («neuer Auftrag, Auftragsbestätigung»); the help explains the phases) — deviation from plan §9.5's «⋮ → edit dialog», the article's reason: a modal popup cannot carry the field help (ADR-048). The switch answers with its row; a refused activation names the phase's other default.
- **Navigation**: seed `module-order.json` — `auftraege-liste` «Aufträge» (route `backend/order/order/list`, sort 0 under debtor's area `auftraege` — the FIRST entry; debtor's seed moved Rechnungen / Debitoren / Zahlungseingänge / Mahnungen to 1–4) and `auftragsstatus` «Auftragsstatus» under debtor's `stammdaten-auftraege`, sort 10. ## rules

- When code needs «the» status for a step (a new order, the order confirmation, the delivery note, the booking print) → MUST take the DEFAULT of the step's PHASE through `OrderStatuses` (`initial()`, `defaultOf()`, `actionTarget()`); MUST NOT name a status code in code (harness N1), and MUST NOT give a status behaviour of its own — behaviour is the phase's (`OrderPhase`, ADR-043 addendum 2026-10-15)
- When an order, its lines or its status change → MUST go through `OrderService` with a named actor and the version the caller saw; MUST NOT persist `SalesOrder`, `SalesOrderLine` or `SalesOrderStatusChange` anywhere else, and MUST NOT call `moveTo()`, `describe()`, `write()` or `linkInvoice()` outside the service
- When an order write changes what the order holds in stock terms → MUST end in the ONE private `syncStock()` with the COMPLETE state of the order in the PHASE of its CURRENT status; MUST NOT call `StockLedger::bringTo()` from a controller, template, repository or a second place (harness N4)
- When a screen rewrites an order → MUST send every existing line back with its `id`; MUST NOT rebuild the lines without ids (every line would get a new stock reference)
- When an order line carries a price → MUST reference an article (variant); MUST NOT accept a new free priced line or the type `lump-sum` (a lump sum is an article with quantity 1) — the one exception is an existing free line sent back UNCHANGED with its id (`OrderService::freeLineUnchanged()`, ADR-043 addendum 2026-10-18)
- When an order's price mode changes while it has priced lines → MUST convert the prices — the window through core.js «price mode», the server through `OrderService` from the posted `prices_mode` (an article line equal to the article's price in the posted mode → the article's price in the order's mode; any other → `convertByRate()`, cents half away from zero); MUST NOT store a price typed under one mode as the other mode's price, and MUST NOT let the window set `prices_mode` before every row is converted (owner decision C 2026-10-18)
- When a screen takes a contact as the customer of a NEW order → MUST have it be a debtor first (debtor's picker «Debitor anlegen»); MUST NOT take a contact without a debtor profile as a new customer (owner decision D 2026-10-18 — an existing order keeps its own). The re-check is `OrderService`'s own since 2026-10-19 (`contact_id`, `DebtorProfileService::notDebtor()`) — no second check in the window.
- When an importer, a shop or a script creates an order → MUST create the contact AND the debtor FIRST (`DebtorProfileService::open()`, the one creation path), then the order (owner 2026-10-19 — `OrderService` refuses a customer without a profile; the booking print's `openDebtorProfile()` is only the fallback for OLD orders, plan D9)
- When an order status row is written → MUST go through `OrderMasterData::save()` / `setActive()`; MUST NOT delete a row or change an existing row's code, and MUST NOT edit `order_statuses.json` through Windows PowerShell (DATA-JSON-001)
- When the order's totals or its invoice are needed → MUST map with `OrderInvoiceDraft::of()` and ask debtor (`preview()`, later `invoiceAndFinalize()`); MUST NOT compute VAT, line amounts or the 0.05 rounding in module-order (D11)
- When module-order needs debtor or article → MUST use their public seams (`InvoicingService`, `PaymentStates`, the repositories, `StockLedgers::default()`); debtor and article MUST NOT name `Z77\Module\Order` (harness N2)
- When an order unit of work locks → MUST take the `sales_order` rows with `SalesOrderRepository::lockIds()` and compare the version there before reading the order with `withLines()`; MUST NOT read the order plainly inside the unit of work before that lock
- When an order is booked → MUST go through `OrderService::book()` (the order rows locked first, debtor's `invoiceAndFinalize()` joined, link + booked status + log row `booking-print` + stock in the SAME unit of work); MUST NOT call `InvoicingService::invoice()` / `finalize()` or `invoiceAndFinalize()` for an order from anywhere else, and MUST NOT set the `invoiceBooked` status any other way
- When a screen offers the booking print a second time for the same selection → MUST decide the repeat with `Ui\BookingSelection::bookedBy()` (every order linked to a FINAL invoice at the version shown + 1) and answer the same result list without calling `book()`; MUST NOT rely on the service for idempotency — it refuses an order with an invoice (`already-invoiced`)
- When a screen shows the order list's tabs → MUST derive them from the PHASES (`OrderListing::viewOf()` / `codesOf()`); MUST NOT list status codes per tab (a new status must land in its tab without code)
- When an order or its PDFs carry the «Betreffname» → MUST go through debtor's `SubjectLabel` (`normalize()`, `line()`) and pre-fill a NEW order from `SubjectLabelDefaults`; MUST NOT print the label without the subject or compose «label: subject» in a template
- When the order window shows VAT (the MWST column, the rates, the VAT rows of the totals) → MUST ask `OrderService::chargesVat()` (debtor's one rule) and leave all three out when it answers false; MUST NOT convert a price between the modes with a rate then (`convertByRate()` returns it unchanged)
- When `pdf/order` is drawn without VAT → MUST pass `vatNote` = the mandator's `documentVatNote()` (`OrderPdf`, read through `Creditor::mandator()`) and hand it to debtor's `pdf/documentSummary` as `note`; MUST NOT draw the note in the order's own layout, store it on the order, or print it on a preview that carries VAT or on the delivery note
- When an order PDF is drawn → MUST take every amount from `OrderService::preview()` and the title from the phase (`OrderPdf::orderTitle()`); the order confirmation of a quote and the delivery note MUST be printed through the POST that calls `printConfirmation()` / `printDeliveryNote()` first; MUST NOT print them from a GET when they move the order (the status move would be skipped)
